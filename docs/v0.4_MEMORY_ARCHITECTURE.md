# v0.4 — Memory Architecture Update

**Status:** DESIGN. Not yet implemented. Drafted 2026-05-13.

**Companion to** [`MEM_FUSION_ARCHITECTURE.md`](MEM_FUSION_ARCHITECTURE.md) and [`CONSTELLATION_ARCHITECTURE.md`](CONSTELLATION_ARCHITECTURE.md). Once v0.4 ships, the load-bearing sections of those documents get amended to match this design and this file gets archived.

**Branch / tag context:** v0.3 line is cut at tag `v0.3.1` with maintenance branch `v0.3.x`. v0.4 work happens on `main`.

---

## 1. Why v0.4

v0.3 shipped a working group-memory system but left a real privacy gap: the dual-routing logic in `/remember` was a Band-Aid over a deeper architectural problem. The problem:

> v0.3 assumed Mem-Fusion could *classify* what's safe to share with teammates by looking at the content (rule vs. knowledge). But classification is inherently fuzzy, and any mis-classification on the wrong side becomes a privacy leak — a personal preference auto-pushed to your teammates' machines.

v0.4 replaces *content classification* with *explicit user intent*. Every memory has a `group` tag that the user sets (explicitly or by default). The group is the routing key for sharing. There is no fuzzy heuristic — if a memory isn't tagged for a group with peers, it doesn't leave the local machine.

This also dissolves the v0.3 separation between "local" and "federation" entries. There is one kind of entry now, distinguished only by which group it belongs to.

---

## 2. The new model in one sentence

**Every memory has a group tag. Sharing happens by group. Default group is `personal`. Same protocol, same storage, same dedup — only the peer list differs per group.**

## 3. Object model

### Memory entry

A Qdrant point with:

| Field | Purpose |
|---|---|
| `content` | The memory text, verbatim |
| `vector` | 768-dim embedding (nomic-embed-text) |
| `content_hash` | Dedup + integrity key |
| `groups` | **Routing key for sharing.** A list of group names. Default `["personal"]`. A memory can belong to multiple groups simultaneously — `["personal", "engineering@branch"]` means "share with my own machines AND with engineering teammates." Set explicitly per-memory by the user. |
| `type` | Decorative filter (`decision` / `preference` / `fact` / `error` / `code` / `context` / `session`). Does NOT gate sharing. |
| `timestamp` | When this entry was stored locally |
| `origin_node` | Which peer originated this memory (= self for locally-originated) |
| `submitted_at` | When the memory was promoted to its group (= timestamp for locally-originated; preserved across pulls) |
| `importance` | 1–5, as today |
| `project`, `tags`, `session_id` | As today |

Notable absence: the `source` field (`local` / `group`) goes away. The `groups` field replaces its routing role; `origin_node` covers the provenance role.

### Group

A named scope identifying who can see a memory. Examples: `personal`, `engineering@branch`, `LegalRO`.

- A memory can belong to **one or more groups** simultaneously. Multi-group membership is intentional: a decision relevant to both `engineering@branch` and `platform-team@branch` shouldn't have to be written twice.
- A peer can belong to **multiple** groups (multi-membership — relaxes the v0.3 single-membership limit).
- The default group set is `["personal"]`. New installs of Mem-Fusion + Constellation get a `personal` membership pre-configured with empty peers.
- `personal` is not exclusive — a memory can be in `["personal", "engineering@branch"]`, meaning it lives on your own machines (personal peers) AND with your engineering teammates.

### "Personal" group — the implicit default

`personal` is a real group, not a sentinel for "local". Its peers list:

- **Empty** = single-machine personal memory. Memories tagged `personal` never leave this machine.
- **Populated** = your-own-machines. Memories tagged `personal` propagate across machines you own.

This is the load-bearing simplification of v0.4: there's no separate "local-only" code path. A truly-local memory is just one with `groups: ["personal"]` whose `personal` group has an empty peer list.

## 4. /remember skill — the new shape

```
/remember <content>                              → store with groups=[personal]
/remember <content> for <group>                  → store with groups=[<group>]
/remember <content> for <group1>, <group2>, …    → store with groups=[<group1>, <group2>, …]
/remember push                                   → for each group with peers, push memories
                                                     where that group appears in the entry's
                                                     groups list
/remember push <group>                           → push only that group's memories
/remember pull                                   → for each group with peers, pull from
                                                     that group's peers; merge into local store
/remember pull <group>                           → pull only that group's peers
```

The v0.3 classify-and-route logic is gone. Routing is now entirely explicit via the `for <group>[, <group>, …]` clause. Default = `["personal"]` (local).

**Examples:**

```
You:   /remember always use uv for Python environments
Claude: ✓ Stored with groups=[personal]. Stays on this machine.

You:   /remember We picked Postgres 16 for the auth service, for engineering@branch
Claude: ✓ Stored with groups=[engineering@branch].
        ✓ Pushed to engineering@branch peers:
            - bob-mac:       stored
            - alice-desktop: stored

You:   /remember API gateway uses bearer tokens for service-to-service auth,
       for engineering@branch, platform-team@branch
Claude: ✓ Stored with groups=[engineering@branch, platform-team@branch].
        ✓ Pushed to engineering@branch: bob-mac stored, alice-desktop stored.
        ✓ Pushed to platform-team@branch: dave-mac stored.
        (One memory, two groups, three peers — duplicate peers receive once each.)
```

A few notes:
- `for <group>[, <group>, …]` is the explicit-group syntax. The user has to opt-in to sharing. There is no auto-sharing.
- A push fan-out de-duplicates peer endpoints across groups — if `bob-mac` is in both `engineering@branch` and `platform-team@branch`, he receives the memory once, not twice. The receiver's dedup-merge rule (§6) handles the case where it arrives via different routes anyway.
- `/remember push` (without a group) iterates every configured group with non-empty peers and pushes memories whose `groups` list includes that group. Personal group with empty peers skips silently.
- `type=preference` continues to exist as a filter (search/recall semantics) but doesn't gate sharing. A `type=preference` memory in `groups=[engineering@branch]` would share with engineering teammates; the user opted into that by tagging the group explicitly.

## 5. Storage model — dual write

Every memory is written to **both** the Qdrant vector DB **and** the file-based memory tree. The vector DB is the source of truth for semantic search; the file-based mirror is a resilience layer.

### Why both

1. **Search** — Qdrant gives semantic similarity over 768-dim vectors. Files don't.
2. **Resilience** — If Qdrant corrupts or Mem-Fusion is uninstalled, the files remain in `~/.claude/projects/<encoded-cwd>/memory/`. Claude Code loads them at session start. Claude keeps working — just without semantic search.

### File layout

Each memory has exactly one canonical file on disk, regardless of how many groups it belongs to. Files live in a flat `entries/` directory; MEMORY.md cross-lists them under each relevant group's section.

```
~/.claude/projects/<encoded-cwd>/memory/
├── MEMORY.md                          # top-level index, organized by group
└── entries/
    ├── <slug>.md                      # one file per memory, regardless of group count
    ├── <slug>.md
    └── ...
```

Why one file (not one-per-group-subdirectory): a memory in `groups: [engineering@branch, platform-team@branch]` is *one* memory. Duplicating it as separate files under each group's subdirectory would create the same drift problem v0.3 had — N copies that have to stay in sync. The canonical file lives once; MEMORY.md is the index that surfaces it under multiple sections.

### File format

Per-memory `.md` file:

```markdown
---
name: <short human-readable name>
description: <one-line summary>
type: <decision | preference | fact | error | code | context | session>
groups: [<group>, <group>, …]
created_at: <ISO-8601 UTC>
qdrant_id: <UUID — pointer to the vector DB row>
---
<content body>
```

The `qdrant_id` is a back-reference. If Qdrant goes down, the file is still readable. If Qdrant comes back up, the vector DB entry can be reconstructed from the file (re-embed via Ollama).

### MEMORY.md index

Top-level index with one section per group. A memory in multiple groups appears under each.

```markdown
# Memory Index

## personal
- [Use uv for Python](entries/use-uv-for-python.md) — Always use uv for Python environments on this machine.
- [Concise responses](entries/concise-responses.md) — I prefer concise replies.

## engineering@branch
- [gRPC for internal RPC](entries/grpc-for-internal-rpc.md) — Use gRPC for service-to-service; HTTP/JSON for public APIs.
- [Postgres 16 + LR for auth](entries/postgres-16-lr-auth.md) — We picked Postgres 16 with logical replication for the auth service.
- [API gateway auth](entries/api-gateway-auth.md) — Bearer tokens for service-to-service. _Also in: platform-team@branch_

## platform-team@branch
- [API gateway auth](entries/api-gateway-auth.md) — Bearer tokens for service-to-service. _Also in: engineering@branch_
```

The `_Also in: …_` annotation on multi-group entries makes the multi-membership visible at the index level. Loaded at session start by Claude Code's existing auto-memory mechanism.

### Write path

`core.store_memory(...)` becomes a single entry point that:

1. Computes `content_hash`. Dedup check on `content_hash` — see merge rule below.
2. If a matching entry exists with the same content but a *different* `groups` list: **merge** — union the new groups into the existing entry's groups, update both the Qdrant payload and the file's frontmatter, refresh MEMORY.md to add the entry under any newly-relevant group sections. Skip re-embedding.
3. If no matching entry exists: embed via Ollama, generate UUID, write Qdrant payload (with `groups: [...]`), write the canonical `entries/<slug>.md`, update MEMORY.md to list under every group in the entry's `groups`.
4. Returns `{status: "stored" | "merged", qdrant_id, file_path, groups: [...]}`.

If file-write fails but Qdrant succeeds: log a warning, return success (Qdrant is the source of truth). If Qdrant fails but file write succeeds: log a warning, return `{status: "stored_to_file_only"}` so caller knows search won't reach it until vector DB recovers.

## 6. Sharing model — group-keyed

### Push

`/remember push [group]` triggers `group_push` on the Constellation gateway:

1. Daemon reads its config — finds all `memberships[]` entries with non-empty `peers[]`.
2. If a specific group was requested: only that membership.
3. For each such membership `G`, scrolls local Qdrant for entries where `G ∈ groups` (Qdrant array-match filter). The same memory may match multiple memberships — that's expected for multi-group entries.
4. De-duplicates the recipient peer set across memberships before fan-out: a peer in two of the user's groups receives each memory at most once per push call.
5. For each (peer, memory) pair, calls `POST /memory/put` with the full record including its `groups` list (preserved verbatim).
6. Returns per-peer-per-group telemetry.

### Pull

`/remember pull [group]` triggers `group_pull`:

1. For each membership (or just the named one), iterate peers.
2. Call `GET /memory/since?group=<group>&cursor=<max submitted_at across local entries whose groups list includes this group>` on each peer.
3. Each returned entry carries its `groups` list verbatim. Apply the **dedup-merge rule**: if `content_hash` already exists locally, union the incoming `groups` into the local entry's `groups` (update Qdrant payload + the canonical file's frontmatter + MEMORY.md cross-listings). If `content_hash` doesn't exist locally, insert with the received `groups` as-is.
4. Returns per-peer-per-group telemetry.

### Dedup-merge rule (additive)

When a memory arrives (via push receive or pull) and we already have its `content_hash`:

| Local groups | Incoming groups | Result |
|---|---|---|
| `[A]` | `[A]` | No change — already have it |
| `[A]` | `[A, B]` | Merge → `[A, B]` |
| `[A, B]` | `[A]` | No change — local groups are a superset |
| `[A]` | `[B]` | Merge → `[A, B]` |
| `[A, B]` | `[C]` | Merge → `[A, B, C]` |

**Always additive, never subtractive.** Receiving a memory never removes it from a group; it only adds groups. Removing a group from a memory is a deliberate user action (out of scope for v0.4 — see §11).

The merge rule prevents echo-bugs (Alice pushes to Bob with `groups: [eng]`; Bob pushes back to Alice via a different path with `groups: [eng]` — Alice already has it with `groups: [eng, personal]`, no change).

### What's NOT in this protocol

- **No cross-group propagation by routing.** A memory in `engineering@branch` doesn't *automatically* enter `personal` because peers overlap. The memory's `groups` field is the only thing that determines routing.
- **No re-grouping at receive time.** Receiver stores the entry with the originator's `groups` list, then merges if a local copy already exists (additive, per rule above).
- **No content classification.** Routing is by tag, not by inspection.
- **No subtractive merge.** Receiving a memory with a smaller `groups` list never shrinks the local entry's `groups`.

## 7. Constellation alignment

### Multi-membership

v0.3 restricted `memberships` to length 1. v0.4 lifts that. Config:

```json
{
  "node_name": "alice-mac",
  "peer_listen_address":    "0.0.0.0:7533",
  "gateway_listen_address": "127.0.0.1:7534",
  "qdrant_url":             "http://127.0.0.1:6333",
  "state_dir":              "~/.local/share/mem-fusion/constellation",
  "memberships": [
    {
      "group_name": "personal",
      "peers": [
        { "node_name": "alice-desktop", "endpoint": "http://10.0.0.4:7533" }
      ]
    },
    {
      "group_name": "engineering@branch",
      "peers": [
        { "node_name": "bob-mac",      "endpoint": "http://10.0.0.5:7533" },
        { "node_name": "carol-laptop", "endpoint": "http://10.0.0.7:7533" }
      ]
    }
  ]
}
```

The `personal` membership is pre-populated by the installer with `peers: []`. Cross-machine personal sync is opt-in: the user adds their other machines to the personal group's peer list when they're ready.

### Out-of-the-box personal-group experience

After installing Constellation on each of your machines and adding each other to the personal group's peers list, your memories sync automatically across your devices. Same protocol as teammate-group sharing, just a different peer list.

## 8. Backward compatibility with v0.3 data

Existing v0.3 vector DB entries lack a `groups` payload field (some were `source=local` without any group; others were `source=group` with a singular `group_name`).

**Read-time fallback rule:** any entry without a `groups` field is treated as `groups: ["personal"]`. v0.3 entries with `source=group` and `group_name=X` are read as `groups: [X]`. No mandatory data migration — the read-time fallback gives every legacy entry a usable shape.

`v0.3 → v0.4 install` script proposed (optional, opt-in):
- Iterate all entries lacking `groups` payload.
- For entries with `source=group` and `group_name=X`, write `groups: [X]`.
- For entries without `source=group`, write `groups: ["personal"]`.
- Drop the deprecated `source` and `group_name` fields after migration.
- Idempotent; can be re-run.

## 9. What stays the same from v0.3

The structural pieces below don't change; v0.4 is a re-routing inside the same skeleton:

- **Two-listener Constellation daemon** (peer surface + gateway surface) — same code shape, same ports.
- **`core.py` shared library** — same module surface, `store_memory` gets a `groups` arg (list of strings, default `["personal"]`) but otherwise unchanged.
- **`mem_fusion.py` MCP server** — 11 tools today; `group_pull` / `group_push` adapt to multi-group routing, signatures unchanged.
- **Test harness** (`tests/lib/harness.py`) — same lifecycle helpers.
- **Self-contained test discipline** — every test still spins up its own Qdrant + daemons; nothing depends on externally-running infrastructure.
- **The four hooks** — `SessionStart`, `UserPromptSubmit`, `Stop`, `PostToolUse:Write`. The Stop hook's extraction logic stays; what changes is that every hook-captured entry gets `groups: ["personal"]` by default. Routing-by-type goes away.

## 11. Open questions still TBD

- **Push idempotency.** Today's push sends the same memory every time it's pushed. v0.4 could track per-(peer, group, memory) push state to skip already-delivered entries. Or accept the redundancy (the receiver dedup-merges). MVP: accept the redundancy.
- **Group-rename ergonomics.** What happens if a user wants to rename `engineering@branch` to `eng@branch`? Probably: rename in config + bulk-update Qdrant payload (every entry whose `groups` contains `engineering@branch` gets it replaced with `eng@branch`) + update MEMORY.md section headings. Out of scope for v0.4; document as a future operational task.
- **Re-grouping existing memories.** Today's `/remember <content> for <group1>, <group2>` works at store time. A separate `/remember add <id> to <group>` (or `/remember remove <id> from <group>`) would let users adjust group membership on existing memories. Subtraction is non-trivial in distributed settings (peers in the removed group already have the memory; removing it from your `groups` list doesn't un-share it). Out of scope for v0.4 — surface it when real usage demands it.
- **Hook-extracted memory types.** Today's Stop hook extracts `preference`, `decision`, `error`. Under v0.4, all of these store with `groups: ["personal"]` by default — including preferences (which previously were the privacy-leak risk). Group tag handles the safety. Worth re-examining whether the hook's pattern extractors are still well-calibrated; might be over-eager for v0.4's clearer semantics.
- **Cross-machine personal scope.** When a user adds another of their machines to the `personal` group's peer list, do auto-extracted hook memories (session summaries, etc.) propagate? Probably yes — that's the value of personal-as-real-group. Worth confirming with real usage whether this is desired or noisy.

## 12. What this dissolves vs. what it preserves

**Dissolves:**
- The dual-routing skill logic (classify rule vs. knowledge)
- The `source=local` vs `source=group` distinction
- The "/CLAUDE.md is hand-edited but vector DB is automatic" two-mode user mental model
- The single-membership constraint on Constellation
- The need for hook-extracted preferences to route differently from hook-extracted decisions

**Preserves:**
- All test infrastructure
- The protocol surfaces (peer + gateway HTTP, MCP tools)
- The dedup-by-content-hash invariant
- Verbatim vector preservation across the wire
- Self-contained test discipline
- The two-process model (Mem-Fusion stdio MCP + Constellation HTTP backend)

**Adds:**
- File-based dual-write for resilience
- Multi-group membership per peer (a peer can be in any number of groups)
- **Multi-group membership per memory** (a memory can belong to any number of groups simultaneously)
- Group-keyed sharing as the routing primitive
- The `personal` group's special role as the unified default
- Additive dedup-merge on receive (a memory's groups list grows on cross-arrival, never shrinks)

# v0.6 Personal Sync — Zero-Config Slack Substrate

**Status:** Architect design, 2026-05-19. Continues on `main` (no v0.6 branch). Targets two use cases through one substrate: personal device-to-device sync and team channel collaboration.

**Author:** Claude-Architect (brmaclap0819, this session)

**Supersedes:** the verbose "mode/format/auto_sync/poll_interval/batch" connector config sketch from the same session. Architect call: less is more.

**Companion drafts (parked):** `docs/drafts/v0.6_EMAIL_CONNECTOR_DRAFT.md`.

---

## Design principle

**The user never thinks the word "connector."** They think "channels I share to." The system observes channel membership, infers mode, picks wire format, sets cadence — all without configuration. State lives in a sqlite DB the user never touches.

The previous design exposed `mode`, `format`, `auto_sync`, `poll_interval_seconds`, and `batch.max_memories` as user-facing knobs. That was architectural fumes. v0.6 removes them.

## Architecture in one model

```
                ┌──────────────────────────────────────┐
                │  ~/.local/share/mem-fusion/sync.db   │   ← only state
                │                                       │
                │  channels(channel_id, name,           │
                │           member_count,               │
                │           last_seen_active,           │
                │           cursor,                     │
                │           registered_at)              │
                └──────────────────────────────────────┘
                              ▲
                              │ observes + adapts
                              │
┌─────────────────────────────┴─────────────────────────────┐
│       Constellation daemon — auto-sync workers             │
│                                                             │
│   For each channel where member_count == 1 (personal):     │
│     Pull worker — adaptive 10s/60s/300s                    │
│     Flush worker — every 30s OR 10 buffered memories       │
│                                                             │
│   For each channel where member_count >= 2 (team):         │
│     Pull worker — slow (120s default, adaptive)            │
│     No flush worker — push is user-explicit (`for <name>`) │
└─────────────────────────────────────────────────────────────┘
                              ▲
                              │
                          Slack API
                       (user-tier OAuth
                        reused from Claude MCP)
```

The user-facing primitives stay tiny:

| What they do | What happens |
|---|---|
| `install.sh` | Finds or creates `mf-<userhandle>-sync` private channel. Registers it in sync.db. Auto-sync starts. **Done.** |
| `/remember <content>` | Stored locally + auto-flushed to personal channel. Other machines pull within seconds. |
| `/remember <content> for #engineering` | Channel resolved via Slack API; if new, observed (member count read), registered in sync.db with inferred defaults, memory pushed. |
| `/sync status` | "Syncing 3 channels — personal (last 12s), engineering (4m, 47 members), product (2h, 12 members)." |
| `/sync forget #channel` | Soft-delete: stop pulling, leave history + cursor intact. |

## Inference rules (no config required)

| Signal | Inference |
|---|---|
| Channel `member_count == 1` | Personal substrate. Compact wire format (gzip+base64, no vector). Auto-sync ON. Aggressive polling (10s active, 60s/300s back-off). |
| Channel `member_count >= 2` | Team channel. §5.1 JSON wire format (humans read). Auto-sync OFF. Slow polling (120s). Push is user-explicit only. |
| Channel becomes active (new messages last 5 min) | Tighten poll → 10s |
| Channel idle > 5 min | Loosen poll → 60s |
| Channel idle > 1 hr | Loosen poll → 300s |
| Slack 429 response | Exponential back-off + batch harder on flush |
| Membership changes (teammate joins personal channel) | Next push re-evaluates: switch to JSON format if member_count becomes >=2 |

All inferences happen against `member_count` and `last_seen_active` columns in sync.db, refreshed on every pull. No daemon restart needed when membership changes.

## Wire format compatibility

Receivers detect format per-message:

```
1. If body starts with "[mf v0.6 compact n=...]"  →  parse_batch (CompactSlackConnector)
2. Else if body contains a fenced JSON block      →  parse_envelope (SlackConnector, §5.1)
3. Else                                            →  not_envelope, skip
```

Senders pick format per-channel based on `sync.db.channels.member_count`:

```
member_count == 1  →  CompactSlackConnector.format_batch([env1, env2, ...])
member_count >= 2  →  SlackConnector.format_envelope(env1)   (one body per memory)
```

This means **the same Slack channel can mix formats during a membership transition** — a personal channel that gains a member will accept the next compact post just fine (you're still alone for that moment), but the post after the membership change uses JSON. Both formats coexist in channel history; receivers handle either.

### Compact wire format (Format C, from local benchmark)

```
[mf v0.6 compact n=10 sha=a1b2c3d4]
H4sIAAAAAAAAA+1abXLbNhL+K7sP9Bw4...
```

- **Header line:** `[mf v0.6 compact n=<N> sha=<hex8>]` — parser fast-skips non-matches; `n` is envelope count for telemetry; `sha` is sha256[:8] of the base64 payload for transport integrity.
- **Body:** `base64(gzip(json.dumps([env1, env2, …], separators=(',',':'))))` — vectors stripped (receiver re-embeds via Ollama at ~25 ms per envelope).
- **Compression ratio:** measured 13× vs current §5.1 JSON on this peer's 50-memory sample. 200-memory backlog catches up in ~8 Slack messages, ~5 s wall-clock.
- **Per-envelope `content_hash`** is the same NFC+UTF-8+sha256[64] as §5.1 — `verify_integrity` unchanged.

### Compatibility matrix

| Sender → Receiver | v0.5 JSON | v0.6 compact |
|---|---|---|
| v0.5 receiver | ✅ stored | ❌ `not_envelope` (compact header doesn't match v0.5 regex) — message ignored, no error |
| v0.6 receiver | ✅ stored (via SlackConnector path) | ✅ stored (via CompactSlackConnector path) |

So **v0.6 → v0.5 is a soft downgrade**: v0.5 receivers silently ignore compact posts. A user on personal-sync between a v0.6 laptop and a v0.5 desktop would see asymmetric sync (desktop receives, laptop misses). Mitigation: install.sh `0.5.0-020`+ blocks personal-sync setup until both ends are on v0.6.

## Resolved decision points (architect defaults)

These were open in the design conversation; resolved here.

### 1. Default personal channel name
**`mf-<userhandle>-sync`** — namespaced enough to avoid collision with most workspace channel naming, predictable enough for users to find via Slack search. `<userhandle>` is the Slack `user_id`'s associated handle (e.g., `mcoopet`). For users with display-name conflicts, falls back to the workspace-unique `user_id`-suffixed form: `mf-<userhandle>-<userid-suffix>-sync`.

### 2. Auto-create vs auto-find at install
**Try find first, create if absent, fall back to a single user prompt only if creation fails.**

```
install.sh personal-sync setup:
  1. slack_search_channels(query="mf-<userhandle>-sync")
  2. If found and creator == current user: adopt it.
  3. Else slack_create_channel(name="mf-<userhandle>-sync", is_private=true)
  4. If creation fails (workspace policy blocks channel creation):
       prompt user: "Create a private channel for personal sync, then paste its channel ID."
       (one-time)
  5. Register in sync.db, start daemon workers, exit.
```

Workspace-creation failures are real (some orgs lock down channel creation). Surface the error clearly with the one-line remediation.

### 3. Push-on-store for bare `/remember <content>`
**YES, auto-push to personal-sync channel.** This is the entire v0.6 story — stuff just works. Privacy invariant unchanged: the personal channel is by definition member_count==1, so "auto-push to personal" never touches any other audience. Non-personal channels still require explicit `for <name>` naming.

### 4. `/sync forget` semantics
**Soft delete.** Mark `channels.registered_at = NULL` (or add a `disabled` column). Stop pulling. Leave history + cursor untouched. Re-enabling is `/sync resume <channel>` — picks up from the old cursor cleanly.

For hard delete (clear cursor + remove channel from sync.db entirely), add `/sync purge <channel>` as a separate command. Distinct verbs prevent the "I meant to pause but accidentally wiped state" failure mode.

## Migration from v0.5

v0.5 ships `~/.local/share/mem-fusion/connector.json`. v0.6 ships sync.db. Migration is one-shot at first v0.6 daemon start:

```
1. If sync.db doesn't exist: create schema.
2. If connector.json exists:
     For each entry in connector.json["connectors"]:
       - Look up channel via slack API → get member_count
       - Insert into sync.db.channels with appropriate format inferred
       - Copy any existing cursor from connector_cursors.json
3. Leave connector.json with a header comment pointing at sync.db.
4. After v0.7 ships, remove connector.json reading entirely.
```

Cursor format change: v0.5 stored ISO timestamp from `envelope.submitted_at`. v0.6 stores **Slack `message_ts`** (per-channel monotonic, unambiguous, no "back-posted envelope from older origin" footgun we hit in the architect session). Migration: re-parse each v0.5 cursor's ISO against the channel's history to find the matching Slack message_ts; if no exact match, use the next-newer message_ts in the channel.

## Test plan summary

1. **Wire round-trip** — encode 50 envelopes via CompactSlackConnector → simulate Slack delivery → decode → assert byte-exact content + integrity.
2. **Mixed-format channel** — drop a v0.5 §5.1 JSON envelope and a v0.6 compact batch in the same fixture; assert v0.6 parser dispatches each correctly.
3. **Membership-transition mid-sync** — channel starts at member_count==1, second member joins, sender re-evaluates and switches format on next flush.
4. **Two-machine E2E** — laptop offline 1h while desktop writes 100 memories; laptop comes online, daemon catches up; assert wall-clock under 30s; assert all 100 memories present locally on the laptop.
5. **Loopback / dedup** — outgoing memories returned in pull are loopback_skipped; content_hash dedup catches cross-channel duplicates (personal + team both carrying the same memory).
6. **Slack 429 back-off** — synthetic rate-limit response; flush worker backs off, retries with larger batch; no memory loss.
7. **`/sync forget` + `/sync resume`** — soft-delete persists cursor; resume picks up cleanly.

## Open questions for architect review

None blocking the prototype. All four design questions resolved above. Decision review points likely to surface during implementation:

- Cursor representation: ISO timestamp vs Slack message_ts. Architect call: **Slack message_ts** (closes the cursor-regression bug from the v0.5 architect session).
- Buffer file format: `jsonl` (one envelope per line) vs `pickle` (faster, less debuggable). Architect call: **jsonl** (debuggable, human-greppable, no Python-only lock-in).
- Daemon implementation: extend Constellation's existing async loop vs spawn separate worker process. Architect call: **extend Constellation** (one fewer launchd plist).

If any of these turn out wrong in implementation, the architect (Mitch or Claude-Architect hat) lands a revision PR with rationale.

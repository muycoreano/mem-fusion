## Strategic thesis (architect's proposed direction)

The competitive analysis from 2026-05-17 (memory `3b9c8720`, doc `~/CTO Assistant/drafts/Competitive_Analysis_Mem_Fusion_2026-05-17_1245.md`) identified a four-property intersection that no current competitor occupies:

1. Local-first by default
2. P2P personal mesh
3. Role-attributed per-memory identity (the v0.6 work)
4. Explicit group-keyed sharing as a privacy invariant

v0.5 and v0.6 fill out the first three. The architect's lean for v0.7 is a coordinated three-track release that:

- **Closes table-stakes gaps** (typed knowledge graph and consolidation pass are the most-cited gbrain features mem-fusion doesn't have; benchmark suite is the credibility gap with Mem0).
- **Extends the unique lead** by formalizing memory-as-work-queue (memory `25bb4ca4`) as a shipped feature — turning *"mem-fusion turns your machines into a coordinated team"* from observation into product story.
- **Makes the white-space visible** through OSS readiness + positioning content. The strongest architectural position is invisible without active framing.

The three-track combination is what the architect believes earns the "best memory storage and sharing system" framing the user requested. Any one track alone falls short:

| Track alone | Why it fails |
|---|---|
| Capability only | Feature parity that nobody hears about. |
| Positioning only | Caveats kill the story when product can't back it up. |
| Ecosystem only | Reach without substance — adoption stalls. |

That's the architect's read. PM and Marketing should push back on this framing before any of it crystallizes.

## Proposed workpackages (architect's current lean — debatable)

Nine WPs grouped into three tracks. Per the project-plan convention, one sentence of intent per WP — design detail goes in per-WP architecture docs once the WP is real work.

### Capability track (architect proposes as v0.7-core)

**WP-1 — Memory-as-work-queue formalization.** Promote the emergent coordination pattern (memory `25bb4ca4`) to first-class shipped feature: structured `action_item` and `bug_report` memory types with `assignee`, `status`, `blocks`, `resolves` fields and a state machine.

**WP-2 — Typed knowledge graph (auto-extracted relation edges).** Pattern-match where possible (zero-LLM cost), LLM-augment for ambiguous cases. Integrates with the existing wikilink convention.

**WP-3 — Consolidation pass (proposal-only, no auto-mutation).** Async periodic. Detects stale memories, dead wikilinks, redundant content. Surfaces findings as proposal memories the user reviews.

**WP-4 — Benchmark suite + public results.** Reproducible benchmarks against Mem0, gbrain, Letta on LongMemEval / MultiTurnQA / a novel multi-machine coordination benchmark.

### Positioning track (architect proposes as v0.7-core)

**WP-5 — OSS readiness + repository hygiene.** License (Apache-2.0 vs MIT — architect leans Apache for patent grant; PM/Marketing should weigh in), CONTRIBUTING.md, security policy, hardened install, comprehensive README, performance characterization.

**WP-6 — Public positioning content.** README rewrite around the four-property intersection + blog post framing group-keyed-by-explicit-intent as the answer to Mem0's "open problem" + conference talk submission.

### Ecosystem track (architect proposes as v0.7 stretch — splits to v0.8 if scope balloons)

**WP-7 — OpenClaw integration adapter.** Mem-fusion as memory layer for the OpenClaw runtime. Distribution channel per competitive analysis (OpenClaw is not a competitor; it's a host that needs a memory layer).

**WP-8 — Framework SDK adapters (LangChain, LlamaIndex, AutoGen).** Three highest-leverage frameworks. Thin per-framework shims over the existing MCP surface.

**WP-9 — Connector breadth: Notion + GitHub.** Two new connector types beyond Slack. GitHub specifically pairs with WP-1 for end-to-end issue-to-resolution flow.

## What architect proposes NOT doing in v0.7

Architect's current lean — open to PM/Marketing pushback:

- **Cloud SaaS offering.** Off-strategy per competitive analysis. Local-first is the position.
- **OS-style memory tiering (Letta's pattern).** Speculative value for our use case.
- **All 21 framework SDKs.** Top 3 cover the long tail; the other 18 are marketing copy.
- **Multi-user SaaS coordination.** v0.7 personal mesh + team-scoped connectors is the model.
- **Web UI / dashboard.** v0.9+ consideration if community demand emerges.

1. WP-2 graph schema design → engineer implements.

## Open architectural questions (genuine unknowns, not rhetoric)

1. **WP-2 typed-edge extraction quality.** Pattern-based is cheap but brittle; LLM-based is robust but expensive. Hybrid threshold needs design.
2. **WP-3 consolidation aggressiveness.** Too many proposals = spam; too few = invisible. Tunability surface is unclear.
3. **WP-4 benchmark methodology fairness.** Benchmarking competitors while building our own invites bias accusations. Independent review or external runner is worth considering. Marketing should weigh in on perception risk.
4. **WP-7 OpenClaw API stability.** ~19 days old at competitive-analysis time. Either we track and accept churn, or we wait for v0.2+. Verify before scoping.
5. **WP-9 GitHub connector model.** GitHub has issues, PRs, comments, labels — which subset becomes memory-shaped? Probably issues + PR descriptions, but the contract is open.

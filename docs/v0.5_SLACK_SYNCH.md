# v0.5.0 Slack Sync Driver

Design doc for the Slack sync driver in Constellation v0.5. Implementation tracked under WP-E (SlackDriver) and WP-F (Slack wire format) of the v0.5 work-package list.

---

## 1. Goal

Make a Slack channel a first-class peer transport — addressable as `slack:#<channel-name>` in a Constellation peer config — so peers that can't host inbound HTTP (corporate-locked Macs, NAT'd machines, mobile) can still participate in a group's memory sync.

Load-bearing constraints from prior architecture decisions:
- **Slack auth never enters the Constellation daemon.** Claude holds the Slack token via its own MCP layer; the daemon delegates `slack:` peers to Claude.
- **Privacy invariant survives unchanged.** Adding a `slack:#channel` peer to a group works exactly like adding an HTTP peer: explicit naming required for non-personal groups; bare `/remember push` still defaults to `personal` only.

---

## 2. Mental Model

**The channel IS the peer group AND manages the peers.** Memories are things we drop off in the channel and things we pick up from the channel. There is no concept of "node A pushes to node B" — there is only "this node deposits memories in the channel" and "this node retrieves memories from the channel."

- **No per-peer addressing on the wire.** When pushing, we aim at the channel. Every channel member becomes a potential recipient via their own pull.
- **No peer discovery.** Slack's channel-member list IS the directory. Adding a teammate to the channel = adding a peer. Removing them = removing them.
- **No symmetric configuration.** Every member configures the same one-line entry (`slack:#<channel>`).

**HTTP is point-to-point; Slack is publish-subscribe.** The driver interface (push/pull/status/since) stays identical, but its semantics change underneath.

What's NOT inherited from Slack: identity verification. A single Slack user may run multiple machines posting to the same channel. `user_id` is insufficient — `origin_node` in the payload is the routing key. See §3.3.

---

## 3. Wire Format

Each memory is **one top-level Slack message** carrying two payloads:
1. A **human-readable message body** (what humans scrolling the channel see).
2. A **JSON file attachment** carrying the full machine-readable record.

### 3.1 Message body

```
[mem-fusion 0.5] mc-macbookpro · decision · 2026-05-15T03:00:00Z
content_hash: sha256:abc1234...

Privacy invariant fix landed for /remember autopush — non-personal groups now require explicit naming.

(JSON attached: memory-abc1234.json)
```

Three load-bearing things in the body:
- **`[mem-fusion <version>] <origin_node> · <type> · <submitted_at>`** — the parseable header. Pull-side filter on the prefix.
- **`content_hash: sha256:...`** — visible AND parseable. Lets pull-side skip downloading the attachment when this content is already in local store.
- **First-line content snippet** (~100–200 chars) — humans can scan the channel without expanding the JSON.

### 3.2 JSON file attachment

Filename: `memory-<short-content-hash>.json` (8-char prefix for visual hint; full hash inside).

```json
{
  "envelope_version": 1,
  "content_hash": "sha256:abc1234...",
  "origin_node": "mc-macbookpro",
  "submitted_at": "2026-05-15T03:00:00Z",
  "content": "<full memory text>",
  "vector": [0.123, 0.456, ...],
  "type": "decision",
  "tags": ["v0.5", "wp-1", "privacy"],
  "project": "mem-fusion",
  "importance": 5,
  "groups": ["branch-ai-mem-fusion"]
}
```

Same fields as the v0.4 HTTP wire shape — no Slack-specific additions, no missing fields. `envelope_version: 1` reserves space for WP-I (propagating edits) to add fields without breaking older peers.

### 3.3 `origin_node` is the machine ID, not the Slack user

A single Slack user (e.g. Mitch) may have multiple machines posting to the same channel. Slack tells us "Mitch posted this"; we need to know *which* of Mitch's machines.

Two consequences:

1. **Loopback prevention.** When mc-macbookpro pulls from the channel and sees its own post: `if origin_node == self.node_name: skip`. Never re-ingest your own posts.
2. **Cross-machine recognition.** When mc-macbookair pulls and sees `origin_node = "mc-macbookpro"`, it knows: "my other machine, ingest."

Machine identity is in the payload; user identity is in the channel ACL. Two layers, two roles.

### 3.4 Size considerations

- Message body: ~500 chars, well under Slack's 40 KB text limit.
- JSON attachment: usually 8–16 KB (768-dim vector ~6 KB + content).
- Memories with content > 100 KB still fit comfortably as file attachments. (Slack supports up to 1 GB.)

## 4. Driver Interface

Four methods: `push`, `pull`, `status`, `since`.

### 4.1 `push(memory) -> {status, slack_ts, file_id}`

Format the body per §3.1, serialize the memory record per §3.2, call `files.upload(channels=[<channel_id>], filetype="json", filename="memory-<short>.json", content=<json>, initial_comment=<body>)`. Capture `ts` and `file_id`.

Per-memory result: `{"status": "stored", "slack_ts": "1778829123.884419", "file_id": "F08XXX"}` or `{"status": "error", "reason": "..."}`.

Note: Slack doesn't dedup on receipt, so push always lands a new channel message. Sender-side dedup (don't re-post recently pushed memories) is the caller's responsibility.

### 4.2 `pull(since=<timestamp>) -> [memory, ...]`

1. **Read channel** — `slack_read_channel(channel_id, oldest=<unix-ts>)`.
2. **Filter on marker** — keep messages whose body starts with `[mem-fusion <N>]`.
3. **Parse header** — extract `origin_node`, `content_hash`, `submitted_at`.
4. **Loopback check** — `if origin_node == self.node_name: skip`.
5. **Dedup check (cheap)** — `if content_hash in local_store: skip without downloading`.
6. **Fetch attachment** — for messages that survive 1–5, download the JSON via `files.info` → `url_private` (auth'd HTTPS).
7. **Yield** — emit memory records.

### 4.3 Dedup story

Two layers:
- **Header-level (cheap)** — `content_hash` in the message body lets the pull filter skip already-known memories without downloading the attachment.
- **Content-hash dedup (canonical)** — `core.find_existing_by_hash` handles the actual local-store dedup, same path the HTTP driver uses.

The header-level fast-path is purely an optimization; correctness comes from content-hash dedup at the local store layer.

### 4.4 `status() -> {ok, channel_id, channel_name, last_seen_ts, ...}`

Verify Claude has Slack auth, channel is accessible, return last message `ts` for informational purposes.

### 4.5 `since` cursor

`submitted_at` ISO-8601 from local store ↔ Slack `ts` unix-seconds. Double-filter (`Slack ts > X` AND `JSON submitted_at > X`) defends against clock skew between origin_node and Slack ingest.

## 5. Execution Context (Claude-side, not daemon)

Daemon's gateway adds a scheme-registry (WP-C). When the daemon processes `/pull` or `/push` and encounters a `slack:` peer URI, it doesn't try to contact it. Instead, the response includes a `delegated_to_caller` array listing slack peers and the operation context. Claude receives the daemon's response, sees the delegated work, and orchestrates the Slack calls itself using its `mcp__claude_ai_Slack__*` MCP tools.

This split has three properties:
- **Slack auth stays in Claude** — never enters the daemon.
- **No daemon dependency on Slack SDK** — keeps the daemon's footprint thin.
- **Claude renders results** — the daemon returns thin per-peer telemetry for HTTP peers; Claude appends its own telemetry for slack peers. Final user-facing prose is rendered by Claude from the combined whole.

## 6. End-to-End Example

User has this peer config:

```json
{
  "memberships": [
    {"group_name": "personal", "peers": ["http://192.168.4.170:7533"]},
    {"group_name": "branch-ai-mem-fusion", "peers": ["slack:#branch-ai-mem-fusion"]}
  ]
}
```

### Push flow

User: `/remember <decision text> for branch-ai-mem-fusion`

1. Claude calls `mem-fusion/store_memory(...)` → local id `abc-...`, `content_hash sha256:def567...`.
2. Claude calls daemon `/push {group: "branch-ai-mem-fusion", memory_ids: ["abc-..."]}`.
3. Daemon sees only `slack:` peer, returns `{peers: [], delegated_to_caller: [{driver: "slack", channel: "#branch-ai-mem-fusion", memory_ids: ["abc-..."]}]}`.
4. Claude exports payload via `mem-fusion/export_record("abc-...")`.
5. Claude formats body + JSON, calls `files.upload(channels=["C..."], filetype="json", filename="memory-def567xx.json", content=<json>, initial_comment="[mem-fusion 0.5] mc-macbookpro · decision · ...\\ncontent_hash: sha256:def567...\\n\\nPrivacy invariant fix...\\n\\n(JSON attached)")`.
6. Slack returns `ts=...`, `file_id=F08xxx`.
7. Claude renders: *"Posted to #branch-ai-mem-fusion."*

### Pull flow (mc-macbookair, after the above push)

User on mc-macbookair: `/remember pull branch-ai-mem-fusion`

1. Claude calls daemon `/pull {group: "branch-ai-mem-fusion"}`.
2. Daemon returns `{peers: [], delegated_to_caller: [{driver: "slack", channel: "#branch-ai-mem-fusion", since: "<local cursor>"}]}`.
3. Claude converts `since` to Slack `oldest`, calls `slack_read_channel(...)`.
4. For each message: marker check, header parse → `origin_node="mc-macbookpro"`, `content_hash=sha256:def567...`.
5. Loopback check: `origin_node != "mc-macbookair"` → proceed.
6. Dedup check: `content_hash` not in local store → proceed.
7. Download attached JSON via `files.info` → `url_private` (auth'd HTTPS fetch).
8. Parse, store via `mem-fusion/store_memory(..., groups=["branch-ai-mem-fusion"])`.
9. Render: *"Pulled from #branch-ai-mem-fusion: 1 new memory from mc-macbookpro."*

### Loopback case (mc-macbookpro pulls from same channel)

Same as pull flow above, except step 5:
- `origin_node == "mc-macbookpro"` (self) → skip without downloading.

mc-macbookpro never re-ingests its own posts.

## 7. Notification Design

Constellation's v0.4 HTTP driver provides no notification surface: a user has no idea when new memories arrive on a peer until they manually `/remember pull`. Slack opens new options because the channel is both a human-readable activity log AND a machine-pollable surface.

### 7.1 Option space and constraints

| Approach | Status |
|---|---|
| Slack Events API webhooks | Ruled out — needs inbound HTTP, exactly what Falcon blocks on corporate Macs |
| Slack RTM (WebSocket) | Outbound, but needs a long-running listener holding the Slack token |
| Background daemon polling | Breaks both "no background sync" rule AND "Slack auth never in daemon" rule |
| Session-start auto-pull | Reuses existing patterns; respects auth boundary |
| In-session opportunistic polling | Possible but adds complexity over session-start |

Four constraints prune the space:
- Slack auth lives in Claude, not the daemon.
- Corporate-Mac inbound HTTP is blocked.
- "User-initiated, no background" principle from MVP.
- Claude isn't always running (session-based, not a daemon).

### 7.2 Tier 1 + Tier 2 design

**Tier 1 — Slack native channel UI (zero infrastructure).**

Users get Slack desktop/mobile notifications for new messages in subscribed memory channels through Slack's standard notification stack. The `[mem-fusion 0.5]` prefix makes machine messages visually distinct from human chat. Users configure Slack channel-specific notification preferences (mute, only-mentions, etc.) per their taste.

This solves the "did anything new arrive?" question for free for any user already in Slack throughout their workday.

**Tier 2 — Session-start auto-pull for `slack:` peers.**

When Claude starts a new session and the active config has any `slack:` peer URIs, Claude automatically runs `group_pull(group)` for each affected group as part of session priming. New memories land in the local store before the user types their first prompt. The SessionStart context block surfaces a one-line summary: *"Pulled from #branch-ai-mem-fusion since last session: 3 new memories from mc-macbookair, 1 from alice-mac."*

What changes:
- A behavior rule in the `/remember` skill (or CLAUDE.md): "at session start, if `slack:` peers exist in any group's config, run `group_pull` for that group."
- The existing SessionStart bash hook (`session_prime.sh`) can't hold Claude's Slack auth — so this is a Claude-side behavior rule, not a hook change.
- No daemon changes beyond the WP-C scheme-registry.
- No new long-running processes.

Tier 2 aggressiveness policy: pull every group with slack peers, every session start. Latency bounded by Slack response time (~1–2 sec per channel), parallelized across groups for total session-start latency under 2 seconds in steady state.

### 7.3 Deferred to later versions

- **Tier 3 — In-session opportunistic polling.** While the user is in an active Claude session, periodically check Slack for new memories. Useful when teammates are pushing concurrently. Could live in `UserPromptSubmit` hook.
- **Slack RTM listener.** Real-time push delivery. Needs a long-running component holding the Slack token. Genuinely complex for marginal value over Tier 1 + Tier 2.

## 8. Slack Limits

### 8.1 Rate limits (Slack Web API tiers)

| Method | Tier | Practical limit |
|---|---|---|
| `files.upload` | Tier 2 (~20/min) | ~20 push operations per minute |
| `conversations.history` | Tier 3 (~50/min) | ~50 pull operations per minute |
| `conversations.info` | Tier 3 (~50/min) | Status checks plentiful |
| `files.info` | Tier 4 (~100/min) | Attachment metadata fetches |

Implications:
- Bulk push of 80 memories hits Tier 2 cap of ~20/min → ~4 minutes serialized at a 3-second-per-message self-imposed rate limit. Acceptable for occasional bulk catch-up.
- Bulk pull catch-up bounded by `conversations.history` (one call returns up to 1000 messages) plus N `files.info` for unique new attachments — well within Tier 4's 100/min.
- Steady state (a few memories per session): far below all limits.

### 8.2 Size limits

- **Message text:** 40 KB. Our message body is ~500 chars — 80× headroom.
- **File upload:** 1 GB per file (workspace plan dependent). Our typical memory JSON is 8–16 KB — 60,000× headroom.
- **Channel history retention:** Slack workspace policy dependent; unlimited on paid plans, 90 days on free tier.

### 8.3 Channel limits

- **Members per channel:** 1,000 (private) / 50,000 (public). Memory groups will be far smaller.
- **Files per channel:** unlimited but counted against workspace storage quota (typically 5 GB free / 10 GB+ paid). At 16 KB/memory, 10 GB = ~625,000 memories — years of headroom.

### 8.4 Notification limits

Slack throttles notifications during burst activity. A bulk push of 80 memories generates 80 channel messages → typically collapsed into "N new messages" summaries. Same throttling on mobile push.

**Mitigation for bulk push notification flooding:** Optionally post bulk memories as threaded replies under a single summary message rather than top-level. Generates one notification per batch. Tradeoff: complicates the `since` cursor (threaded messages have different `ts`-ordering). Deferred to v0.6.

## 9. Human-Performance Considerations

The Slack channel is dual-purpose: peer transport AND human-readable activity log. Both directions need consideration.

### 9.1 Channel noise

Heavy memory traffic can drown out human conversation. Recommendation: **dedicated memory-channel per group.** Don't mix mem-fusion channels with general team-chat channels. The conceptual pattern is "a Slack channel is the group's memory log" — not "let's also dump memories in #general."

### 9.2 Visual differentiation

Mitigations baked into the wire format:
- `[mem-fusion 0.5]` prefix is the visual marker, always at the start of the first line.
- Header line uses `·` separators — distinctive in normal prose.
- First-line content snippet gives skim-friendly summary.

Optional: emoji prefix (`📝 [mem-fusion 0.5] mc-macbookpro · decision · ...`) for enhanced scannability. Decorative; pull-side filter still matches on the `[mem-fusion ...]` prefix.

### 9.3 Notification fatigue

Every memory generates a Slack notification by default. Mitigations:
- Encourage users to set high-traffic memory channels to **"only mentions"** notification level. Channel still shows in sidebar with unread indicators but doesn't push for every memory.
- For `personal` group channels (cross-machine sync of one user), this is especially safe — the user is both poster and recipient.

Don't auto-mute the channel for the user — that defeats Tier 1's whole purpose. Let the user choose.

### 9.4 Search & discovery (a notable win)

Slack indexes every message body, so a user searching for *"privacy invariant"* in their Slack client finds the original memory's message — and can click through to see the original push context. This is a usability win over the HTTP driver, where stored memories are searchable only via Claude's `search_memory`.

### 9.5 Accidental human triggering

A human typing `[mem-fusion 0.5] ...` literally would not trigger ingest. Defense in depth: pull-side filter requires BOTH the prefix AND a parseable header (origin_node, content_hash, submitted_at well-formed) AND a JSON file attached. Any human message that hits the prefix fails the structural validation and is skipped.

## 10. Machine-Performance Considerations

### 10.1 Session-start latency (Tier 2)

Cost: auto-pulling N groups at session start adds latency before the user can interact.

Numbers:
- One `slack:` group, no new memories since last session: ~500 ms.
- One `slack:` group, 5 new memories: ~500 ms + 5×(~200 ms attachment fetch) = ~1.5 sec.
- Three `slack:` groups, ~5 new each: ~4.5 sec serialized.

Recommendation: **parallelize pulls across groups.** With parallelization, session-start Tier 2 latency stays under 2 seconds in steady state.

### 10.2 Bulk catch-up after long offline

Cost: a user offline for a week may have 100+ new memories. Pull = one `conversations.history` + 100 attachment fetches = 20 sec serialized.

Recommendation: **concurrency-limited parallel fetches.** Cap at 10 concurrent attachment downloads → ~2-3 seconds total. Surface progress to the user during long catch-up: *"Pulling 100 new memories from #branch-ai-mem-fusion (12 of 100…)."*

### 10.3 Push throughput

Cost: `files.upload` Tier 2 limit ~20/min. Bulk push of N>20 incurs rate-limit delays.

Recommendation: **self-rate-limit at 3 seconds per push** to stay safely under 20/min. For N=80 bulk push: 80×3 = 4 minutes. User sees progress.

### 10.4 Concurrent multi-peer pulls

If a user has 3 groups with `slack:` peers and 2 with `http:` peers, session-start runs 5 pulls concurrently. Run all in parallel; cap total concurrency at 10 outbound connections. Slack and HTTP don't share rate-limit budgets.

### 10.5 Token expiry mid-session

Claude's Slack OAuth refreshes periodically. If a token expires mid-pull, the operation returns 401. Catch 401 in the driver, surface a re-auth prompt, don't auto-retry — re-auth is interactive.

### 10.6 Attachment storage bloat (long-tail)

Each pushed memory is a Slack file. Over months, a channel accumulates files in workspace storage. 16 KB/memory × 1000 memories/year = 16 MB — negligible against typical 5–10 GB quotas. Revisit with a "compact older messages" pattern only if channel passes 10k memories.

### 10.7 Out-of-order delivery

A peer with a slow clock could post a memory with `submitted_at` slightly older than a peer that already pushed. The double-filter (Slack `ts > X` AND JSON `submitted_at > X`) handles it; local content-hash dedup catches any duplication.

## 11. Risks

- **Slack workspace retention** silently deleting memories. Source-of-truth remains each peer's local Qdrant — Slack is transport, not archive.
- **Channel rename / archive** breaks `slack:#name` resolution. Status check fails; user updates config.
- **Token expiry** — re-auth via Claude's normal Slack flow.
- **Out-of-order processing** — double filter handles it.
- **Channel access lost mid-session** — surface clearly to the user.
- **File attachment deletion** — Slack admin or retention can delete attached files without deleting the message body. Pull tries to fetch, gets 404. Recovery: log + skip; the message body's `content_hash` makes the gap identifiable.

## 12. Validation Plan

End-to-end test on real Slack:

1. Create test channel `#mf-driver-test`. Add Claude's user.
2. Configure two peers with `slack:#mf-driver-test` in a test group.
3. `/remember <test memory> for mf-driver-test` from one peer.
4. Verify message + attachment lands in the channel with correct wire format.
5. From another peer: `/remember pull mf-driver-test`. Verify ingest, dedup, loopback prevention.
6. Test failure modes: archive channel temporarily (status check fails); remove a user (pull 403s).
7. Test Tier 2: start a fresh Claude session, verify auto-pull runs and surfaces summary in priming.
8. Test corporate-Mac use case: a Falcon-blocked-inbound machine as `slack:`-only peer, verify outbound push/pull works.

## 13. Out of Scope

- **Install / config UX.** Adding `slack:` peer to config = Claude writes a line in `peers[]` per WP-C.
- **Channel hygiene / locking.** Deferred per v0.5 architecture decision.
- **Scheme→executor registry on daemon side.** WP-C; this design assumes it exists.
- **WP-I (propagating edits).** The `envelope_version: 1` field is the seam where WP-I will add fields.
- **Tier 3 in-session polling.** §7.3.
- **Slack RTM / WebSocket subscription.** §7.3.
- **Threaded bulk-push notification mitigation.** §8.4.

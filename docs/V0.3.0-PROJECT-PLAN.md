# Mem-Fusion v0.3.0 — Project Plan (revised)

**Date:** 2026-05-11
**Supersedes:** `docs/V0.3.0-PROJECT-PLAN.md` (2026-05-10)
**Versioning:** v0.3.0 is the next release after v0.1.0. Single version stream — Constellation ships alongside Mem-Fusion as a separately-installed extension. v0.2.0 was skipped intentionally.

---

## What changed in this revision

Six concrete corrections vs the 2026-05-10 plan, in order of impact:

1. **Auth + security hardening is OUT of v0.3.0.** The 2026-05-10 plan baked Bearer-token swarm-key auth, 401/403 distinction, and a localhost/network filter into WP3. Per 2026-05-11 scope decision (commit `b10bed4`): **all auth deferred to v0.4** so we can validate full prototype functionality first. The `swarm_key` config field is now accepted but unused.
2. **WP3 closes at 3a + 3b shipped.** What was one ~3-4 hr work package became two sub-phases, both delivered. WP3a (`/memory/put` + `/memory/get` by id) shipped at commit `646a99b`; WP3b (`/peers` + `/peers/self`) shipped at commit `fce48ba`. **WP3 is complete.**
3. **Refactor before feature: semantic search moves to WP4c.** The old plan implicitly bundled semantic search (`/memory/get?query=...` via Ollama embed + Qdrant vector search) into WP3. It is being **pushed downstream to WP4c** so the install refactor lands first. Adding tool surface on top of a structurally-broken INSTALL.md compounds the maintenance debt; refactoring first means the new feature lands into a clean home.
4. **WP4 (Operational integration) is repurposed and expanded.** The old WP4 was "launchd plist + register MCP" as a single ~2 hr task. The new WP4 absorbs the full **INSTALL.md restructure** identified in the 2026-05-11 project-structure analysis: extract embedded code from INSTALL.md into standalone files, rename `mcp_server.py` → `mem-fusion.py`, build `scripts/install.sh`, create Constellation's own install surface (`src/INSTALL.md` + install script + launchd plist). WP4 is now ~2 working days, not 2 hours, and splits into **WP4a (Mem-Fusion install refactor)**, **WP4b (Constellation install surface)**, **WP4c (semantic search — completes the Constellation tool surface)**.
5. **`dev/` is explicitly out of scope for v0.3.0 formalization.** Stays as the testing area it is today. Any cleanup, ownership re-decomposition, or directory split is deferred to a later pass after v0.3.0 ships.
6. **Several stale path references corrected.** Old plan referenced `~/.local/share/cowork-memory/mcp_server.py` (wrong path — that's the legacy cowork-memory install location). Dev peers actually live at `~/.local/share/mem-fusion-dev/`, `~/.local/share/mem-fusion-peer-b/`, `~/.local/share/mem-fusion-peer-c/`. The "move ARCHITECTURE.md from drafts to extensions/" step is also stale — that move already happened (`docs/CONSTELLATION_ARCHITECTURE.md` is committed).

## WP3 — Constellation tools (split into 3a / 3b / 3c)

**Scope change vs 2026-05-10:** Auth middleware (Bearer swarm-key, 401 wrong-token, 403 non-member) is **dropped from WP3 entirely and deferred to v0.4**. The integrity guarantee for v0.3.0 is `content_hash` only. Vector preservation is verified byte-identically in tests.

### WP3a — `/memory/put` + `/memory/get` by id ✅ SHIPPED

Status: committed at `646a99b` ("WP3 Phase 3a: memory promotion end-to-end verified").

Delivered:
- `POST /memory/put`: validates `memory_record` shape, recomputes `content_hash`, rejects mismatch with HTTP 400, validates vector dimension (768), dedups by `content_hash + group_name`, inserts canonical with full provenance payload (`origin_node`, `origin_local_id`, `submitted_at`, `received_at`, `received_by`, `submission_kind`).
- `GET /memory/get?group_name=X&id=Y`: returns the canonical record with verbatim vector.
- `GET /memory/get?group_name=X`: scrolls recent records in the group (limit 10).
- Verification script `dev/test-wp3a-promotion.py` — 14 invariants pass including byte-identical content + vector across the federation hop, dedup (re-PUT returns `status: "duplicate"`), and tampered-content_hash rejection (returns 400).

### WP3b — `/peers` + `/peers/self` ✅ SHIPPED

Status: committed at `fce48ba` ("WP3 Phase 3b: directory endpoints (/peers and /peers/self)").

Delivered:
- `GET /peers?group_name=X`: aggregates `origin_node` across canonicals to produce a recency-ordered member list with `submission_count`, `first_seen`, `last_seen`. Peers are inferred from submission activity (no separate registration step) — adequate for the trust-as-membership model.
- `GET /peers/self`: returns this node's identity (`node_name`, `listen_address`, `version`, `memberships[]`).
- `scroll_all()` generator helper isolates cursor pagination so handlers iterate with explicit termination conditions.
- Verification script `dev/test-wp3b-directory.py` — 19 invariants including aggregation across multiple peers, sort ordering, count increments, missing-group → 400, unknown-group → 403.

### WP3c — Semantic search in `/memory/get` 🚧 NOT STARTED

**Goal:** Complete `/memory/get` by accepting a `query` parameter that runs semantic vector search against the canonical collection.

**Scope:**
- Add `query` query-string parameter to `GET /memory/get`.
- When `query` is present: embed via Ollama (`nomic-embed-text`, 768-dim) → `qdrant.search()` with the embedded vector → return top-K with similarity scores.
- Optional filters that combine with `query`: `type`, `since` (relative `24h`/`7d` or ISO), `tags`, `min_importance` — mirrors Mem-Fusion's local `search_memory` filter surface for consistency.
- `top_k` parameter, default 8.
- New constants needed: `EMBED_MODEL`, `OLLAMA_URL` (or read from config — the daemon currently doesn't talk to Ollama, this is the first time).
- Update the existing scroll branch (`/memory/get?group_name=X` with no id, no query) to also accept `since`, `type`, `tags`, `min_importance` filters for symmetry.

**Deliverables:**
- Daemon code: ~80 lines (embed call, search branch, filter builder).
- New dev test: `dev/test-wp3c-semantic-search.py` — verifies (1) `query` returns ranked results, (2) scores are between 0 and 1 with the right ordering, (3) `query + type` filter narrows correctly, (4) tampered embedding round-trip still finds the memory (vectors are verbatim, search still works).

**Success criteria:**
- Promote three semantically-related memories from peer-b → orchestrator
- `GET /memory/get?group_name=X&query="constellation orchestrator role"` returns those memories ranked by similarity
- Score > 0.75 for the most-relevant; score ordering matches subjective relevance
- Filter combinations work (`query + since=24h`, etc.)

**Stop point:** Constellation's tool surface is complete. All four MCP tools are HTTP-verifiable end-to-end. Ready to start the install refactor (WP4) in parallel with thinking about WP5.

### WP4b — Constellation install surface

**Goal:** Constellation has its **own** install path, fully separate from Mem-Fusion's. Mem-Fusion's install ends by pointing users to Constellation's install as the optional next step.

**Scope:**
- `src/INSTALL.md` — separate document with prereq check (verifies Mem-Fusion is installed), explains what gets installed, points at `scripts/install.sh`.
- `src/scripts/install.sh` — orchestrator. Verifies Mem-Fusion presence (bail with clear error if absent). Initializes canonical Qdrant collection. Writes `~/.local/share/mem-fusion/constellation/config.json` from `config.example.json` template + user-provided group info. Loads launchd plist. Registers HTTP MCP with Claude (`claude mcp add constellation http://127.0.0.1:7533`). Runs health check.
- `src/config.example.json` — config template with `node_name`, `listen_address`, `qdrant_url`, `canonical_collection`, `memberships[]` (with `swarm_key` field as an accepted-but-unused placeholder reserved for v0.4).
- `src/launchd/com.branchapp.memfusion.constellation.plist` — persistent service definition.
- `src/scripts/uninstall.sh` — reverse the install (unregister MCP, unload plist, drop canonical collection optionally).
- Handoff: append a section to `mem-fusion/INSTALL.md` (shrunken in WP4a) saying "Next: install Constellation (optional, for group memory) — see `src/INSTALL.md`."

**Success criteria:**
- After `mem-fusion/scripts/install.sh`: Mem-Fusion works; user is told how to install Constellation.
- `src/scripts/install.sh` (run from a fresh state): Constellation runs as a launchd service, `claude mcp list` shows both `mem-fusion` and `constellation`, daemon survives reboot.
- Running Constellation install without Mem-Fusion installed produces a clear precondition error and exits non-zero.

**Stop point:** v0.3.0 is operationally deployable end-to-end. A new user could `git clone` and end up with personal memory (Mem-Fusion) and group memory (Constellation) working in Claude Code.

## Out of scope for v0.3.0 (explicit deferrals)

These were either in the 2026-05-10 plan or have come up in design discussions, and are explicitly NOT shipping in v0.3.0:

| Item | Deferred to | Why |
|---|---|---|
| Bearer-token swarm-key auth on Constellation endpoints | v0.4 | Localhost-only deployment doesn't earn its keep; revisit when cross-machine federation is real |
| Non-loopback bind warning + bind_address validation | v0.4 | Same reason — localhost-only |
| Per-peer cryptographic identity (mTLS, Ed25519) | v0.4 | Group-shared swarm key was already group-level trust; per-peer needs a real design phase |
| Human review queue / apprenticeship loop / curator pattern | v0.4 | Auto-promote default proves the protocol; review layer is significant new scope |
| Multi-group membership per node | v0.4 | Schema already supports it; runtime code enforces single membership for v0.3.0 simplicity |
| Hierarchical orchestrators (orchestrator-as-member-of-parent-group) | v0.4+ | Architecturally supported; routing code not written |
| Cross-group memory propagation | v0.4+ | Routing rules forbid it in v0.3.0 |
| Native OS notifications (macOS Notification Center) | v0.4+ | Claude-native channels (SessionStart, MCP tools) sufficient for v0.3.0 |
| Per-memory "stay local" privacy flag | v0.4 | Auto-promote is the v0.3.0 default; flag adds protocol surface |
| `dev/` directory cleanup and ownership split | post-v0.3.0 | Testing area; formalize after we have lived experience |
| claude-mod / Monet / Debussy rebrand | v1.0 | Naming holds through v0.4; rebrand at the v1.0 release moment |
| `vector_hash` integrity check on payloads | post-v0.4 | Content_hash + TCP checksums sufficient for v0.3.0 localhost; revisit for cross-machine non-Python clients |

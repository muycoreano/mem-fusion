# Email Connector — Parked Draft (2026-05-19)

**Status:** PARKED. v0.6 stays on Slack per architect call 2026-05-19. This draft preserves the email-substrate exploration in case we revisit later. Not authoritative; not on any roadmap.

## Why this was considered

During v0.6 personal-sync design (architect, 2026-05-19), the conversation surfaced that Slack's 40 KB body cap forced a compact wire-format work package (gzip+base64 batching) to fit reasonable backlog catch-up. Email was raised as a substrate that sidesteps that constraint entirely.

## Substrate properties relative to Slack

| Property | Slack | Email |
|---|---|---|
| Message size cap | 40 KB | 25 MB (Gmail) — 600× headroom |
| Attachments as first-class | No (MCP has no `files.upload`) | Yes — `.tar.gz` is native |
| Vendor lock-in | Slack-only | Protocol; any IMAP/SMTP provider |
| Latency (active) | ~1–5 s websocket | ~1–30 s IMAP IDLE |
| Setup cost | Slack app or user token | SMTP+IMAP creds or OAuth |
| Retention | Free-tier limits matter | Provider-dependent (Gmail unlimited by default) |
| Offline-first semantics | Polling | Native — IMAP designed for "sync after laptop comes back" |
| Existing mem-fusion code | `SlackConnector` exists | greenfield |

## Sketch design

```
EMAIL-AS-SUBSTRATE
  Outbound: SMTP to <user>+mfsync@<domain>   (Gmail + addressing for label routing)
  Inbound:  IMAP IDLE on the +mfsync label

  Subject: [mf-sync v0.6 from=mc-air batch=12 ts=2026-05-19T20:30Z]
  Body:    one-line summary (count, types) — humans can scan if they ever look
  Attach:  memories.jsonl.gz  (one envelope per line, gzipped)

  Connector config:
    { "id": "personal-sync",
      "type": "email",
      "smtp": { ... },     // or OAuth creds
      "imap": { ... },
      "label": "mfsync",
      "format": "jsonl-attachment" }
```

Receive flow: `EmailConnector.parse_envelope(raw_mime)` extracts attachment, gunzips, splits lines, returns list of envelopes. Same `ingest_connector_message` per-envelope flow downstream.

## Why parked

- Existing scaffolding cost: `SlackConnector`, `format_envelope`, `parse_envelope`, MCP integration all already written for Slack. Email is greenfield.
- ACK semantics: Slack returns `message_ts` synchronously; SMTP returns "queued" with no inherent receipt confirmation.
- Spam-filter risk for automated binary-attachment self-mail on Gmail (manageable with filter rules, but real).
- Daily-send quotas on personal Gmail accounts (500/day) — plenty for personal sync but a real ceiling.

## Conditions that would unpark this

- If the compact-wire-format design under Slack proves brittle in practice (parse ambiguity, fence-collision edge cases, Slack normalization changes).
- If memory volume exceeds Slack's daily rate-limit budget per app.
- If a use case emerges that needs >40 KB per atomic message (e.g., shipping binary blobs, large code attachments, image memories).
- If retention becomes a real concern on a free-tier Slack workspace.

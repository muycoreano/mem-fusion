# v0.5 — `content_hash` Canonicalization Spec

**Status:** PROPOSED · awaiting architect review
**Author:** Claude-Engineer (mc-macbookair) · 2026-05-17
**Targets:** mem-fusion v0.5+
**Audience:** mc-macbookpro (architect) for review

---

## 1. Why this spec exists

`content_hash` is mem-fusion's load-bearing dedup key. It appears in:

- `core.py`: `find_existing_by_hash`, `store_memory`'s pre-write check, `upsert_memory`, `find_or_create`, and as a payload index in the Qdrant collection schema.
- `constellation.py`: `/memory/put` integrity check, `_merge_pulled` dedup-or-merge decision, push-time wire payload.
- The v0.5 SlackConnector wire format (per `docs/v0.5_CONNECTOR_ARCHITECTURE.md` §5.1): receiver MUST verify `sha256(envelope.content)` matches the header's content_hash for integrity, and uses it for cross-peer dedup on pull.

Today, `core.content_hash()` works correctly for any single peer's pairwise operations. But the algorithm is **never formally specified** — its behavior is whatever Python's `hashlib.sha256` + a particular text-normalization recipe produces. The moment two peers diverge in their normalization (different Python version, different locale, different mem-fusion version, different connector implementation in another language), dedup silently breaks: the same logical content yields different hashes → entries are stored twice → search returns duplicates → group sync loops accumulate noise.

This spec locks the algorithm explicitly so future drift is impossible and so non-Python implementations of mem-fusion or its connectors can produce byte-identical hashes.

## 2. Current implementation (as of 2026-05-17)

```python
# core.py:127
def content_hash(text: str) -> str:
    """The dedup + integrity hash. Must be byte-identical across all daemons."""
    return hashlib.sha256(text.strip().lower().encode()).hexdigest()[:16]
```

Properties of this implementation:

| Property | Choice | Comment |
|---|---|---|
| Algorithm | SHA-256 | Solid; not the question |
| Encoding | `.encode()` → UTF-8 | Python default; not portable to other languages without specifying |
| Whitespace | `.strip()` only (leading/trailing) | Internal whitespace preserved |
| Case | `.lower()` | English-centric; locale edge-cases with Turkish dotless-i, German eszett |
| Unicode normalization | None | NFC/NFKC/NFD/NFKD: undefined |
| Output | hex digest, first 16 chars (64 bits) | Truncation point arbitrary |

## 3. Issues with the current implementation

### 3.1. Unicode-naive
"café" (composed, U+00E9) and "café" (decomposed, e + U+0301) hash differently. Most editors and tools produce one form or the other; users won't notice; dedup quietly fails for content that round-trips through different normalization layers.

### 3.2. Locale-edge-case case folding
`str.lower()` in Python is Unicode-aware-by-codepoint but doesn't fold all visually-equivalent characters identically across edge cases. `"İ".lower()` produces `"i̇"` (i + combining dot above) which is two characters, surprising callers. `str.casefold()` is more aggressive (e.g. `"ß".casefold() == "ss"`) and probably more correct, but isn't used today. Locale doesn't actually affect CPython's `str.lower()`, contrary to what the docstring implies — but the lack of clarity is the bug.

### 3.3. Aggressive case-stripping conflates content
`"Decision: pick Postgres"` and `"DECISION: PICK POSTGRES"` are intentionally distinct memories in many human-curation patterns (a corrective memory that's just SHOUTING for emphasis vs. the original calm decision). The current implementation merges them. Whether this is desired or accidental is undocumented.

### 3.4. Whitespace stripping is incomplete
Leading/trailing only; internal whitespace differences distinguish memories. So `"a b"` and `"a  b"` are different hashes; `"a b"` and `"\n a b \n"` are the same. The boundary is arbitrary.

### 3.5. Truncation to 64 bits
Birthday-paradox collision at ~4 billion entries (≈√2⁶⁴). Cross-peer fleet at 200/day × 10 peers × 365 days × 100 years ≈ 73M entries — comfortably below collision threshold. Single-user yearly: ~7K. Operationally fine forever at expected scale, but worth noting the explicit choice and the boundary.

### 3.6. No spec for non-Python implementations
The v0.5 SlackConnector wire format mandates a round-trip `sha256(envelope.content)` integrity check. A future TypeScript / Go / Rust implementation of the connector reading from the same Slack channel must produce byte-identical hashes. Today there is no document to point them at.

## 4. Proposed canonical algorithm

```
content_hash(text: str) -> str:
  1. Apply Unicode NFC normalization to `text`.
  2. Encode the result as UTF-8 with no BOM.
  3. Compute SHA-256 of the byte stream.
  4. Hex-encode the digest (lowercase hex).
  5. Return the full 64-character hex digest.
```

### 4.1. Rationale per step

- **NFC, not NFKC.** NFC preserves visual identity (composed forms); NFKC additionally folds compatibility-equivalent characters (full-width digits → ASCII digits, ligatures → constituent letters) which can lose semantic information in technical content like CJK or mathematical notation. NFC is the W3C-recommended interchange normalization and what most editors emit by default.
- **No case folding.** Memories are user-curated; capitalization is semantic. If a future use-case wants case-insensitive dedup, it's a different operation (`case_insensitive_hash`) — not the canonical content_hash.
- **No whitespace stripping.** All whitespace preserved byte-exact. A trailing newline is intentional content; a missing trailing newline is intentional content. If callers want to dedup-modulo-whitespace, they normalize their own input *before* calling content_hash.
- **UTF-8 without BOM.** RFC 3629; no BOM because it's non-content metadata that some emitters omit.
- **Full 64-char digest.** No truncation. 256-bit collision resistance well past any plausible mem-fusion fleet size. Storage cost is 32 bytes per memory in payload — tiny compared to vector + content.

### 4.2. Reference implementation (Python)

```python
import hashlib, unicodedata

def content_hash(text: str) -> str:
    """Canonical content hash per docs/v0.5_CONTENT_HASH_SPEC.md."""
    normalized = unicodedata.normalize("NFC", text)
    return hashlib.sha256(normalized.encode("utf-8")).hexdigest()
```

## 5. Consumers & API contract

`content_hash(text)` is called by:

| Consumer | Purpose | Sensitivity to spec change |
|---|---|---|
| `store_memory` | Pre-write dedup lookup | High — different hash → duplicate entries |
| `upsert_memory` | Stamp on new content | High |
| `find_or_create` | Dedup gate | High |
| `find_existing_by_hash` | Read by hash | High |
| Constellation `/memory/put` | Integrity check (sender included hash; receiver recomputes) | High — cross-peer wire |
| Constellation `_merge_pulled` | Dedup-or-merge decision | High |
| SlackConnector receive (per v0.5 architecture doc §5.1) | Envelope integrity + dedup | High |
| Future cross-language connectors | Cross-impl dedup | Highest — failure mode is silent duplicate accumulation |

The contract is: **two implementations of `content_hash` agree byte-for-byte on identical input** for all text the system might store. Any implementation that diverges is non-conformant.

## 6. Migration

### 6.1. Existing memories

Every entry in Qdrant currently has a `content_hash` payload field computed via the legacy algorithm. After the new algorithm lands, those hashes are wrong for the new spec.

**Migration approach:** one-shot batch rewrite. For each memory in the local store, recompute `content_hash(content)` using the new algorithm and update the payload. Idempotent (running twice produces the same hash). Ship as fix script `0.5.0-NNN-migrate-content-hash-canonical.sh`.

Estimated impact at current scale: ~130 memories × ~1ms per recompute + Qdrant set_payload ≈ ~0.5 sec total. Trivial.

### 6.2. Wire format compat

During the migration window, peers running new + old code interop incorrectly: new peer recomputes incoming hash and rejects with integrity-mismatch; old peer ignores normalization differences. Mitigation: bump a `wire_version` field in the v0.5 envelope; old peers ignore unknown fields. New peers refuse to dedup against old-hash entries (legacy entries get re-hashed during the migration sweep before the new code becomes the receiver).

### 6.3. Truncation removal

Legacy hashes are 16 chars; new hashes are 64. The Qdrant `content_hash` payload index supports variable-length keyword strings, so no index migration is needed. Storage cost increases by 48 bytes per memory — negligible.

## 7. Open questions for architect

1. **NFC vs NFKC** — the proposal leans NFC for semantic preservation. NFKC would be more aggressive (collapses more "visually equivalent" characters into one hash). Which fits mem-fusion's storage-of-record story?
2. **Case folding** — the proposal drops it entirely. If existing tooling relied on case-insensitive dedup (does it? I haven't found evidence), this is a behavior change worth flagging.
3. **Whitespace** — the proposal preserves all whitespace byte-exact. If the original `.strip()` was load-bearing for any user-curation pattern (e.g., a hook that pastes content with trailing newlines we don't want as distinct memories), we should know.
4. **Truncation removal** — going from 16 hex → 64 hex bumps payload size by 48 bytes/entry. Worth it for collision safety; should it be 32 hex (128 bits, well past collision threshold) as a middle ground?
5. **Migration trigger** — auto-run at install or as an explicit opt-in fix script? Recommend explicit fix script; users on lock-step v0.5 deployment run it themselves.

---

## 8. Out of scope

- **Hashes of vectors.** Embedding values aren't hashed for dedup; same content → same embedding (modulo Ollama version drift, which is a separate concern).
- **Hashes of full payloads** (metadata + content). Different memories can share identical content; the metadata fields (project, tags, importance, groups) are separate dedup axes if needed in future.
- **Encrypted content.** If mem-fusion ever encrypts at rest, the hash is over the plaintext (so dedup still works regardless of key/IV); spec'd separately.

## §A — Content-hash spec answers (CONTENT_HASH_SPEC §7)

### A.1 — NFC vs NFKC

**Decision: NFC.**

Reasoning: NFC preserves semantic identity for visually distinct but meaningfully different content. NFKC would collapse full-width digits (`１２３` → `123`), CJK compatibility ideographs, mathematical alphanumerics, and ligatures (`ﬁ` → `fi`) into ASCII equivalents — destroying meaning in technical content mem-fusion routinely stores. NFC matches W3C interchange recommendation and what most editors emit by default. Engineer's lean accepted.

### A.2 — Case folding

**Decision: No case folding.**

Reasoning: Engineer's argument is correct — capitalization is semantic. A corrective memory shouting "DECISION: PICK POSTGRES" is meaningfully distinct from the original calm "Decision: pick Postgres" in human-curation patterns. The current `.lower()` behavior conflates them unintentionally. If case-insensitive dedup is ever needed downstream, that's a separate function (`case_insensitive_hash`) with its own contract.

### A.3 — Whitespace

**Decision: Preserve all whitespace byte-exact.**

Reasoning: Trailing newlines are intentional content. Internal whitespace differences distinguish memories meaningfully. The current `.strip()` is inconsistent (only leading/trailing) and creates surprising edge cases. If callers want whitespace-tolerant dedup, they normalize their input *before* calling `content_hash`. The hash function does one thing.

### A.4 — Truncation length

**Decision: Full 64 hex chars. No truncation.**

Reasoning: 48-byte payload growth per memory is negligible at any plausible scale. Cross-language connector implementations (Go, TypeScript, Rust, etc.) get byte-identical output without needing to know our truncation point. Removes a footgun for future implementers. The middle-ground (32 hex / 128-bit) saves 16 bytes per memory at the cost of one more "why this specific length" question downstream — not worth it.

### A.5 — Migration trigger

**Decision: Explicit fix script. No install-time auto-run.**

Reasoning: Lock-step deployment is the v0.5 norm for peers in the mesh; explicit `bash src/scripts/fixes/0.5.0-015-fix-content-hash-canonical.sh` matches the existing pattern (idempotent, reversible, peer-by-peer rollout). Auto-run at install creates the wrong incentive — silent payload migrations on upgrade are hard to audit. Engineer's lean accepted.

## §B — First-pull semantics answers (FIRST_PULL_SEMANTICS §6)

### B.1 — First-pull cap / opt-out

**Decision: No cap by default. ADD the knob.**

`first_pull_max_age_days: int | None` on the connector entry, default `None` (full back-fill). Users with very large channels can opt into a measured back-fill via the per-connector knob. Adds ~5 LOC of config handling for real user flexibility on edge-case channels (e.g., a 5-year-old channel with 50K memory-tagged messages).

### B.2 — Bot-user invite preflight

**Decision: Yes, preflight check with a clear "invite required" message.**

Engineer's recommendation accepted. Slack's `channel_not_found` is opaque and unhelpful when the actual cause is "the connector's bot user hasn't been invited to the channel." The preflight is one extra `conversations.info` call (~30ms) and converts a confusing failure into a clear remediation hint.

### B.3 — Slack-posted progress

**Decision: No. v0.5 logs to local file only.**

Engineer's recommendation accepted. Posting progress to Slack from inside the connector creates a backchannel that obscures the actual memory flow and produces noise readers must filter. Local log file is sufficient for the user who wants to `tail -f`. Revisit only if a real user asks.

### B.4 — Parallel vs sequential multi-connector first-pull

**Decision: Sequential.**

Engineer's recommendation accepted. Slack's rate-limit budget is per-app, so parallel pulls share the budget anyway — no actual time savings, but parallel makes error handling and rate-limit back-off significantly more complex. Sequential is simpler, deterministic, and the wall-clock cost of 2–3 sequential first-pulls is small enough not to matter at v0.5 scale.

### B.5 — Generalize to non-Slack connectors

**Decision: Yes — make §3 connector-implementation-defined with Slack as the reference.**

Engineer's recommendation accepted. The general contract becomes: *"each connector type defines its own first-pull semantics; the implementation must be idempotent under content_hash dedup; pagination and rate-limit handling are connector-specific."* Slack is the v0.5 reference. Formalize the generalized contract during v0.6 when a second connector type begins design — until then, do not over-spec.

## §C — Chunked embedding decision (separate item from gap report)

**Engineer's proposal:** memory `bcb8d737` (also `47b20eb1`) — chunked embedding with `canonical_id` + post-search dedup at search time, as the correct long-term answer for memories exceeding EMBED_MAX_CHARS. The current `0.5.0-007` soft-truncation is harm-reduction only.

**Decision: Land in v0.6, NOT v0.5.x.**

Reasoning:

1. **v0.5 is mid-flight.** Adding chunked embedding now slows the Slack connector ship. Push orchestration (`0.5.0-016`) + content_hash canonicalization (`0.5.0-015`) are higher leverage and on critical path for v0.5 completion.
2. **v0.6 is the natural home.** v0.6 ships the Node Identity Context work (`docs/v0.6_NODE_IDENTITY_CONTEXT.md`) which also adds payload fields (`about_me`). Bundling the chunked-embedding payload changes (`canonical_id`, `chunk_index`, `chunk_count`) into the same schema bump amortizes one substrate change instead of two.
3. **Truncation is operationally acceptable in the interim.** v0.5 memories that exceed 8000 chars get truncated with full content preserved in the stored payload — degraded recall on the tail, not data loss. Worth flagging in any user-facing comm.

**Migration path when v0.6 lands:** a future fix script re-embeds existing memories from their stored full-content payload using the new chunked-embedding logic. No data loss. No manual intervention.

Engineer can park this on the v0.6 backlog. No new work expected until v0.5 ships clean.

# v0.4 — Memory Architecture

**Status:** IMPLEMENTED. Drafted 2026-05-13; landed on `main` 2026-05-13.

**Supersedes** the v0.3 design described in [`MEM_FUSION_ARCHITECTURE.md`](MEM_FUSION_ARCHITECTURE.md) and [`CONSTELLATION_ARCHITECTURE.md`](CONSTELLATION_ARCHITECTURE.md). Those documents are kept as historical record of the v0.3 design path; the routing model, payload shape, and protocol described here are the live design.

**Branch / tag context:** v0.3 line is cut at tag `v0.3.1` with maintenance branch `v0.3.x`. v0.4 work shipped on `main`.

**Verification:** all v0.4 work packages landed and 164/164 test invariants pass across the seven self-contained test suites under `tests/`. See `tests/README.md` for the matrix.

---

## 1. Why v0.4

v0.3 shipped a working group-memory system but left a real privacy gap: the dual-routing logic in `/remember` was a Band-Aid over a deeper architectural problem. The problem:

> v0.3 assumed Mem-Fusion could *classify* what's safe to share with teammates by looking at the content (rule vs. knowledge). But classification is inherently fuzzy, and any mis-classification on the wrong side becomes a privacy leak — a personal preference auto-pushed to your teammates' machines.

v0.4 replaces *content classification* with *explicit user intent*. Every memory has a `groups` tag that the user sets (explicitly or by default). The group is the routing key for sharing. There is no fuzzy heuristic — if a memory isn't tagged for a group with peers, it doesn't leave the local machine.

This also dissolves the v0.3 separation between "local" and "federation" entries. There is one kind of entry now, distinguished only by which group(s) it belongs to.

**v0.4 is a strict simplification of v0.3.** No new storage layers, no new daemons, no new transports. The vector DB becomes the sole source of truth for memory content, group membership, and routing. The v0.3 dual-routing skill goes away, the `source` field goes away, and the proposed file-mirror layer that was floated mid-design has been dropped — Qdrant snapshots handle durability natively; a parallel markdown mirror would only add coordination cost.

---

## 2. The new model in one sentence

**Every memory has a group tag. Sharing happens by group. Default group is `personal`. Same protocol, same storage, same dedup — only the peer list differs per group.**

## 3. Object model

### Memory entry

A Qdrant point with:

| Field | Purpose |
|---|---|
| `content` | The memory text, verbatim |
| `vector` | 768-dim embedding (nomic-embed-text) |
| `content_hash` | Dedup + integrity key |
| `groups` | **Routing key for sharing.** A list of group names. Default `["personal"]`. A memory can belong to multiple groups simultaneously — `["personal", "engineering@branch"]` means "share with my own machines AND with engineering teammates." Set explicitly per-memory by the user. |
| `type` | Decorative filter (`decision` / `preference` / `fact` / `error` / `code` / `context` / `session`). Does NOT gate sharing. |
| `timestamp` | When this entry was stored locally |
| `origin_node` | Which peer originated this memory (= self for locally-originated) |
| `submitted_at` | When the memory was promoted to its group (= timestamp for locally-originated; preserved across pulls) |
| `importance` | 1–5, as today |
| `project`, `tags`, `session_id` | As today |

Notable absence: the `source` field (`local` / `group`) goes away. The `groups` field replaces its routing role; `origin_node` covers the provenance role.

### Group

A named scope identifying who can see a memory. Examples: `personal`, `engineering@branch`, `LegalRO`.

- A memory can belong to **one or more groups** simultaneously. Multi-group membership is intentional: a decision relevant to both `engineering@branch` and `platform-team@branch` shouldn't have to be written twice.
- A peer can belong to **multiple** groups (multi-membership — relaxes the v0.3 single-membership limit).
- The default group set is `["personal"]`. New installs of Mem-Fusion + Constellation get a `personal` membership pre-configured with empty peers.
- `personal` is not exclusive — a memory can be in `["personal", "engineering@branch"]`, meaning it lives on your own machines (personal peers) AND with your engineering teammates.

### "Personal" group — the implicit default

`personal` is a real group, not a sentinel for "local". Its peers list:

- **Empty** = single-machine personal memory. Memories tagged `personal` never leave this machine.
- **Populated** = your-own-machines. Memories tagged `personal` propagate across machines you own.

This is the load-bearing simplification of v0.4: there's no separate "local-only" code path. A truly-local memory is just one with `groups: ["personal"]` whose `personal` group has an empty peer list.

## 4. /remember skill — the new shape

```
/remember <content>                              → store with groups=[personal]
/remember <content> for <group>                  → store with groups=[<group>]
/remember <content> for <group1>, <group2>, …    → store with groups=[<group1>, <group2>, …]
/remember push                                   → bulk push: for every group with peers,
                                                     push memories tagged with that group
/remember push <group>                           → push only that group's memories
/remember pull                                   → bulk pull: for every group with peers,
                                                     pull from that group's peers; merge locally
/remember pull <group>                           → pull only that group's peers
```

Plus a natural-language path Claude handles via reasoning, not an explicit slash command:

```
You: "share those memories with <group>"          → Claude resolves "those" from session
                                                     context, calls add_groups + targeted push
You: "also share them with <group>"               → Claude adds the new group and pushes ONLY
                                                     to that group (not re-pushing prior groups)
You: "make sure all your groups have these"       → Claude iterates every group the memories
                                                     belong to, pushes each individually
```

The v0.3 classify-and-route logic is gone. Routing is now entirely explicit via the `for <group>[, <group>, …]` clause at store time, or via the share-after-the-fact pattern through natural language. Default = `["personal"]` (local).

### Examples — store-time tagging

```
You:   /remember always use uv for Python environments
Claude: ✓ Stored with groups=[personal]. Stays on this machine.

You:   /remember We picked Postgres 16 for the auth service, for engineering@branch
Claude: ✓ Stored with groups=[engineering@branch].
        ✓ Pushed to engineering@branch peers:
            - bob-mac:       stored
            - alice-desktop: stored

You:   /remember API gateway uses bearer tokens for service-to-service auth,
       for engineering@branch, platform-team@branch
Claude: ✓ Stored with groups=[engineering@branch, platform-team@branch].
        ✓ Pushed to engineering@branch: bob-mac stored, alice-desktop stored.
        ✓ Pushed to platform-team@branch: dave-mac stored.
        (Receivers in both groups get the memory once each.)
```

### Examples — share-after-the-fact (the store-now-share-later workflow)

This is the natural workflow: insights emerge during work, you reflect, you decide who would benefit.

```
You:   "Ok, let's pause and reflect on what we learned today and store the memories."
Claude: ✓ Stored 4 memories with groups=[personal]:
        - decision: gRPC for internal RPC (id: a7e3)
        - decision: Postgres 16 with logical replication (id: b8f4)
        - error:    JWT clock-skew fix (id: c9a5)
        - context:  Auth service migration timeline (id: d0b6)

You:   "Ok, let's share those memories with engineering."
Claude: ✓ Added engineering@branch to 4 memories.
          (now tagged groups=[personal, engineering@branch])
        ✓ Pushed to engineering@branch peers:
            - bob-mac:       4 stored
            - alice-desktop: 4 stored

You:   "Oh, I also want to share those with product."
Claude: ✓ Added product@branch to the same 4 memories.
          (now tagged groups=[personal, engineering@branch, product@branch])
        ✓ Pushed to product@branch peers ONLY:
            - dave-mac:      4 stored
            - eve-laptop:    4 stored
        (Engineering peers are NOT re-contacted — they already have these
         from the previous step.)
```

The third step is the load-bearing one: **only product's peers receive the new push.** The fact that the memories are also tagged for engineering is irrelevant to this push call — engineering's peers already have the memories from the previous turn. Re-contacting them would be wasteful.

### A few notes on scope

- `for <group>[, <group>, …]` is the explicit-group syntax at store time. The user opts in to sharing. There is no auto-sharing.
- Once a memory is stored, the user can extend its group set at any time via natural-language requests like *"share those with X"*. This uses `add_groups` (additive only — see §6) to widen the memory's group set, then a targeted push.
- **Push scope is determined by what the user named, not by every group the memory belongs to.** *"Share with product"* pushes to product peers only. To push to multiple groups in one user action, name them all: *"share with engineering and product."* Claude composes the calls.
- A push fan-out de-duplicates peer endpoints across groups — if `bob-mac` is in both `engineering@branch` and `platform-team@branch`, he receives a memory once even if it's pushed to both groups in one user request.
- `/remember push` (no args) is the explicit bulk catch-up command: iterates every configured group with peers and pushes everything that group can accept. Used for *"sync everything we have."*
- `type=preference` continues to exist as a filter (search/recall semantics) but doesn't gate sharing. A `type=preference` memory tagged for engineering shares with engineering teammates; the user opted into that explicitly.

## 5. Storage model — Qdrant only

The vector DB is the **sole** source of truth for memory content, group membership, and routing. Every memory is one Qdrant point with the payload described in §3. There is no parallel file-based mirror, no dual-write coordination, no two-source-of-truth question to answer.

### Why no file mirror

The v0.3 → v0.4 design exploration considered a markdown-mirror layer for resilience (a backup readable when Qdrant is corrupted or Mem-Fusion is uninstalled). It was dropped for clarity:

- **Qdrant is already a durable database.** Persists to disk at `~/.local/share/mem-fusion/qdrant-data/`. Supports snapshots, export, import. Survives reboots. It already solves the durability problem the mirror was being introduced to solve.
- **A parallel mirror introduces coordination cost without coordination benefit.** Every write would have to succeed in two places. Updates (group merges, renames) would need to keep both in sync. Failure-handling forks (Qdrant-yes-file-no, file-yes-Qdrant-no) would need explicit semantics. None of that complexity earns its keep when Qdrant is already a real database.
- **Recurring confusion was the signal.** During the v0.4 design conversation, the file layer kept getting re-imagined every time it came up — first as per-group subdirectories, then as a flat-slug tree with a MEMORY.md index, then as flat-slug with informational frontmatter. The fact that the same construct kept shifting shape was evidence the construct itself wasn't load-bearing; it was being shoehorned into a system that didn't need it.

### Durability is handled by Qdrant snapshots

If the user wants a backup of their memory data, they take a Qdrant snapshot (or copy the `qdrant-data/` directory). Standard database operational practice. Not a Mem-Fusion concern beyond optionally surfacing a `mem-fusion export` convenience command later if real users ask for it.

### Uninstall

If Mem-Fusion is uninstalled, the user's Qdrant data directory remains on disk by default (deletion is optional, prompted, opt-in — see the uninstall section of `INSTALL_MEM_FUSION.md`). The user can preserve it by copying the directory before uninstall, or by taking a Qdrant snapshot. A future re-install can point at the existing data directory and pick up where they left off.

### Write path

`core.store_memory(...)` is a single entry point that:

1. Computes `content_hash`. Queries Qdrant for an entry with the same `content_hash`.
2. **If a match exists** with a different `groups` list: union the incoming groups into the existing entry's `groups`, update the Qdrant payload (no re-embedding), return `{status: "merged", id, groups}`.
3. **If a match exists with identical groups**: return `{status: "duplicate", id, groups}` (no-op).
4. **If no match**: embed via Ollama, generate UUID, write Qdrant payload with `groups: [...]`, return `{status: "stored", id, groups}`.

Failures are simple: if Ollama is unreachable, return `{error: "ollama_unreachable"}`. If Qdrant is unreachable, return `{error: "qdrant_unreachable"}`. No silent queueing, no partial-success states, no parallel-store divergence to reason about.

## 6. Sharing model — group-keyed

### Adding groups to an existing memory: `add_groups`

A new MCP tool on Mem-Fusion lets Claude widen the group set of memories already stored:

```
mem-fusion/add_groups(memory_ids: list[str], groups: list[str])
   → { updated: [...], no_op: [...], errors: [...] }
```

For each `memory_id`:
- Retrieve the current entry from Qdrant.
- Compute the union of existing `groups` with incoming `groups`.
- If the union equals the existing list: `no_op`.
- Otherwise: `set_payload` with the union; return the updated entry in `updated`.

**Additive only.** `add_groups` can extend a memory's reach; it cannot remove a group. Removal is deliberately deferred (see §11) because un-sharing is non-trivial in distributed settings — peers that already received the memory still have it.

This is the operation that enables the "store now, share later" workflow. The user's natural-language *"share those with engineering"* maps to: Claude resolves *those* from session context, calls `add_groups(ids, ["engineering@branch"])`, then targeted push (below).

### Push

`group_push` on the Constellation gateway:

```
constellation/group_push(group: str, memory_ids?: list[str])
```

Semantics:
1. Daemon reads its config — finds the named group in `memberships[]` (`group_push` is always scoped to a single group; multi-group push is multiple calls from Claude).
2. **If `memory_ids` is provided**: scrolls local Qdrant for entries matching those IDs *and* where `group ∈ groups`. Memories whose `groups` list doesn't include the target group are skipped silently.
3. **If `memory_ids` is omitted**: scrolls all local entries where `group ∈ groups` (the bulk catch-up case, used by `/remember push <group>`).
4. For each matching memory, computes the **push-time group filter** (see below) to determine which groups to include on the wire for each recipient peer.
5. For each (peer, memory) pair, calls `POST /memory/put` with the full record and the filtered `groups` list.
6. Returns per-peer-per-memory telemetry.

**Scope discipline:** `group_push` targets *one* group at a time. To push to multiple groups in one user action, Claude makes multiple `group_push` calls — one per group. The system never silently fans out to groups the user didn't name. *"Share with product"* → product peers only, even if the memory is also tagged for engineering.

### Push-time group filter

The wire-shape `groups` field sent to a recipient is filtered to groups the recipient is a member of from the sender's perspective:

```
groups_sent_to_peer_P = memory.groups ∩ { g | P ∈ sender.memberships[g].peers }
```

Why: each user's `personal` group is *their* personal group. Sending Alice's `personal` tag to Bob would be semantically wrong — Bob is not in Alice's personal group; that tag has no meaning to him. The filter ensures recipients only learn about groups they're actually members of (from the sender's view).

### Pull

`group_pull` on the Constellation gateway:

```
constellation/group_pull(group?: str)
```

Semantics:
1. For the named group (or every group with peers if no arg), iterate peers.
2. Call `GET /memory/since?group=<group>&cursor=<max submitted_at in this group's local entries>` on each peer.
3. Each returned entry carries its `groups` list verbatim. Apply the **dedup-merge rule** below: union local + incoming groups; insert if new.
4. Returns per-peer telemetry.

### Dedup-merge rule (additive)

When a memory arrives (via push receive or pull) and we already have its `content_hash`:

| Local groups | Incoming groups | Result |
|---|---|---|
| `[A]` | `[A]` | No change — already have it |
| `[A]` | `[A, B]` | Merge → `[A, B]` |
| `[A, B]` | `[A]` | No change — local groups are a superset |
| `[A]` | `[B]` | Merge → `[A, B]` |
| `[A, B]` | `[C]` | Merge → `[A, B, C]` |

**Always additive, never subtractive.** Receiving a memory never removes it from a group; it only adds groups. The same rule applies to `add_groups` (sender-side widening) and to dedup-merge (receiver-side widening). Subtraction is deferred to post-v0.4 (see §11).

The merge rule prevents echo-bugs (Alice pushes to Bob with `groups: [eng]`; Bob pushes back to Alice via a different path with `groups: [eng]` — Alice already has it with `groups: [eng, personal]`, no change).

### What's NOT in this protocol

- **No cross-group propagation by routing.** A memory in `engineering@branch` doesn't *automatically* enter `personal` because peers overlap. The memory's `groups` field is the only thing that determines routing.
- **No re-grouping at receive time.** Receiver stores the entry with the originator's filtered `groups` list; merges additively if a local copy already exists.
- **No content classification.** Routing is by tag, not by inspection.
- **No subtractive merge.** Receiving a memory with a smaller `groups` list never shrinks the local entry's `groups`.
- **No implicit multi-group push.** `group_push` targets exactly the group named by its argument. Pushing to multiple groups requires multiple calls.

## 7. Constellation alignment

### Multi-membership

v0.3 restricted `memberships` to length 1. v0.4 lifts that. Config:

```json
{
  "node_name": "alice-mac",
  "peer_listen_address":    "0.0.0.0:7533",
  "gateway_listen_address": "127.0.0.1:7534",
  "qdrant_url":             "http://127.0.0.1:6333",
  "state_dir":              "~/.local/share/mem-fusion/constellation",
  "memberships": [
    {
      "group_name": "personal",
      "peers": [
        { "node_name": "alice-desktop", "endpoint": "http://10.0.0.4:7533" }
      ]
    },
    {
      "group_name": "engineering@branch",
      "peers": [
        { "node_name": "bob-mac",      "endpoint": "http://10.0.0.5:7533" },
        { "node_name": "carol-laptop", "endpoint": "http://10.0.0.7:7533" }
      ]
    }
  ]
}
```

The `personal` membership is pre-populated by the installer with `peers: []`. Cross-machine personal sync is opt-in: the user adds their other machines to the personal group's peer list when they're ready.

### Out-of-the-box personal-group experience

After installing Constellation on each of your machines and adding each other to the personal group's peers list, your memories sync automatically across your devices. Same protocol as teammate-group sharing, just a different peer list.

## 8. Backward compatibility with v0.3 data

Existing v0.3 vector DB entries lack a `groups` payload field (some were `source=local` without any group; others were `source=group` with a singular `group_name`).

**Read-time fallback rule:** any entry without a `groups` field is treated as `groups: ["personal"]`. v0.3 entries with `source=group` and `group_name=X` are read as `groups: [X]`. No mandatory data migration — the read-time fallback gives every legacy entry a usable shape.

`v0.3 → v0.4 install` script proposed (optional, opt-in):
- Iterate all entries lacking `groups` payload.
- For entries with `source=group` and `group_name=X`, write `groups: [X]`.
- For entries without `source=group`, write `groups: ["personal"]`.
- Drop the deprecated `source` and `group_name` fields after migration.
- Idempotent; can be re-run.

## 9. What stays the same from v0.3

The structural pieces below don't change; v0.4 is a re-routing inside the same skeleton:

- **Two-listener Constellation daemon** (peer surface + gateway surface) — same code shape, same ports.
- **`core.py` shared library** — same module surface, `store_memory` gets a `groups` arg (list of strings, default `["personal"]`) but otherwise unchanged.
- **`mem_fusion.py` MCP server** — 11 tools today; `group_pull` / `group_push` adapt to multi-group routing, signatures unchanged.
- **Test harness** (`tests/lib/harness.py`) — same lifecycle helpers.
- **Self-contained test discipline** — every test still spins up its own Qdrant + daemons; nothing depends on externally-running infrastructure.
- **The four hooks** — `SessionStart`, `UserPromptSubmit`, `Stop`, `PostToolUse:Write`. The Stop hook's extraction logic stays; what changes is that every hook-captured entry gets `groups: ["personal"]` by default. Routing-by-type goes away.

## 11. Open questions still TBD

- **Push idempotency.** Today's push sends the same memory every time it's pushed. v0.4 could track per-(peer, group, memory) push state to skip already-delivered entries. Or accept the redundancy (the receiver dedup-merges). MVP: accept the redundancy.
- **Group-rename ergonomics.** What happens if a user wants to rename `engineering@branch` to `eng@branch`? Probably: rename in config + bulk-update Qdrant payload (every entry whose `groups` contains `engineering@branch` gets it replaced with `eng@branch`). Out of scope for v0.4; document as a future operational task.
- **Removing a memory from a group.** Subtraction is non-trivial in distributed settings — peers in the removed group already have the memory; removing it from your local `groups` list doesn't un-share it. Out of scope for v0.4 — surface a `remove_groups` primitive when real usage demands it. (The additive case — *adding* groups after store time — is in-scope; see §6 `add_groups`.)
- **Hook-extracted memory types.** Today's Stop hook extracts `preference`, `decision`, `error`. Under v0.4, all of these store with `groups: ["personal"]` by default — including preferences (which previously were the privacy-leak risk). Group tag handles the safety. Worth re-examining whether the hook's pattern extractors are still well-calibrated; might be over-eager for v0.4's clearer semantics.
- **Cross-machine personal scope.** When a user adds another of their machines to the `personal` group's peer list, do auto-extracted hook memories (session summaries, etc.) propagate? Probably yes — that's the value of personal-as-real-group. Worth confirming with real usage whether this is desired or noisy.

## 12. What this dissolves vs. what it preserves

**Dissolves:**
- The dual-routing skill logic (classify rule vs. knowledge)
- The `source=local` vs `source=group` distinction
- The "/CLAUDE.md is hand-edited but vector DB is automatic" two-mode user mental model
- The single-membership constraint on Constellation
- The need for hook-extracted preferences to route differently from hook-extracted decisions
- The mid-design idea of a parallel markdown-mirror layer for resilience (Qdrant snapshots cover durability natively; a mirror would have added coordination cost without commensurate benefit)

**Preserves:**
- All test infrastructure
- The protocol surfaces (peer + gateway HTTP, MCP tools)
- The dedup-by-content-hash invariant
- Verbatim vector preservation across the wire
- Self-contained test discipline
- The two-process model (Mem-Fusion stdio MCP + Constellation HTTP backend)
- **Qdrant as the single source of truth for memory content, group membership, and routing** — v0.3 already had this implicitly; v0.4 makes it the explicit design center

**Adds:**
- Multi-group membership per peer (a peer can be in any number of groups)
- **Multi-group membership per memory** (a memory can belong to any number of groups simultaneously)
- Group-keyed sharing as the routing primitive
- The `personal` group's special role as the unified default
- Additive dedup-merge on receive (a memory's groups list grows on cross-arrival, never shrinks)
- **Retroactive add-to-group** via `add_groups` — the store-now-share-later workflow ("share those memories with engineering")
- **Targeted push via `memory_ids`** — surgical pushes for share-after-the-fact flows; pushes only what the user named, not the full group bucket
- **Push-time group filter** — recipients only see the groups they're members of (from sender's view); other groups (notably the sender's `personal`) are stripped on the wire

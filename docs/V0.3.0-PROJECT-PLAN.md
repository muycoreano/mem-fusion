**Total estimated effort:** ~13-15 hours of focused work, spread across however many sessions makes sense.

## WP1 — Mem-Fusion `export_record`

**Goal:** Add one new tool to Mem-Fusion that returns the full Qdrant record (including vector) for a stored memory by ID. This is the only Mem-Fusion-core change in v0.3.0.

**Scope:**
- Add `export_record(id)` to `~/.local/share/cowork-memory/mcp_server.py` (and the canonical version at `~/dev/mem-fusion/INSTALL.md`)
- Tool returns: `{id, vector, content, content_hash, type, tags, importance, timestamp}`
- Implementation: thin wrapper around `qdrant.retrieve(with_vectors=True, with_payload=True)`
- Update `list_tools()` to register the new tool

**Deliverables:**
- Updated `mcp_server.py` (in INSTALL.md source-of-truth)
- Updated tool count in CLAUDE.md snippet (8 → 9)
- Existing `test_mcp_tools.py` patched to cover `export_record`

**Success criteria:**
- `export_record(id="<valid>")` returns the full record with vector
- `export_record(id="<invalid>")` returns `{error: "Memory not found"}`
- All other Mem-Fusion tools work unchanged

**Stop point:** Mem-Fusion has the new tool. No Constellation work has started yet. Repo state is "Mem-Fusion v0.2.0-shape ready" but not tagged.

## WP2 — Constellation daemon scaffold

**Goal:** A standalone, persistent daemon with an HTTP MCP server skeleton. Doesn't yet implement the tools, but is reachable, healthy, and reads its configuration.

**Scope:**
- Create `~/dev/mem-fusion/extensions/constellation/` directory structure:
  - `constellation.py` — entry point; loads config; starts HTTP MCP server
  - `config.json.tmpl` — template for per-deployment config (name, role, group, swarm key, listen address)
  - `__init__.py` (if Python package) — module init
- HTTP server using stdlib `http.server` (or `aiohttp` if cleaner — decide at impl time)
- Endpoints:
  - `GET /health` — returns `{ok: true, daemon: "constellation", version: "0.3.0-alpha"}`
  - `POST /mcp` or `/sse` for actual MCP transport (start simple, can evolve)
- Logs to `~/.local/share/mem-fusion/constellation/logs/daemon.log`
- Own Qdrant collection: `mem_fusion_canonical_memories` (initialized on first start)

**Deliverables:**
- `extensions/constellation/constellation.py` (~200 lines)
- Config template
- Collection initializer (similar to Mem-Fusion's `init_collection.py`)
- Log infrastructure

**Success criteria:**
- Daemon starts via `python constellation.py --config config.json` without errors
- `curl http://127.0.0.1:7433/health` returns 200
- Daemon writes to its log
- Qdrant has the canonical collection created with correct schema

**Stop point:** Daemon runs in foreground, you can curl it, it's empty but alive. No tools yet.

## WP3 — Constellation 4-tool implementation

**Goal:** All four Constellation MCP tools work end-to-end against the daemon. Auth, dedup, content_hash verification, and Qdrant insertion all implemented.

**Scope (in dependency order):**

1. **`constellation/peers/self`** — return this node's info from config
2. **`constellation/peers`** — return list of group members (from config + registry)
3. **`constellation/memory/put`**:
   - Validate caller's swarm key (Bearer token)
   - Validate caller is in group's member list
   - Recompute content_hash, verify against caller's claim → reject mismatch
   - Validate vector dimensions (768)
   - Dedup by `content_hash + group_name` in canonical collection
   - Insert PointStruct with full payload (per the ARCHITECTURE.md replication schema)
   - Return `{status: "stored"|"duplicate", canonical_id, received_at}`
4. **`constellation/memory/get`**:
   - Validate auth + membership
   - Accept filters: `id`, `since`, `tags`, `type`, `query` (semantic search)
   - For semantic query: embed via local Ollama, search canonical collection
   - For non-query: scroll with filters
   - Return matching records with full payload

**Middleware (applies to all tools):**
- Bearer token check (swarm key)
- Localhost-vs-network filter (in v0.3.0, identical tool surface for both, but the filter scaffold is there for v0.4)
- Request logging to daemon log

**Deliverables:**
- All 4 tools implemented in `constellation.py` (or split into `tools.py`)
- Auth middleware
- Content_hash function as a protocol constant (identical to Mem-Fusion's)

**Success criteria:**
- `curl` calls to each tool return expected responses
- Content_hash mismatch rejected with 400
- Wrong swarm key rejected with 401
- Non-member access rejected with 403
- Duplicate put returns `{status: "duplicate"}` with original ID
- Semantic search returns ranked results matching query

**Stop point:** All 4 tools demonstrated working via direct HTTP. No Claude integration yet; tools are callable but not yet wired into the user's Claude flow.

## WP4 — Operational integration (launchd + MCP registration)

**Goal:** A user can install Mem-Fusion + Constellation, and Claude Code sees both as registered MCP servers.

**Scope:**
- `launchagents/com.branchapp.memfusion.constellation.plist.tmpl` — launchd plist that runs `constellation.py` as a persistent service
- `~/dev/mem-fusion/dev/` tooling: a `setup-constellation.sh` script analogous to `setup-peer.sh`:
  - Generates swarm key (32 random bytes)
  - Writes config.json
  - Initializes Qdrant collection
  - Installs launchd plist
  - Registers MCP with Claude: `claude mcp add constellation http://127.0.0.1:7433`
- Daemon dependencies: requires Qdrant + Ollama already running (Mem-Fusion's existing services)

**Deliverables:**
- Working launchd plist
- Install script
- Updated INSTALL.md with Constellation install steps (additive to Mem-Fusion's install)

**Success criteria:**
- `launchctl list | grep memfusion.constellation` shows running
- `claude mcp list` shows `constellation: ... ✓ Connected`
- Daemon survives a reboot (launchd brings it back)
- Daemon restart after config change works

**Stop point:** v0.3.0 is operationally deployable. A fresh-install user could follow the steps and have a running Constellation daemon. Claude sees it. They just haven't done anything with it yet.

## WP5 — Claude bridge (the dual-call pattern)

**Goal:** When a user tells Claude to remember something, Claude automatically performs the dual call (store_memory + export_record + memory/put) so the memory ends up in both local and group canonical.

**Scope:**
- Write the CLAUDE.md snippet for the dual-call pattern (verbatim content preservation, group routing, error handling)
- Document the auto-promote default + the privacy escape hatch (if any in v0.3.0)
- Update `config/claude-md-snippet.md` in the repo
- Document scope: v0.3.0 auto-promotes manual `store_memory` calls; session/file-write captures stay local (per earlier scope decision)

**Deliverables:**
- Updated CLAUDE.md snippet in the repo
- Updated INSTALL.md step that prints this snippet for the user to paste

**Success criteria:**
- A test user in a Claude Code session says "remember that we chose Qdrant for v0.3.0"
- Claude calls `mem-fusion/store_memory(...)` → gets local ID
- Claude calls `mem-fusion/export_record(id=...)` → gets full record
- Claude calls `constellation/memory/put(group_name=..., memory_record=...)` → gets canonical ID
- All three calls succeed; user is told both copies exist

**Stop point:** End-user flow works in a single Claude session. Memories propagate. Not yet tested across multiple peers.

## WP6 — End-to-end multi-peer verification

**Goal:** Demonstrate the full federation working — three peers, one orchestrator, memories flow correctly, search returns expected results, vectors are preserved.

**Scope:**
- Use the dev peer tooling (existing `~/dev/mem-fusion/dev/`) to spin up 3 peers
- One peer (`mem-fusion-dev`) = orchestrator for group `engineering@branch-test`
- Two peers (`mem-fusion-peer-b`, `mem-fusion-peer-c`) = members
- Test scenarios:
  1. **Basic propagation**: Alice (peer-b) stores memory → appears in canonical
  2. **Cross-peer query**: Bob (peer-c) searches canonical → finds Alice's memory
  3. **Content_hash dedup**: Same content from two peers → second is rejected as duplicate
  4. **Vector preservation**: Memory stored on peer-b has same vector in canonical (byte-identical)
  5. **Auth failure**: Wrong swarm key → 401
  6. **Membership failure**: Non-member tries to put → 403
  7. **Search quality**: Semantic search in canonical returns reasonable rankings

**Deliverables:**
- Test script(s) that run the scenarios
- Documentation of results (what passed, what surprised)

**Success criteria:**
- All 7 test scenarios pass
- No silent failures (every error path has a clear error response)
- Vector preservation verified bit-exactly (canonical's vector == peer's vector after promotion)

**Stop point:** v0.3.0 federation is provably working. Major surprises (if any) get documented and either fixed or scoped out.

## Things to revisit between sessions

A few questions worth surfacing for confirmation as we go:

1. **WP1's `export_record` location:** does the implementation patch live in the prod-installed `~/.local/share/cowork-memory/mcp_server.py` (touches running system) or only in the GitHub repo source (no immediate effect on this session's Claude)? My lean: only repo source; prod-install update is a separate "deploy" step the user can run when ready.

2. **WP3 transport details:** stdlib `http.server` (zero deps, simpler) vs. `aiohttp` (async-native, cleaner code, one dependency). I lean stdlib for v0.3.0; can refactor later.

3. **WP3 MCP-over-HTTP specifics:** does py-mcp 1.6.0 actually support HTTP/SSE transport directly, or do we need to implement a minimal MCP protocol handler on top of `http.server`? Will verify during WP2 spike.

4. **WP6 test infrastructure:** do we add a `dev/tests/` directory with reusable scenarios, or just run ad-hoc Python snippets? Lean: a reusable test script (`test-federation.sh` and `test-federation.py`) so we can re-run after changes.

5. **WP7 README rewrite scope:** lighter (just version bump + bullets) or deeper (mode story rewritten with v0.3.0-real examples)? Lean: deeper, since v0.3.0 is the real shippable moment for group memory.

These don't block anything; we resolve them as we hit each WP.

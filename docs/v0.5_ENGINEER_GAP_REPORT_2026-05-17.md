## Critical gaps (block or visibly tarnish v0.5)

### G1. Wire `content_hash` and local `core.content_hash()` diverge silently

**What it is.** The Slack wire format (architecture doc §5.1, validated by both your smoke test and mine) uses `"sha256:" + hashlib.sha256(content.encode("utf-8")).hexdigest()` — raw 64-char hex of UTF-8 bytes. The local dedup function `core.content_hash(text)` does `hashlib.sha256(text.strip().lower().encode()).hexdigest()[:16]` — strip + lower + truncate to 16 chars. **They are different values for the same content.**

**Why it bites.** A memory ingested from Slack would have `content_hash` set to whatever the receiver chooses to recompute (presumably wire-style for integrity, then local-style for dedup). The two values disagree on every memory. Result: when the local pre-write check (`find_existing_by_hash`) runs against a freshly-pulled memory, it computes the local hash, doesn't match anything in the store keyed by the wire hash, treats it as new, and inserts. Roundtrip from peer A through Slack to peer B works once, but cross-pull cycles can duplicate.

**Recommendation.** Land `docs/v0.5_CONTENT_HASH_SPEC.md` as actually-implemented: unify on the spec's `sha256(NFC(text))` hex-digest form. The fix is small (`core.py` line 127 + a payload migration sweep) and unblocks the cross-peer integrity contract. **Highest priority gap; everything else builds on this.**

### G2. SKILL.md `/remember push|pull <connector-id>` orchestration is incomplete

**What it is.** The SKILL.md clean-up pass (this commit) updated the command-surface table and dispatch description, but does not yet contain the **step-by-step procedure** Claude follows on `/remember push engineering`:

- Resolve the connector via `connector.json`
- For each memory whose `connector_ids` contains the id, format a wire-format envelope per §5.1
- Post via `slack_send_message`
- On success, update `connector_cursors.json` via `set_connector_cursor(id, max_submitted_at)`
- Render telemetry to the user

Without these procedural steps in SKILL.md, the v0.5 connector flow isn't actually usable end-to-end yet — even though all the primitives (E-A/B/C/D/E) are in place.

**Recommendation.** Author the orchestration section as a follow-on commit. Block on architect ack of the open questions in `v0.5_FIRST_PULL_SEMANTICS.md` (especially first-pull cap and bot-user invite preflight) since those shape the `/remember pull` half. Push half can land independently; my recommendation is to **ship push first** (simpler, no rate-limit pagination), then pull after architect signs off on first-pull semantics.

### G3. `connector.json` has no schema validation

**What it is.** A user can write a malformed `connector.json` (missing `id`, missing `type`, duplicate ids, non-list at root, etc.) and the failure surfaces only at first push/pull — usually as a confusing `KeyError` or `TypeError` deep in the orchestration. There's no load-time validation gate.

**Recommendation.** Add `load_connectors_config()` helper in `core.py` that opens `connector.json`, validates the schema (list of objects with required `id`/`type` keys; unique `id` values; recognized `type` values), and returns `(connectors, errors)`. SKILL.md orchestration calls this first, surfaces errors clearly, and aborts before the user-facing operation. ~30 lines of code; closes a real UX foot-gun.

## Medium gaps (works correctly, but rough)

### G4. No primitive for "untag from a connector"

**What it is.** `add_connector_ids` is additive only. Once a memory carries `connector_ids: ["engineering"]`, you can't remove that tag locally. This mirrors the v0.4 `add_groups` decision ("removal deferred — peers already have it") but for connectors the calculus is slightly different: you might want to mark a memory as "no longer relevant for engineering" locally even though the Slack-channel copy persists. Today's API offers no path; users would have to delete and re-store.

**Recommendation.** Two flavors:
- **Soft:** add a `connector_id_overrides: {<id>: "muted"}` payload field — opt-out without losing audit trail. Pushes skip "muted" entries on bulk-push to that connector.
- **Hard:** add `remove_connector_ids(memory_ids, connector_ids)` — accepts the architectural one-way-ness limitation and removes the tag locally only.

My lean: defer to v0.6, document the limitation prominently in SKILL.md so users don't expect un-share.

### G5. No `/remember push|pull` on connector declaration / first use

**What it is.** When a user adds a new connector to `connector.json`, nothing happens automatically. Their local store has no memories tagged with the new id, and the channel may have memories Claude doesn't know about. Pull-on-declare would catch them up; today it doesn't.

**Recommendation.** Document in SKILL.md: after `connector.json` edit, suggest the user run `/remember pull <new-connector-id>` to ingest channel history. Optional auto-prompt: if Claude reads `connector.json` and notices a new id with no cursor entry, suggest the pull proactively. Don't auto-execute (would surprise the user); do prompt.

### G8. Wire format and local store disagree on `content_hash` field semantics

**Related to G1 but distinct.** Even without unifying the algorithm, the wire envelope's `content_hash: "sha256:abc..."` field includes the `"sha256:"` prefix; the local Qdrant payload stores `content_hash: "abc..."` (16 hex chars, no prefix). On receive, the parser must strip the prefix and re-compute the local hash separately. The architecture doc §5.3 sketches this but doesn't explicitly say the local-store field has different semantics from the wire field. Code-level confusion risk when WP-E (connector code) lands.

**Recommendation.** Add an explicit note to architecture doc §5.3: "the wire `content_hash` is the integrity hash (raw sha256, `sha256:` prefix); the local Qdrant `content_hash` is the dedup hash (post-canonicalization, no prefix). They are computed from the same `content` but are different strings. Receivers re-compute both on receive."

## Operational polish (low priority but visible)

### G9. MCP tool list isn't dynamic — long sessions miss new tools

**What it is.** When `0.5.0-014` lands `add_connector_ids`, an already-running Claude session doesn't see the new tool until it restarts. The mem-fusion MCP subprocess caches its tool list at startup. Users mid-session can't invoke `add_connector_ids` until they `/exit` and reopen.

**Recommendation.** Document this in the 0.5.0-014 fix-script header (already done). Long-term, MCP supports `tools/list_changed` notifications — wiring those up would surface new tools live. Not blocking; cosmetic.

### G10. No telemetry / observability for connector traffic

**What it is.** When `/remember push engineering` happens, the user sees one-shot telemetry inline. There's no rolling log of "engineering connector has shipped N memories over T days" or "last successful pull from engineering at <ts>." Operators have no view of connector health.

**Recommendation.** A small `~/.local/share/mem-fusion/connector_telemetry.json` that the orchestration appends to on each push/pull. Schema: `{<connector_id>: {pushes: N, pulls: N, last_push_ts, last_pull_ts, errors: [...recent...]}}`. Capped at last 50 events to bound file size. Defer to v0.6 unless an operator (Atif, Shane, Jake) asks for it sooner.

### G11. Smoke-test messages linger in `#mf-test-connector`

**What it is.** Yours and mine are both still there. Real connector traffic will eventually accumulate test pollution that confuses readers and may falsely satisfy a future first-pull. Slack MCP available to me doesn't expose `chat.delete`.

**Recommendation.** Two options. (a) Add `chat.delete` to the Slack MCP scope and clean up periodically. (b) Mark smoke-test envelopes with `"is_smoke_test": true` (you already did this on your message; I didn't) and have the receive-side parser skip them as a routine filter. Option (b) is cheaper, doesn't require MCP scope changes, and gives test messages a permanent home in the channel without polluting the working set.

### G12. Connector reject path (rate-limit, malformed) has no user-facing design

**What it is.** Architecture doc §10 has the rate-limit table but the failure-mode user experience isn't designed. If `slack_send_message` returns 429, what happens? Does Claude retry? Surface the error? Drop the memory? Right now: undefined.

**Recommendation.** `v0.5_FIRST_PULL_SEMANTICS.md` §4 has a failure-modes table for pulls; do the symmetric thing for pushes in a brief addition to architecture doc §6. Three classes: retry-able (429 with Retry-After), fatal (401/403), unexpected (500). For retry-able: 3-attempt back-off. For fatal: surface to user with remediation hint. For unexpected: store memory locally tagged with a `pending_push_to: <connector>` marker for later retry.

# Mem-Fusion v0.5: Connector Architecture

Mem-fusion is a local memory layer for Claude plus a connector model that bridges local memories to productivity tools (Slack, etc.) for cross-machine sharing and human-observable activity. v0.5 introduces the connector architecture and ships the Slack connector as the first implementation.

Implementation tracked under WP-E (SlackConnector) and WP-F (Slack wire format).

---

## 1. Architecture in One Sentence

**Local mem-fusion + optional connectors to productivity tools. No peers, no groups, no daemon required.**

---

## 2. Mental Model

### Local mem-fusion (unchanged from v0.4)

Each machine runs its own complete stack:
- Qdrant (vector store) on `127.0.0.1:6333`
- Ollama (embedding model) on `127.0.0.1:11434`
- Mem-fusion MCP server exposing `store_memory`, `search_memory`, `memory_stats`, etc.
- Hooks for session priming, prompt injection, file-write capture, session ingestion

Memories live in the local Qdrant. The default is local-only — no propagation anywhere unless the user explicitly attaches a connector.

### Connectors (new in v0.5)

A **connector** is a declared bridge between local mem-fusion and one productivity-tool destination. Connectors live in `~/.local/share/mem-fusion/connector.json`. Each connector has:
- `id` — user-chosen string identifier (e.g., `engineering`, `marketing`, `personal-devices`)
- `type` — discriminator selecting which connector implementation handles it (`slack` in v0.5; future: `gdrive`, `teams`, `discord`, `notion`)
- Type-specific fields per the connector type's contract

A user can declare as many connectors as they like. Each targets a distinct substrate destination (a Slack channel, a GDrive folder, etc.).

### Memory-to-connector binding

Memories carry an optional `connector_ids: list[str]` field. A memory with no `connector_ids` is local-only. A memory tagged with `connector_ids: ["engineering"]` is eligible for push to the engineering connector.

`/remember push <connector-id>` pushes eligible memories through the named connector.
`/remember pull <connector-id>` ingests new memories from the named connector's substrate.

### Personal memories are always local by default

There is **no `personal` pseudo-connector.** A user who wants cross-machine sync of their own devices declares a regular connector (e.g., `{id: "personal-devices", type: "slack", channel: "mem_fusion_mitch_devices"}` pointing at a private Slack channel only they can read) and tags memories with that connector's id. Same flow, no special case.

### What's eliminated from v0.4 / earlier v0.5 drafts

- **Peers** (HTTP-addressed nodes that talked to each other).
- **Groups** (logical collections of peers).
- **Constellation daemon** (the two-listener HTTP server). Runs alongside through v0.5; retired post-connector-build phase.
- **HTTP connector type.** Productivity tools replace direct peer-to-peer.
- The `groups: [...]` field on memories. Read-tolerantly-ignored going forward. Existing v0.4 memories with `groups: ["personal"]` are treated as local-only.

## 3. Connector Config Schema

`~/.local/share/mem-fusion/connector.json` is the authoritative connector configuration:

```json
{
  "connectors": [
    {"id": "engineering",      "type": "slack", "channel": "mem_fusion_engineering"},
    {"id": "marketing",        "type": "slack", "channel": "mem_fusion_marketing"},
    {"id": "personal-devices", "type": "slack", "channel": "mem_fusion_mitch_devices"}
  ]
}
```

### Reserved fields (every connector)
- `id` — string identifier, user-chosen, unique within this user's config.
- `type` — discriminator, must match a known connector type.

### Type-specific fields
- **`slack`**: `channel: str` — the Slack channel that backs this connector.
- **Future (groundwork only in v0.5):**
  - `gdrive`: `folder: str`
  - `teams`: `channel: str`
  - `discord`: `channel: str`
  - `notion`: `database_id: str`

### Validation
Config-load time: each connector's fields are validated against its type's contract. Unknown `type` is rejected: *"unknown connector type 'X' — available: slack"*. Missing type-specific fields are rejected with the expected field list.

### Lifecycle
User edits `connector.json` directly (or asks Claude to edit it). No daemon restart required — the config is read on every push/pull invocation.

## 4. Memory Model

### Local-by-default
Default scope of any memory stored by mem-fusion is local-only. No propagation. The user opts in to sharing by attaching connector IDs.

### Connector tagging
Memories carry an optional `connector_ids: list[str]` field:
- `connector_ids: []` (or absent) — local only.
- `connector_ids: ["engineering"]` — eligible for push to the engineering connector.
- `connector_ids: ["engineering", "marketing"]` — eligible for push to both.

A memory can be tagged with multiple connector IDs. Pushing to each connector happens independently — pushing to "engineering" does not implicitly push to "marketing." Each push contacts exactly one connector at a time.

### `/remember push <connector-id>` requires a connector id

There is no "bare `/remember push`" — that would have been the `personal` group fallback in v0.4 and is gone. The user must name the connector explicitly. **Privacy invariant: outbound propagation requires explicit naming.**

Push semantics: send all memories tagged with `<connector-id>` whose `submitted_at` is greater than the local cursor for that connector. Cursor is tracked locally per-connector.

### `/remember pull <connector-id>`

Pulls new memories from the named connector's substrate. Filters out:
- Memories with `origin_node == self.node_name` (loopback prevention).
- Memories with `content_hash` already in local store (dedup).

### Migration from v0.4
v0.4 memories with `groups: [...]` continue to deserialize without error. The `groups` tag is ignored at scope-determination time. To re-tag an existing memory for a connector, the user invokes `add_connector_ids(memory_ids=[...], connector_ids=["<id>"])` — additive, same shape as v0.4's `add_groups`.

## 5. Wire Format (Slack Connector)

Each memory is one top-level Slack message carrying two payloads:
1. A human-readable message body (what humans see in the channel).
2. A JSON file attachment carrying the full machine-readable record.

### 5.1 Message body

```
[mem-fusion 0.5] mc-macbookpro · decision · 2026-05-15T03:00:00Z · engineering
content_hash: sha256:abc1234...

Privacy invariant fix landed for /remember autopush — non-personal connectors now require explicit naming.

(JSON attached: memory-abc1234.json)
```

Header line format:

```
[mem-fusion <version>] <origin_node> · <type> · <submitted_at> · <connector_id>
```

The `connector_id` in the header lets a human reading the channel identify which connector traffic they're seeing (useful when a workspace hosts multiple memory channels for different connectors).

`content_hash` on the second line is visible AND parseable — the pull-side optimization skips downloading the JSON attachment when the content_hash is already in local store.

The first-line content snippet (~100-200 chars) gives a skim-friendly summary.

### 5.2 JSON file attachment

Filename: `memory-<short-content-hash>.json` (8-char prefix; full hash inside).

```json
{
  "envelope_version": 1,
  "content_hash": "sha256:abc1234...",
  "origin_node": "mc-macbookpro",
  "submitted_at": "2026-05-15T03:00:00Z",
  "content": "<full memory text>",
  "vector": [0.123, 0.456, ...],
  "type": "decision",
  "tags": ["v0.5", "wp-1"],
  "project": "mem-fusion",
  "importance": 5,
  "connector_ids": ["engineering"]
}
```

`envelope_version: 1` reserves space for future format evolution (propagating edits, signatures, etc.). Receivers ignore unknown fields; receivers seeing a higher major envelope_version log and accept rather than reject.

### 5.3 `origin_node` semantics

`origin_node` is the machine ID of the posting node, distinct from the Slack user_id. A single Slack user may have multiple machines that all push to the same connector — each machine's posts carry its own `origin_node`, enabling:

- **Loopback prevention.** When mc-macbookpro pulls from a connector and sees its own past posts: `if origin_node == self.node_name: skip`. Never re-ingest your own posts.
- **Cross-machine recognition.** When mc-macbookair pulls and sees `origin_node = "mc-macbookpro"`, it knows the memory came from a different machine and should be ingested.

Slack's `user_id` is informational only — never stored in the payload, never used for routing.

### 5.4 Content hashing

`content_hash = "sha256:" + hex(sha256(content.encode("utf-8")))`. UTF-8 byte-exact content. No whitespace normalization. No Unicode normalization. Content is byte-exact at store time.

### 5.5 Size considerations

- Message body: ~500 chars; well under Slack's 40 KB text limit.
- JSON attachment: usually 8-16 KB (768-dim vector ~6 KB + content); under Slack's 1 GB file limit with massive headroom.

## 6. Slack Connector Interface

Four methods, defined by the connector SDK contract (WP-G):

### 6.1 `push(memory) -> {status, slack_ts, file_id}`

Format the body per §5.1, serialize the memory per §5.2, call `files.upload(channels=[<channel>], filetype="json", filename="memory-<short>.json", content=<json>, initial_comment=<body>)`. Capture `ts` and `file_id`.

Per-memory result: `{"status": "stored", "slack_ts": "1778829123.884419", "file_id": "F08XXX"}` or `{"status": "error", "reason": "..."}`.

Note: Slack doesn't dedup on receipt, so push always lands a new channel message. Sender-side dedup (per-connector cursor tracking) is the caller's responsibility.

### 6.2 `pull(since=<timestamp>) -> [memory, ...]`

1. **Read channel** — `slack_read_channel(channel_id, oldest=<unix-ts>)`.
2. **Filter on marker** — keep messages whose body starts with `[mem-fusion <N>]`.
3. **Parse header** — extract `origin_node`, `content_hash`, `submitted_at`, `connector_id`.
4. **Loopback check** — `if origin_node == self.node_name: skip`.
5. **Dedup check (cheap)** — `if content_hash in local store: skip without downloading`.
6. **Fetch attachment** — for survivors, download the JSON via `files.info` → `url_private`.
7. **Yield** — emit memory records.

### 6.3 `status() -> {ok, channel_id, channel_name, last_seen_ts, ...}`

Verify Claude has Slack auth, the channel exists and is accessible, return last message `ts`.

### 6.4 `since` cursor

Cursor is a `submitted_at` ISO-8601 timestamp from the local store, derived as the max `submitted_at` of memories tagged with this connector_id. First pull (no cursor): fetch all history with a progress UI surfaced to the user.

Double-filter on pull (`Slack ts > X` AND `JSON submitted_at > X`) defends against clock skew between origin nodes and Slack ingest.

## 7. Execution Context

The Slack connector runs **in Claude**, not in any daemon. The local mem-fusion MCP server handles `store_memory` / `search_memory` operations; Claude orchestrates push/pull through its own `mcp__claude_ai_Slack__*` MCP tools.

Why this is load-bearing:
- **Slack OAuth never enters mem-fusion's process space.** Claude already has the user's Slack auth via the MCP layer; mem-fusion does not duplicate or hold Slack tokens.
- **No new network surface.** No inbound listener, no daemon — exactly the property that corporate-Mac EDR environments need.
- **Connector implementation lives where the auth lives.** Slack-side calls happen in Claude's process context; mem-fusion stays local-only on the daemon side.

`/remember push <connector-id>` is a Claude-orchestrated operation:
1. Read `connector.json`; find connector by `id`.
2. Read local Qdrant for memories tagged with this connector_id whose `submitted_at` is past the local cursor.
3. For each memory: format wire payload, call Slack MCP tool, capture result.
4. Render per-memory delivery telemetry to the user.

Same shape for pull.

## 8. End-to-End Examples

### Example A: Single connector

User's `connector.json`:
```json
{"connectors": [{"id": "engineering", "type": "slack", "channel": "mem_fusion_engineering"}]}
```

User on mc-macbookpro: `/remember <decision text> for engineering`

1. Claude calls `mem-fusion/store_memory(content=..., type="decision", connector_ids=["engineering"])` → local id `abc-...`, content_hash `sha256:def567...`.
2. Claude reads `connector.json`, finds `engineering`.
3. Claude exports payload via `mem-fusion/export_record("abc-...")`.
4. Claude formats body + JSON, calls `files.upload(channels=["mem_fusion_engineering"], filetype="json", filename="memory-def567xx.json", content=<json>, initial_comment="[mem-fusion 0.5] mc-macbookpro · decision · ... · engineering\\ncontent_hash: sha256:def567...\\n\\nPrivacy invariant fix...\\n\\n(JSON attached)")`.
5. Slack returns `ts=...`, `file_id=F08xxx`.
6. Claude renders: *"Posted to engineering (#mem_fusion_engineering)."*

User on mc-macbookair: `/remember pull engineering`

1. Claude reads `connector.json`, finds `engineering`.
2. Reads local store cursor for connector_id "engineering" — currently empty → first-pull semantics: fetch all history.
3. Calls `slack_read_channel("mem_fusion_engineering", oldest=0)`.
4. For each message: marker check, header parse → `origin_node="mc-macbookpro"`, `content_hash=sha256:def567...`, `connector_id=engineering`.
5. Loopback check: `origin_node != "mc-macbookair"` → proceed.
6. Dedup check: not in local store → proceed.
7. Download attached JSON, parse, store via `mem-fusion/store_memory(..., connector_ids=["engineering"])`.
8. Render: *"Pulled from engineering: 1 new memory from mc-macbookpro."*

### Example B: Personal cross-machine sync

Mitch wants his two Macs to share personal memories. He creates a private Slack channel `#mem_fusion_mitch_devices` (only he is a member). Adds the same connector to both Macs' `connector.json`:

```json
{"connectors": [{"id": "personal-devices", "type": "slack", "channel": "mem_fusion_mitch_devices"}]}
```

He tags personal memories with `connector_ids: ["personal-devices"]` at store time (or after the fact). `/remember push personal-devices` from mc-macbookpro pushes them to the channel; `/remember pull personal-devices` from mc-macbookair ingests them. Same code path as Example A — no special case for "personal."

### Example C: Loopback case

mc-macbookpro pulls from the engineering channel it has been posting to:

Step 4 of the pull flow: `origin_node == "mc-macbookpro"` (self). Skip without downloading attachment. The Mac never re-ingests its own posts.

## 9. Migration from v0.4

### Existing v0.4 memories
v0.4 memories carry `groups: ["personal"]` or `groups: [<team-name>]`. Going forward:
- The `groups` field is read tolerantly and ignored at scope-determination time.
- Existing memories become local-only effectively.
- Re-tagging an existing memory for a connector: `add_connector_ids(memory_ids=[...], connector_ids=["<id>"])` (additive, same shape as v0.4's `add_groups`).

### Constellation daemon
The Constellation daemon (`com.branchapp.memfusion.constellation`) stays running through v0.5 connector development — no urgent retirement. Post-connector-build phase, a fix script (`0.5.0-NNN-retire-constellation.sh`) stops the daemon, unloads the plist, archives `~/.local/share/mem-fusion/constellation/`, and removes peer config remnants.

Until that script lands, Constellation is a no-op for connector flows — it has no role in `/remember push <connector-id>` or `/remember pull <connector-id>` paths.

### Re-establishing cross-machine sync
Users who relied on Constellation HTTP peer sync re-establish sync via a connector:
1. Create a private Slack channel for the sync purpose (e.g., `#mem_fusion_<userhandle>_devices`).
2. Add a matching connector to each machine's `connector.json` (same `id`, same `channel`).
3. Tag memories with that connector_id going forward (or re-tag existing ones via `add_connector_ids`).
4. Run `/remember push <id>` on the source machine and `/remember pull <id>` on the destination.

## 10. Slack Limits

### Rate limits (Slack Web API tiers)

| Method | Tier | Practical limit |
|---|---|---|
| `files.upload` | Tier 2 | ~20/min |
| `conversations.history` | Tier 3 | ~50/min |
| `conversations.info` | Tier 3 | ~50/min |
| `files.info` | Tier 4 | ~100/min |

Bulk push self-rate-limited at 3 sec/message stays well under Tier 2.

### Size limits
- Message text: 40 KB (~80× headroom over a ~500-char body).
- File upload: 1 GB (~60,000× headroom over a 16 KB JSON attachment).
- Channel history retention: workspace policy dependent (unlimited on most paid plans, 90 days on free tier).

### Channel limits
- Members per channel: 1,000 (private) / 50,000 (public).
- Files per channel: unlimited but counted against workspace storage quota.

### Notification limits
Slack collapses bursts into "N new messages" summaries during high-traffic periods. Mitigation via channel-specific user notification preferences ("only mentions" for high-volume memory channels).

## 11. Human-Performance Considerations

### Channel noise
Dedicated channel per connector. Don't mix mem-fusion channels with general team-chat channels — *"this Slack channel is the connector's substrate"* is the load-bearing convention.

### Visual differentiation
Mitigations baked into the wire format:
- `[mem-fusion 0.5]` prefix always at the start of the first line.
- Header line uses `·` separators — distinctive in normal prose.
- First-line content snippet for skim-friendly summary.

Optional emoji prefix (`📝 [mem-fusion 0.5] ...`) for enhanced scannability. Decorative; pull-side filter still matches on the bracketed prefix.

### Notification fatigue
Encourage users to set high-traffic memory channels to **"only mentions"** notification level. The mem-fusion side does not auto-mute.

### Search & discovery (a notable win)
Slack indexes every message body. A user searching for *"privacy invariant"* in their Slack client finds the original memory's channel message — a usability win over the previous local-only model.

### Accidental human triggering
Defense in depth: pull-side filter requires the `[mem-fusion 0.5]` prefix AND a parseable header (`origin_node`, `content_hash`, `submitted_at`, `connector_id` well-formed) AND a JSON file attached. Casual human messages with the prefix fail the structural validation and are skipped.

## 12. Machine-Performance Considerations

### 12.1 Bulk catch-up after long offline
Cost: a user offline for a week may have 100+ new memories. Pull = one `conversations.history` + 100 attachment fetches = 20 sec serialized.

Recommendation: **concurrency-limited parallel fetches.** Cap at 10 concurrent attachment downloads → ~2-3 seconds total. Surface progress: *"Pulling 100 new memories from engineering (12 of 100…)."*

### 12.2 Push throughput
`files.upload` Tier 2 limit ~20/min. Self-rate-limit at 3 seconds per push to stay safely under. For N=80 bulk push: 80×3 = 4 minutes with progress shown to user.

### 12.3 Concurrent multi-connector pulls
A user with 3 slack connectors → bulk pull runs 3 pulls concurrently. Cap total concurrency at 10 outbound connections.

### 12.4 Token expiry mid-session
Claude's Slack OAuth refreshes periodically. If a token expires mid-pull, the operation returns 401. Catch 401 in the connector, surface a re-auth prompt, don't auto-retry — re-auth is interactive.

### 12.5 Attachment storage bloat (long-tail)
~16 KB per memory × 1000 memories/year = 16 MB. Negligible against typical 5-10 GB workspace quotas.

### 12.6 Out-of-order delivery
A peer with a slow clock could post a memory with `submitted_at` slightly older than a peer that already pushed. Double-filter (Slack `ts > X` AND JSON `submitted_at > X`) handles it; local content_hash dedup catches duplication.

## 13. Risks

- **Slack workspace retention** silently deleting memories. Local Qdrant is canonical source-of-truth; Slack is transport, not archive.
- **Channel rename / archive** breaks the connector's `channel` field. Status check surfaces the failure; user updates `connector.json`.
- **Token expiry** — re-auth via Claude's normal Slack flow.
- **Out-of-order processing** — double filter handles.
- **Channel access lost mid-session** — surface clearly to the user.
- **File attachment deletion** — Slack admin or retention may delete attached files without deleting the message body. Pull tries to fetch, gets 404. Log + skip; the message body's `content_hash` makes the gap identifiable.
- **Workspace data residency** — sensitive content lives in Slack's storage. Document; users decide which connectors carry sensitive content.

## 14. Validation Plan

End-to-end test on real Slack:

1. Create test channel `#mf-connector-test`. Add Claude's user.
2. Configure two machines with connector `{"id": "test", "type": "slack", "channel": "mem_fusion_test"}`.
3. `/remember <test memory> for test` from one machine → verify message + JSON attachment lands with correct wire format.
4. From the other machine: `/remember pull test` → verify ingest, dedup, loopback prevention.
5. Test failure modes: archive channel temporarily (status check fails); remove a user (pull 403); expire token (401).
6. Test Example B (personal cross-machine sync) end-to-end with a private channel.
7. Test corporate-Mac use case: a Falcon-blocked-inbound machine pushes/pulls successfully — outbound HTTPS to Slack is allowed.

## 15. Out of Scope for v0.5

- **Other connector types.** GDrive, Teams, Discord, Notion are groundwork only — `type` field reserves their values, but only `slack` ships in v0.5.
- **Claude-routed notifications.** Tier 2 session-start auto-pull deferred per prior architectural decision; v0.5 ships Tier 1 (Slack native channel UI) only.
- **Constellation daemon retirement.** Stays running through v0.5; retired post-connector-build phase via a future fix script.
- **WP-I propagating edits.** `envelope_version` field reserved for future use.
- **Threaded bulk-push notification mitigation.** Deferred.
- **Bulk re-tagging tooling for v0.4 → v0.5 migration.** Manual via per-memory `add_connector_ids` calls for now.
- **Workspace encryption / E2E content protection.** Documented as workspace-policy concern; no in-protocol encryption in v0.5.

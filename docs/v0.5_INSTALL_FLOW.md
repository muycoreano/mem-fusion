## Architectural decisions (locked)

Six decisions; these are not debatable in implementation:

1. **One artifact: `install.sh`.** No `bootstrap.sh`. install.sh self-bootstraps when piped through curl by cloning the repo and re-execing from inside.
2. **Idempotent end-to-end.** Fresh install, partial-upgrade, fully-current install — same command, correct behavior for each. The fix-script idempotency convention extends to the whole installer.
3. **Pure shell + small Python helper.** No Claude in the critical path. The Slack connector setup — the one place Claude is genuinely needed (Slack MCP auth lives in Claude's process) — is deferred to a skill loaded by install.sh, not part of install.sh itself.
4. **Anchor-based file patching.** `~/CLAUDE.md`, `~/.claude/settings.json`, and any other user-editable file is patched between explicit anchor comments (e.g., `<!-- mem-fusion:start -->` … `<!-- mem-fusion:end -->`), backed up before modification, with the canonical block refreshed between anchors. User edits outside the anchors are preserved.
5. **Three invocation paths, one script:**
   - Direct curl: `curl -fsSL .../install.sh | bash` → self-bootstrap clones + re-execs.
   - Claude-mediated: user tells Claude to install; Claude reads README, runs the same curl line via Bash.
   - Developer mode: `git clone && cd && bash install.sh` → self-bootstrap detects existing `src/` adjacent, skips the clone.
6. **Slack connector setup lives in a skill, not install.sh.** install.sh copies `src/skills/mem-fusion-slack-connector/SKILL.md` to `~/.claude/skills/` and ends with a one-line handoff message; the actual Slack-connector-setup interview happens when the user next opens Claude and asks about it.

## install.sh — 16-step spec

```
 1. Self-bootstrap                     (detect or clone; re-exec from inside repo)
 2. Pre-flight                          (macOS, arch, brew prefix, claude CLI, port collisions)
 3. Homebrew deps                       (python@3.12, ollama)
 4. Directory tree                      (~/.local/share/mem-fusion/{bin,scripts,logs,queue,qdrant-data,snapshots})
 5. Python venv + requirements
 6. Qdrant binary                       (download per arch from GitHub releases)
 7. Qdrant config                       (qdrant-config.yaml with absolute paths, no $HOME-in-yaml bug)
 8. Deploy source                       (cp src/core.py, src/mem_fusion.py, src/connectors/, src/scripts/* to deployed locations)
 9. launchd plists                      (Qdrant, Ollama; Constellation conditional)
10. claude mcp add mem-fusion           (idempotent; check existing before adding)
11. settings.json hook entries          (anchor-based; backup + refresh between anchors)
12. ~/CLAUDE.md Vector Memory section   (anchor-based; backup + refresh)
13. ~/.claude/skills/ install           (cp src/skills/remember + src/skills/mem-fusion-slack-connector)
14. Iterate fix scripts                 (bash src/scripts/fixes/0.5.0-*.sh in numeric order; idempotent)
15. Preload + import memories           (Python helper: 8 canonical + scan ~/.claude/projects/*/memory/)
16. Final summary + handoff             (printed status table + Slack-connector skill pointer)
```

### Per-step implementation notes

**Step 1 — Self-bootstrap.** Top of file:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd 2>/dev/null)" || SCRIPT_DIR=""
if [ ! -f "${SCRIPT_DIR}/src/scripts/fixes/0.5.0-001-fix-qdrant-home-path.sh" ]; then
  CLONE_DIR="${MEMFUSION_CLONE_DIR:-${HOME}/dev/mem-fusion}"
  if [ ! -d "${CLONE_DIR}/.git" ]; then
    git clone https://github.com/muycoreano/mem-fusion "${CLONE_DIR}"
  else
    (cd "${CLONE_DIR}" && git fetch origin && git checkout v0.5 && git pull)
  fi
  cd "${CLONE_DIR}"
  exec bash install.sh "$@"
fi
cd "${SCRIPT_DIR}"
```

The detection key — `src/scripts/fixes/0.5.0-001-*.sh` adjacency — is stable: it exists in every clone of the repo.

**Step 2 — Pre-flight.** Existing pre-flight from current INSTALL_MEM_FUSION.md ports cleanly. One addition: detect existing install (`~/.local/share/mem-fusion/bin/qdrant` + Qdrant responsive on :6333 + `claude mcp list | grep mem-fusion`). If detected, log "Existing install detected; will upgrade in place" and continue (don't abort). No `--force` flag needed — idempotency makes the script safe to re-run.

**Steps 3–7 — Platform setup.** Straight port from current INSTALL_MEM_FUSION.md, no behavior changes.

**Step 8 — Deploy source.** Replaces the 2000+ lines of heredoc'd source with simple `cp`. Each file gets a content-hash check before overwrite — if deployed file is byte-identical to repo source, skip. Otherwise backup + replace.

**Step 9 — launchd plists.** Existing pattern. **Important caveat:** apply the `launchctl kickstart -p gui/$UID/<label>` pattern per memory `da77fa1a` (corporate-Mac launchd quirk). Already documented; engineer should ensure every plist load is followed by the kickstart.

**Step 10 — MCP registration.** Idempotent: `claude mcp list | grep -q mem-fusion || claude mcp add mem-fusion <invocation>`. No overwrite logic needed; existing entries are correct.

**Step 11 — settings.json hooks.** Anchor-based patching. Existing settings.json hook entries already use a fixed structure; install.sh reads, locates the anchor pair (creating if absent), refreshes the entries between anchors, writes back with timestamped backup. Use jq or Python; not raw sed.

**Step 12 — CLAUDE.md.** Same anchor-based pattern. Anchors: `<!-- mem-fusion:vector-memory-system:start -->` and `<!-- mem-fusion:vector-memory-system:end -->`. If anchors absent, append to end of file with anchors around the canonical block. If present, refresh between them. Backup `~/CLAUDE.md.bak.<ts>`.

**Step 13 — Skills install.** `cp -R src/skills/remember/ ~/.claude/skills/remember/` and `cp -R src/skills/mem-fusion-slack-connector/ ~/.claude/skills/mem-fusion-slack-connector/`. Overwrite-on-content-drift; backup if user has edited.

**Step 14 — Fix scripts.** This is the upgrade path. Iterate `src/scripts/fixes/0.5.0-*.sh` in numeric order; each script self-detects its applied state and exits clean if so. install.sh just invokes; the scripts handle their own idempotency. Print one line per script: `[applied|skipped|failed]`.

**Step 15 — Preload + import.** Python helper at `src/scripts/install_helpers/preload.py`. Imports `core`, calls `core.store_memory` for each of the 8 canonical onboarding memories (content frozen in the helper), then globs `~/.claude/projects/*/memory/*.md`, parses each, calls `core.store_memory`. Dedup via `core.find_or_create` (existing entries no-op). Idempotent.

**Step 16 — Final summary.** Fixed-format status table:

```
========================================
mem-fusion install complete

  Qdrant:        running (127.0.0.1:6333)
  Ollama:        running (127.0.0.1:11434)
  Constellation: running (127.0.0.1:7533/7534)  [or "not installed"]
  MCP:           registered (mem-fusion)
  Hooks:         4 wired
  Skills:        2 installed (remember, mem-fusion-slack-connector)
  Memories:      143 stored, 8 preloaded this run
  Fix scripts:   17/17 applied

NEXT STEPS:
  1. Restart Claude Code (Ctrl-D / reopen) so the MCP picks up the new code.
  2. (Optional) Ask Claude to set up the mem-fusion Slack connector
     for cross-machine memory sharing.

  Repo:   ~/dev/mem-fusion  (or wherever MEMFUSION_CLONE_DIR points)
  Logs:   ~/.local/share/mem-fusion/logs/
========================================
```

## `src/skills/mem-fusion-slack-connector/SKILL.md` — full spec

Reference-shaped skill, not one-shot installer. Operational guide Claude consults whenever the user touches Slack-connector functionality. Triggered by phrases like *"set up the Slack connector,"* *"connect mem-fusion to Slack,"* *"share memories via Slack,"* *"why isn't my Slack push working,"* *"add another Slack channel for mem-fusion."*

### Sections

1. **What this skill is and isn't.** Operational reference for the Slack connector specifically; complements `/remember` (which handles generic dispatch). Not a one-shot installer; consulted any time Slack-connector work happens.

2. **Setup (first-time connector configuration).** Step-by-step:
   - Check `~/.local/share/mem-fusion/connector.json`. If non-empty + has a slack entry, skip and report current state.
   - Probe Slack MCP via `slack_search_channels(query="general")`. If error → no Slack access; write empty `connector.json`; report "Slack not available, you're set up local-only."
   - Prompt user: default channel suggestion: `mf-<userhandle>-devices` (private, personal mesh). Allow user to choose existing channel or create new.
   - Resolve channel id via `slack_search_channels`. If multiple matches, present options.
   - Bot-user preflight: try `slack_read_channel(channel_id)` with limit=1. If `channel_not_found` or `not_in_channel`, surface "invite required: `/invite @claude_ai` in the channel."
   - Write `connector.json` with the new entry.
   - Smoke test: store a "install complete" memory, push to the connector, read back, verify integrity. Report result.

3. **Push/pull operation.** Slack-specific knowledge: channel-id resolution, rate-limit awareness, fence normalization, body-size cap (38 KB practical vs 40 KB Slack ceiling), bot-user invite requirements. `/remember` skill handles the dispatch; this skill carries the Slack-specifics.

4. **Multi-connector management.** Adding additional Slack channels (e.g., a team channel alongside a personal-mesh channel), changing a channel target, the additive-only constraint on `connector_ids`, soft-mute via empty channel.

5. **Troubleshooting.** Common failure modes:
   - Auth expired → user re-auths Slack MCP
   - `channel_not_found` → channel renamed/deleted or wrong workspace
   - `not_in_channel` → invite the bot user
   - Rate-limit sustained → wait, re-run push (cursor handles resume)
   - Integrity-failed on receive → likely content_hash drift; re-run `0.5.0-015` fix script
   - Smoke test push works but pull returns 0 → likely the receive-side hasn't deployed canonical core.py yet

Each failure mode gets a concrete remediation. The skill is the troubleshooting surface for the Slack connector; `/remember` general-troubleshooting hands off to it for Slack-specific issues.

## Engineering principles applied

Per memory `03a76468` (the five durable principles from the staff audit):

| Principle | Application here |
|---|---|
| 1. Test the production function | install.sh's preload step calls `core.find_or_create` directly. No parallel "preload-scaffold" code. |
| 2. No hand-edited data in tests | The 8 canonical memories are content-frozen in `preload.py`; tests load and verify them via the production path. |
| 3. Maintainability check before commit | install.sh structured as 16 named steps with explicit per-step idempotency; readable cold. |
| 4. Don't grow core.py | preload.py is a standalone helper; doesn't extend core.py. |
| 5. Connectors via the ABC | The Slack-connector skill is the only Slack-specific knowledge embedded in install flow; everything else routes through `connectors.get_connector(type)`. |

## Smoke tests required before merge

Three scenarios; all must pass:

1. **Fresh install on a clean machine.** New macOS user, no Homebrew, no Claude Code installed. Run the curl line. Expect: bootstrap clones repo + Homebrew prompts user to install + everything else proceeds.

2. **Upgrade an existing install.** This machine (mc-macbookpro) or any peer with fix scripts 001-014 applied. Re-run install.sh. Expect: detects existing install, applies 015/016/017 + any missing earlier fixes, refreshes deployed code, no-op on already-applied steps. Total time: ~30 seconds.

3. **Up-to-date install.** Machine with all 17 fix scripts applied + canonical code deployed. Re-run install.sh. Expect: every step reports "skipped (already applied)"; total time ~5 seconds.

Scenario 4 is implicit but worth naming: **interrupted-install recovery.** If install.sh fails midway (network, brew error), the user re-runs it. Idempotency means the second run picks up cleanly from wherever the first left off.

## Open calibration items

Five small decisions worth surfacing to engineer:

1. **Where does the cloned repo live?** Default `${HOME}/dev/mem-fusion`; overridable via `MEMFUSION_CLONE_DIR`. Engineer: confirm or propose alternative.
2. **Branch pinning in the self-bootstrap clone.** Currently `git checkout v0.5`. After release, should pin to a tag (e.g., `v0.5.0`)? Engineer: design tag-vs-branch handling.
3. **Constellation install behavior.** Should install.sh auto-install Constellation if absent, or only when a flag is set? Architect lean: install by default (it's part of the v0.5 experience); engineer can object.
4. **launchd kickstart timing.** Step 9 plist load + kickstart works; but the health-check loop afterwards may need tuning for slow machines. Engineer: empirically calibrate timeouts.
5. **Preload memory content drift.** The 8 canonical onboarding memories will likely evolve over versions. Process for updating: edit `preload.py` content, ship under a new fix script (`0.5.x-NNN-refresh-preload.sh`) that re-runs preload.

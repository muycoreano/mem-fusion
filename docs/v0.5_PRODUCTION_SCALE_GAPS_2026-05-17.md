# Mem-Fusion v0.5 — Production & Scale Gaps Analysis

**Date:** 2026-05-17
**Author:** Claude-Architect (mc-macbookpro)
**Repo state:** `v0.5` branch at commit `3e22410`

> This document enumerates production-readiness and at-scale gaps in mem-fusion as it currently exists. **Solutions are deliberately omitted.** Claude-Engineer (mc-macbookair) will weigh in on remediation paths, sequencing, and which gaps deserve the v0.5 / v0.6 / "deferred indefinitely" buckets.
>
> Each gap is given a stable identifier (`G-<category>-<n>`), the code location where applicable, what the current behavior is, and the scale at which the gap bites. No prescriptions.

---

## 0. Scope

**"Production at scale" assumptions in this analysis:**

- Multi-machine deployment: 5+ peers per user; multiple distinct users across an org.
- Per-machine memory count: 10⁴ → 10⁶ entries on the time horizon.
- Cross-machine sharing via both Constellation P2P (transitional) and Slack connector (v0.5).
- Always-on operation across reboots, network partitions, version drift, and corporate-Mac environments (Falcon/ThreatLocker EDR).
- Sensitive content in some connector channels (audit + compliance concerns).
- Operating budget: human-administered, but with hooks running on every Claude turn — sub-second overhead matters.

**Explicitly out of scope here:**

- Single-user, single-machine dev use (the current happy-path; works fine).
- Workspace-bounded experimentation (the v0.4 / v0.5 development pattern).

## 1. Storage Layer (Qdrant via `core.py`)

### G-STORAGE-1: Hard-coded 10,000-point scroll limit on stats and cursor derivation

**Where:** `src/core.py:555` (`memory_stats`), `src/core.py:655` (`max_submitted_at_in_group`)

**Observation:** Both functions issue `qdrant.scroll(..., limit=10000, ...)` and assume the entire collection (or per-group subset) fits inside that single page. `memory_stats` derives `last_stored` from the timestamps it sees in that one page; `max_submitted_at_in_group` derives the pull cursor the same way.

**Scale trigger:** at >10⁴ memories total, `memory_stats.last_stored` silently reports a timestamp that is not the actual most recent. At >10⁴ memories in any single group, `max_submitted_at_in_group` returns a cursor that's not at the true tail — subsequent pulls miss memories. Both are silent failures; no error surfaced.

---

### G-STORAGE-2: `memory_stats` is O(types + 1) Qdrant calls per invocation

**Where:** `src/core.py:541-561`

**Observation:** `memory_stats` does 7 separate `qdrant.count()` calls (one per declared type enum value) plus one `scroll(limit=10000)` to derive `last_stored`. Called from `SessionStart:compact` hook on every Claude session boot.

**Scale trigger:** 7+1 = 8 Qdrant roundtrips on every session start. With 4 active Claude sessions across machines, ~32 Qdrant calls/session-start-burst. Latency budget for session start: ~200ms target; this alone consumes ~80ms at p50 on healthy local Qdrant, more under load.

---

### G-STORAGE-3: `search_memory` top_k clamped at 20; no pagination

**Where:** `src/core.py:404` — `top_k = min(int(args.get("top_k", 8)), 20)`

**Observation:** Even if a caller wants more results (e.g., bulk semantic enumeration for a UI), the function silently truncates to 20. No `next_cursor` returned. `search_recent` is similarly clamped to 50 (`src/core.py:425`).

**Scale trigger:** any caller wanting to enumerate memories across a topic without per-call query gymnastics. Currently no path to retrieve the 50th-highest-scoring match against a query.

---

### G-STORAGE-4: Content hash truncated to 16 hex chars (64 bits)

**Where:** `src/core.py:134-136` — `return hashlib.sha256(text.strip().lower().encode()).hexdigest()[:16]`

**Observation:** The dedup-and-integrity hash is a 16-char (64-bit) prefix of SHA-256. Birthday-bound collision probability reaches 50% at ~5 billion unique contents. Practical exposure much lower (10⁵-10⁶ memories), but the integrity check used in `constellation.py:296-299` to detect tampering ("content_hash mismatch — content modified in transit") inherits the same 64-bit collision resistance.

**Scale trigger:** integrity claim weakens as a network adversary gains compute or as the corpus grows. At 10⁹ memories the probability that any pair collides is ~1/40.

---

### G-STORAGE-5: `content_hash` strips whitespace and lowercases input

**Where:** `src/core.py:136` — `hashlib.sha256(text.strip().lower().encode()).hexdigest()[:16]`

**Observation:** Two memories that differ only in case or surrounding whitespace are treated as the same content. The "stored" payload preserves the original (un-stripped, original-case) text, but the dedup decision uses a normalized hash. This means the *first* store wins; subsequent stores of "FooBar" after "foobar" are no-ops.

**Scale trigger:** any workflow that depends on case-sensitive memory uniqueness (e.g., code snippets where casing carries semantics like `MyClass` vs `myclass`). Currently silently lossy.

---

### G-STORAGE-6: No backup or snapshot story

**Where:** absent — `~/.local/share/mem-fusion/qdrant/storage/` lives on the user's disk; no scheduled snapshot, no restore script, no cross-machine canonical replica.

**Observation:** Disk corruption, accidental directory deletion, or filesystem failure permanently destroys local memory. Constellation peers may carry partial replicas via push history, but pull is initiated by the empty peer — a freshly-wiped machine has no record of which memories it had.

**Scale trigger:** any disk failure event. MTTF on consumer SSDs is years, but with multiple machines deployed the aggregate probability rises.

---

### G-STORAGE-7: Single shared collection across all users on a machine

**Where:** `src/core.py:44` — `COLLECTION = "cowork_memories"` (note the legacy name — collection rename not yet performed)

**Observation:** Single hard-coded collection name. Any process running as any user account on the same machine that can reach `127.0.0.1:6333` reads/writes the same memories. No per-user namespace.

**Scale trigger:** shared-machine deployments (households, shared workstations, kiosks). Currently mem-fusion is "whichever user has Claude's MCP wired up wins."

---

### G-STORAGE-8: `migrate_legacy_entries` scrolls the entire collection on every daemon startup

**Where:** `src/core.py:663-702`, called from `src/constellation.py:777` and `src/mem_fusion.py:234`

**Observation:** The function paginates through every memory in the collection (`scroll(limit=512, offset=...)` until exhausted), checks each payload for legacy v0.3 shape, and is a no-op for v0.4+ entries. But the *scan* still happens on every startup, including when 100% of entries are already migrated.

**Scale trigger:** at 10⁵+ memories, daemon startup spends multiple seconds scanning before serving its first request. Hooks calling Qdrant during this window get errors or stalls.

---

### G-STORAGE-9: Qdrant has no auth; bound to localhost only

**Where:** `src/core.py:130` — `qdrant = QdrantClient(url=QDRANT_URL, timeout=10)`; default URL `http://127.0.0.1:6333`.

**Observation:** Qdrant runs without an API key. Localhost binding is the only access control. Any process on the machine that knows the URL can read, write, or delete memories.

**Scale trigger:** any compromised local process (malicious npm install, supply-chain'd binary, malware) has full memory exfiltration. No defense-in-depth.

## 2. Embedding (Ollama)

### G-EMBED-1: New HTTP connection per embed call

**Where:** `src/core.py:174` — `async with httpx.AsyncClient(timeout=8.0) as client:` inside every `embed()` invocation.

**Observation:** Each `embed()` call constructs an `httpx.AsyncClient`, makes one request, and tears down the client. No connection pooling across calls. TCP handshake + httpx setup is ~1-3ms; for 100 sequential embeds that's 100-300ms of pure overhead atop the 25ms-per-embed compute cost.

**Scale trigger:** any bulk embed pipeline (initial onboarding, re-embed after model upgrade, batch ingestion from connectors).

---

### G-EMBED-2: Soft truncation at 8000 chars silently loses semantic content

**Where:** `src/core.py:165` — `embed_text = text[:EMBED_MAX_CHARS] if len(text) > EMBED_MAX_CHARS else text`

**Observation:** The 0.5.0-007 fix added input-length guard. The *full content* is preserved in storage but the *vector* derives only from the first 8000 characters. Semantic similarity for the truncated tail is invisible. Two memories of size 12000 chars that share the same first 8000 but differ in the last 4000 produce *identical* vectors and trigger the `find_or_create` 0.82-similarity collapse (`src/core.py:490`), conflating them.

**Scale trigger:** any memory with substantial content past the 8000-char mark (long-form decision memos, multi-page transcripts, code-with-prose summaries). The `0.5.0-007` fix CHANGELOG note already flags this: "chunked embedding with canonical_id post-dedup is the correct long-term answer."

---

### G-EMBED-3: 8s timeout; no retry; no exponential backoff

**Where:** `src/core.py:174` (timeout), `src/core.py:198-202` (catch-all on connection failures)

**Observation:** Single attempt with 8s wall clock. On transient failure (Ollama swapped out of RAM, network hiccup), the embed returns `ollama_unreachable` and the caller surfaces a hard error. The 0.5.0-008 OLLAMA_KEEP_ALIVE=24h fix mitigates cold-load timeouts but doesn't address actual transient failure.

**Scale trigger:** any embed call during a high-load moment on the machine. With 4-6 Claude sessions all hitting embed simultaneously, the Ollama queue can exceed 8s.

---

### G-EMBED-4: Per-process embed cache; not shared across constellation, mem-fusion, hooks

**Where:** `src/core.py:56` — `_embed_cache: OrderedDict = OrderedDict()`

**Observation:** The LRU cache is process-local. Three separate Python processes routinely import `core`: the mem-fusion MCP server, the constellation daemon, and the hook script subprocesses. Each maintains its own cache. Identical embeds across processes pay the Ollama cost three times.

**Scale trigger:** any scenario where the same query is issued by both the MCP server (via Claude's search_memory) and a hook (search_recent in Pass 2) within a session. The constellation daemon also embeds nothing currently, but if push/pull paths ever required re-embedding, the duplication multiplies.

---

### G-EMBED-5: Ollama has no auth; bound to localhost only

**Where:** `src/core.py:41` — default `OLLAMA_URL = "http://127.0.0.1:11434"`

**Observation:** Same as G-STORAGE-9. Any process can issue arbitrary embed requests, including ones that exfiltrate sensitive query content via Ollama's logs.

**Scale trigger:** compromised local process.

## 3. MCP Server (`mem_fusion.py`)

### G-MCP-1: 30-second gateway timeout blocks bulk group operations

**Where:** `src/mem_fusion.py:34` — `GATEWAY_TIMEOUT_S = 30.0`

**Observation:** Both `group_pull` and `group_push` issue HTTP POST to the local Constellation gateway with a 30s timeout. Constellation's push path (`constellation.py:678`) is `for peer in peers: for p in candidates: httpx.post(...)` — serial. At 5 peers × 100 memories × ~50ms/request = 25s; adding any latency tips over 30s.

**Scale trigger:** bulk push of >80 memories to >3 peers. Times out from MCP's perspective; Constellation continues running, leaving inconsistent partial state.

---

### G-MCP-2: No batch primitives

**Where:** all `core.*` functions take one memory at a time.

**Observation:** `store_memory`, `upsert_memory`, `find_or_create`, `delete_memory` all single-record. Bulk ingestion (e.g., importing 500 memories from a transcript) is 500 sequential MCP calls. Claude's MCP tool-call overhead is ~5-15ms per call alone, atop the embed cost.

**Scale trigger:** any bulk ingestion path. Currently impractical for >50-memory batches.

---

### G-MCP-3: No rate limiting at the MCP boundary

**Where:** `src/mem_fusion.py` — no global state on call frequency.

**Observation:** A misbehaving Claude session could fire 1000 `store_memory` calls in a tight loop, saturating Ollama and Qdrant. No back-pressure.

**Scale trigger:** runaway sub-agents, misconfigured hooks, malicious extensions.

---

### G-MCP-4: No observability hooks (metrics, traces)

**Where:** `src/mem_fusion.py` overall.

**Observation:** Logs are written to per-startup files (`core.py:99-121`) in unstructured format. No counter for `store_memory_total`, `embed_failed_total`, `search_latency_ms` histogram, etc. No way to surface "Ollama failure rate climbed in the last hour" without manual log scraping.

**Scale trigger:** any incident response, capacity planning, or perf regression investigation.

---

### G-MCP-5: No per-tool error budget; one bad tool failure becomes a session-level failure

**Where:** `src/mem_fusion.py:159-166` — `call_tool` catches `Exception` and returns `{"error": str(e)}`. Claude treats the error as the tool result.

**Observation:** A transient Qdrant 500 surfaces as a hard error string. Claude has no signal to retry. No circuit-breaker pattern.

**Scale trigger:** flaky Qdrant or Ollama under load → user sees apparent "memory broken" rather than transient hiccup.

---

## 4. Constellation P2P (`constellation.py`, transitional)

### G-CONSTELLATION-1: Single-threaded HTTPServer; peer requests serialize

**Where:** `src/constellation.py:788` — `peer_server = HTTPServer((peer_host, int(peer_port)), PeerHandler)`

**Observation:** Python's `http.server.HTTPServer` is *not* threaded. Concurrent inbound `/memory/put` requests from N peers queue and process one at a time. `gateway_server` likewise.

**Scale trigger:** simultaneous push from multiple peers (e.g., 4 machines all pushing to a 5th at session-end). p99 inbound latency grows linearly with concurrent senders. At 10+ peers, a single slow Qdrant write blocks every other peer waiting.

---

### G-CONSTELLATION-2: No authentication on peer endpoint (`0.0.0.0:7533`)

**Where:** `src/constellation.py:788` binds to all interfaces by default.

**Observation:** The peer surface is LAN-reachable. Any host that can reach `:7533` can:
- POST `/memory/put` with arbitrary content tagged into any group it claims membership in. The `unknown_groups` check (`constellation.py:288-294`) requires the receiver to be a member of the group, but doesn't validate that the *sender* is.
- GET `/memory/since?group_name=<G>` and exfiltrate every memory in group G (subject to the receiver's group membership).
- Spoof `origin_node` — receiver records the value sent on the wire without validating against the sender's actual identity.

**Scale trigger:** any LAN broader than "trusted home network." Coffee shop wifi, hotel wifi, conference LAN, corporate guest network, AirDrop-discoverable Bonjour.

---

### G-CONSTELLATION-3: No TLS; payload in cleartext over the network

**Where:** `src/constellation.py` HTTPServer; `httpx.post(...)` without `https://` schemes in `cfg["memberships"][...]["peers"][...]["endpoint"]`.

**Observation:** Memory content travels in HTTP body unencrypted. A network observer (anyone on the same Layer-2 segment on unencrypted wifi, anyone in the path on routed networks) can read all shared memories.

**Scale trigger:** any deployment beyond a single trusted LAN.

---

### G-CONSTELLATION-4: Push fan-out is O(peers × memories) sequential HTTP

**Where:** `src/constellation.py:673-726` — nested loops, `httpx.post(...)` synchronous.

**Observation:** For N peers and M memories, push does N×M sequential HTTP calls. At 5 peers × 100 memories × 50ms = 25s. No batching, no parallelism, no streaming.

**Scale trigger:** bulk catch-up after offline period. Daily-end push of ~30 memories to 5 peers ≈ 7.5s — already user-visible latency.

---

### G-CONSTELLATION-5: `httpx.post` is synchronous; blocks the gateway HTTPServer thread

**Where:** `src/constellation.py:702` — `resp = httpx.post(...)` (note: `httpx.post`, not `await client.post`).

**Observation:** The gateway handler thread is occupied for the duration of the entire push fan-out. While push runs, no other gateway operations (other group_push, group_pull, status checks) can be served. Combined with G-CONSTELLATION-1, push is a global single-writer lock.

**Scale trigger:** any concurrent operation during push.

---

### G-CONSTELLATION-6: `PULL_LIMIT_DEFAULT = 256` returns one page; no automatic paging

**Where:** `src/constellation.py:61` — `PULL_LIMIT_DEFAULT = 256`; `_handle_memory_since` returns exactly one page.

**Observation:** Pulling from a peer with >256 new memories since last cursor returns the first 256 (sorted by `submitted_at`). Subsequent pulls need to re-issue with an advanced cursor. The current `_handle_pull` does *not* loop on the cursor — it issues one `/memory/since` per peer and moves on.

**Scale trigger:** any peer that's been offline >2-3 days with active sharing. Catch-up never completes in a single pull; user must re-issue `/remember pull` until convergence.

---

### G-CONSTELLATION-7: No retry queue for offline peers

**Where:** absent — `_handle_push` (`src/constellation.py:678-726`) handles each peer's outcome inline. On `unreachable`, the result is "best effort, you're on your own."

**Observation:** If peer B is unreachable when peer A pushes memory M, M is *not* queued for redelivery. M still lives on A; B will get it on the next pull from B's side. But if B never initiates a pull (Claude session not started, machine asleep), M's propagation stalls indefinitely.

**Scale trigger:** any peer that doesn't run Claude regularly. The "always-on" peers carry the corpus; the "occasional" peers fall behind silently.

---

### G-CONSTELLATION-8: No payload signing; no replay protection

**Where:** `src/constellation.py:_handle_memory_put` (266-356).

**Observation:** The receive path validates `content_hash` matches the SHA-256 of `content` — that detects in-transit modification of content. But the `content_hash` itself isn't signed. An attacker rewriting both `content` and `content_hash` passes. There's also no nonce / sequence number to prevent replay; the same `/memory/put` body can be replayed indefinitely (effectively a no-op due to dedup, but observable as repeated "duplicate" responses, exploitable as denial-of-service or as a probe for what content is stored).

**Scale trigger:** any adversary on the network path.

---

### G-CONSTELLATION-9: `origin_node` is sender-asserted, not authenticated

**Where:** `src/constellation.py:341` — `"origin_node": body["origin_node"]` taken verbatim from POST body.

**Observation:** When peer A pushes a memory claiming `origin_node = "B"`, the receiver records it as if it came from B. Loopback prevention (the receiver skipping memories it originated) relies on this same field. An attacker could push memories *appearing* to come from any node name, corrupting cross-machine recognition.

**Scale trigger:** any malicious peer in a group. Subverts the entire mesh's notion of who-said-what.

---

### G-CONSTELLATION-10: Corporate-Mac EDR (CrowdStrike Falcon, ThreatLocker) blocks inbound HTTP

**Where:** environmental, not code — observed empirically on `tk421-*` Macs.

**Observation:** Constellation's peer surface requires inbound HTTP. Corporate EDR commonly blocks inbound listeners as a default-deny policy. The affected Macs become *outbound-only* — they can pull, they can push to peers, but they cannot *receive* pushes or answer pull requests.

**Scale trigger:** any corporate-owned device. This is *the* trigger that drove the v0.5 connector pivot — but Constellation's transitional role still hits it.

## 5. Slack Connector (v0.5)

### G-CONNECTOR-1: Slack `chat.postMessage` rate limit ~1/sec sustained

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §10`.

**Observation:** Bulk push of 100 memories takes ~100 seconds. No 429 backoff handling specified; the connector blocks on Slack's rate-limiter response. No queueing / streaming UI for the user during the wait.

**Scale trigger:** any bulk operation. Onboarding a new machine into the connector mesh requires pushing every memory; for a 500-memory store, that's >8 minutes of channel pollution.

---

### G-CONNECTOR-2: 40 KB Slack message body ceiling rejects large memories

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §5.4`, push-side 38 KB guard.

**Observation:** Memories with content >~30 KB (combined with vector ~6 KB + metadata ~2 KB) exceed Slack's message-body limit. The push returns `{"status": "error", "reason": "memory exceeds Slack message body limit"}` and the memory becomes unsharable through that connector.

**Scale trigger:** long-form memory content (transcripts, documents, multi-page decisions). Currently no fallback.

---

### G-CONNECTOR-3: Slack workspace history retention may delete memories silently

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §10`.

**Observation:** Free tier: 90 days. Paid: workspace-dependent. Catch-up after offline period exceeding retention silently misses memories. Pull's loopback + content_hash dedup checks don't compensate — the memories are gone from Slack.

**Scale trigger:** any free-tier workspace + any user offline >90 days. Memory loss without notification.

---

### G-CONNECTOR-4: Slack token expiry mid-pull has no resume

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §12.4`.

**Observation:** Token refresh is interactive (Claude's MCP auth layer). Mid-pull 401 causes the operation to halt. No cursor advance — the user reauths, re-runs, and starts the pull from the prior cursor. Memories between the cursor and the moment of failure are silently re-read on retry (dedup catches it, but bandwidth/time wasted).

**Scale trigger:** long-running pulls. Token TTL in some Slack OAuth flows is hours; pulls >token-TTL fail mid-stream.

---

### G-CONNECTOR-5: Per-machine cursor; no coordination across machines reading the same connector

**Where:** to be implemented per `docs/v0.5_CONNECTOR_ARCHITECTURE.md §6.4`.

**Observation:** Each machine on the connector maintains its own `submitted_at`-derived cursor in `~/.local/share/mem-fusion/connector_cursors.json`. Three machines watching the same connector all read all messages independently. With content_hash dedup the storage cost is bounded, but Slack API quota is consumed 3× and embed cache hits are 3× duplicated.

**Scale trigger:** team-scale deployments where many peers watch the same connector for a common stream.

---

### G-CONNECTOR-6: Workspace data residency — sensitive content sits in Slack

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §13`.

**Observation:** Memory content is encrypted in Slack's at-rest storage (per Slack's posture) but is plaintext-visible to anyone in the channel and to Slack itself. No client-side encryption. No content classification telling users "don't push this kind of memory."

**Scale trigger:** any deployment where sensitive content (credentials, PII, IP-restricted data) might be tagged with a connector. Currently no guardrails.

---

### G-CONNECTOR-7: No multi-machine same-channel pull coordination

**Where:** to be implemented.

**Observation:** If five machines all pull `#mem_fusion_engineering` independently, they each issue `slack_read_channel(oldest=<their_cursor>)`. There's no coordination, no "I already pulled batch X." 5× redundant Slack API calls; 5× redundant pull-side embed cache work.

**Scale trigger:** large teams sharing a connector channel.

---

### G-CONNECTOR-8: Vector inline in JSON bloats wire format ~6 KB per memory

**Where:** `docs/v0.5_CONNECTOR_ARCHITECTURE.md §5.4` notes "768-dim float array ~6 KB."

**Observation:** Every Slack message carries the 768-dim float vector in JSON (typical Python repr: ~6 KB). Alternative would be receive-side re-embed (saves bandwidth, costs ~25ms-per-memory pull CPU + Ollama dependency on the receiver).

**Scale trigger:** bandwidth-constrained connectors (lower-tier Slack plans throttle on cumulative message size; mobile-network receivers).

---

### G-CONNECTOR-9: Channel rename or archive breaks `connector.json` reference

**Where:** documented in `docs/v0.5_CONNECTOR_ARCHITECTURE.md §13`.

**Observation:** Connector references the Slack channel by *name string*. A rename or archive in Slack silently breaks the connector. The status check would surface the failure on the next pull/push, but autodiscovery / heal is absent.

**Scale trigger:** team reorganization, channel rename hygiene, archival policies.

---

## 6. Hooks (Shell + Python)

### G-HOOK-1: Cold Python subprocess invocation per UserPromptSubmit

**Where:** `src/scripts/prompt_memory_inject.sh` — Pass 1 + Pass 2 each spawn `$VENV - <<PYEOF`.

**Observation:** Every user prompt fires the hook, which spawns *two* fresh Python processes (Pass 1 and Pass 2). Cold-start time per Python process: ~150-400ms (import httpx, qdrant_client, asyncio, build module graph). Total hook overhead per prompt: ~400-1000ms.

**Scale trigger:** every Claude turn. Cumulative across a session: dozens to hundreds of seconds of pure hook startup overhead.

---

### G-HOOK-2: `SEEN_FILE` and `LAST_TS_FILE` per-session state grows unbounded

**Where:** `src/scripts/prompt_memory_inject.sh:13-14` — `${QUEUE}/seen-${SESSION_ID}.txt`, `${QUEUE}/last-prompt-ts-${SESSION_ID}.txt`.

**Observation:** New file per Claude session. SEEN_FILE accumulates one memory ID per prompt (Pass 1 dedup). No cleanup mechanism. With Claude sessions counted in the thousands over months, the `queue/` directory grows without bound.

**Scale trigger:** long-lived install. After 1000 sessions: ~2000 files, none cleaned.

---

### G-HOOK-3: Pass 2 `search_recent(hours=24, top_k=100)` on every prompt

**Where:** `src/scripts/prompt_memory_inject.sh` Pass 2 — `core.search_recent({"hours": 24, "top_k": 100})`.

**Observation:** Every user prompt does a `qdrant.scroll` over the last-24h memories, limit 100. For users with high memory creation rates, this scan returns 100 memories every time; the Python-side filter then re-checks `received_at` and `origin_node`. Linear in returned-memories count per prompt.

**Scale trigger:** active users with >100 memories/day. Pass 2 starts returning a saturated 100-memory page and the filter does most of the work in Python.

---

### G-HOOK-4: No mutex on `LAST_TS_FILE`; concurrent prompts race

**Where:** `src/scripts/prompt_memory_inject.sh` Pass 2 — read-then-write of `LAST_TS_FILE` not atomic.

**Observation:** If a user's session spawns sub-agents that submit prompts concurrently (Task tool, parallel agents), two Pass 2 invocations may both read the old timestamp, both write a new one. The interleaving is benign for correctness (worst case: a memory is mentioned twice) but the file write order is undefined.

**Scale trigger:** parallel Claude sub-agents. Currently a low-frequency scenario but on the v0.6 roadmap.

---

### G-HOOK-5: No structured logging or error path

**Where:** `src/scripts/prompt_memory_inject.sh` — Python failures inside the heredoc print to stderr, which Claude doesn't surface to the user.

**Observation:** If a Pass 2 query fails (Qdrant down, Ollama hung), the user never sees an error. The hook silently produces no `<received_memories>` block; the user assumes there's just nothing new.

**Scale trigger:** any operational degradation. Silent failure mode.

---

## 7. Security & Authentication

### G-SECURITY-1: Constellation peer endpoint has no authentication

**See G-CONSTELLATION-2.** Group_name membership check is necessary but not sufficient.

---

### G-SECURITY-2: Qdrant and Ollama have no authentication

**See G-STORAGE-9 and G-EMBED-5.** Localhost binding is the only ACL.

---

### G-SECURITY-3: No payload signing; integrity check is hash-only

**See G-CONSTELLATION-8.**

---

### G-SECURITY-4: `origin_node` and `submitted_at` are sender-asserted

**See G-CONSTELLATION-9.** Trust model: peers don't lie. Currently no cryptographic identity per peer.

---

### G-SECURITY-5: No content classification or sensitivity tagging

**Where:** mem-fusion has `importance` (1-5) but no `sensitivity` / `classification`.

**Observation:** A user pushing a memory tagged with the `engineering` connector might be pushing credentials, customer data, or unrestricted shop talk — the system has no way to distinguish. No guardrails against pushing sensitive content into a Slack workspace that has third-party guest access, for example.

**Scale trigger:** any deployment where mem-fusion is used across audiences with different access controls.

---

### G-SECURITY-6: Slack token compromise gives connector write access

**Where:** Slack OAuth lives in Claude's MCP auth layer, not mem-fusion.

**Observation:** If Claude's Slack token is exfiltrated, an attacker can post arbitrary `[mem-fusion 0.5]`-prefixed messages to any connector channel the token has write access to. The receiver's loopback check (`origin_node == self`) skips them on the *origin* machine, but every other peer ingests them as legitimate memories.

**Scale trigger:** any token-leak event. Trust is workspace-level.

---

### G-SECURITY-7: Hook scripts execute untrusted Python via venv subprocess

**Where:** `src/scripts/prompt_memory_inject.sh` — `$VENV - <<PYEOF`.

**Observation:** The hook injects Python code into a here-doc, expands shell variables (including `$PROMPT`), and pipes the result into Python. The expansion `${PROMPT//\"/\\\"}` is a quote-escape attempt, but doesn't fully sandbox. A user prompt containing a Python-escape sequence could in principle alter what Python executes.

**Scale trigger:** maliciously crafted user prompts or prompts injected through compromised MCP servers. Low real-world frequency but a real vector.

## 8. Consistency

### G-CONSISTENCY-1: Eventually consistent; no global ordering

**Where:** absent — by design.

**Observation:** Cross-machine ordering of memories is per-origin-node `submitted_at`. There's no global sequence number. Two memories submitted at the same instant from different machines arrive in undefined order at receivers.

**Scale trigger:** any workflow that depends on ordering ("most recent decision wins"). Currently undefined.

---

### G-CONSISTENCY-2: Deletes are local-only; no tombstone propagation

**Where:** `src/core.py:516-519` — `delete_memory` does `qdrant.delete` locally.

**Observation:** A `delete_memory` on machine A doesn't propagate. Machine B still has the memory and will re-push it on its next `group_push` (the entry is still tagged with the group). Net effect: the user "deletes" a memory and it reappears on the next sync.

**Scale trigger:** any genuine retraction. "I shared a memory I shouldn't have" cannot be undone.

---

### G-CONSISTENCY-3: `upsert_memory` doesn't propagate; concurrent edits split

**Where:** `src/core.py:444-472` — local upsert only.

**Observation:** Edit memory M on machine A → A's content and content_hash change. Machine B still has M's original. On A's next `group_push`, M's new content has a *new* content_hash → B receives it as a separate memory. The mesh now has two divergent versions.

**Scale trigger:** any collaborative editing pattern.

---

### G-CONSISTENCY-4: `envelope_version: 1` reserved but not enforced at storage

**Where:** `src/core.py:333` and `constellation.py:333` — payload structure has no `envelope_version` field on stored entries; only the connector wire format carries it (`docs/v0.5_CONNECTOR_ARCHITECTURE.md §5.1`).

**Observation:** Stored memories have an implicit "v0.4 payload shape." There's no versioning at the Qdrant payload level. If the schema changes in v0.6, a migration script is needed, but the current state can't even be queried as "what version are these entries on."

**Scale trigger:** any schema evolution.

---

## 9. Operational

### G-OPS-1: No backup or restore

**See G-STORAGE-6.**

---

### G-OPS-2: Log files grow unbounded; no rotation

**Where:** `src/core.py:111-115` — `<LOG_DIR>/<component>.<timestamp>.log`, no rotation, no retention policy.

**Observation:** Every daemon startup creates a new log file. No log rotation, no compression, no cleanup. Multi-month runs accumulate hundreds of log files.

**Scale trigger:** long-running deployments. After 6 months: log directory in the tens-of-thousands of files.

---

### G-OPS-3: No structured logging or metrics

**See G-MCP-4.**

---

### G-OPS-4: No health-check loop for Qdrant + Ollama

**Where:** absent. Failures surface only when an MCP call tries to use them.

**Observation:** If Qdrant or Ollama crashes (OOM, disk full, segfault), the MCP server doesn't notice until the next request fails. No restart attempt; no user notification.

**Scale trigger:** long-running daemons. Mean-time-to-discovery for backend failure is "the next time a user asks Claude to do something."

---

### G-OPS-5: No inventory of which fix scripts have been applied per machine

**Where:** `src/scripts/fixes/` — scripts are idempotent but no inventory file.

**Observation:** Each fix script self-detects whether it needs to run. But there's no central "what's the current fix-level of this machine" answer. Auditing version drift across the mesh requires running each fix and reading its "already applied" output.

**Scale trigger:** larger meshes with version drift across machines.

---

### G-OPS-6: Configuration drift across machines

**Where:** `~/.local/share/mem-fusion/` per-machine local config; no canonical source.

**Observation:** Qdrant config, Ollama plist, constellation config, hook scripts — all live per-machine. Changes to defaults in the repo require manual application via fix scripts on each machine. The architect-machine and engineer-machine can run different configurations indefinitely.

**Scale trigger:** any multi-machine deployment. Currently we manage this manually with fix scripts; a mesh with >5 machines won't.

---

### G-OPS-7: No disaster-recovery / mesh-resync primitive

**Where:** absent.

**Observation:** If machine A's local Qdrant is destroyed, there's no "rebuild from peers" command. A must run `group_pull` for every group it's a member of, hoping peers carry the missing content. Memories that A originated and never got pushed (e.g., personal-only memories before peers were configured) are lost permanently.

**Scale trigger:** disk failure on any machine.

---

## 10. Multi-Tenant

### G-MULTITENANT-1: Single-user assumption pervades

**Where:** `src/core.py:44` single collection; no user_id in payload; `~/.local/share/mem-fusion/` per-machine-user but shared across same-machine processes.

**Observation:** mem-fusion assumes one user per machine. Shared workstations, classroom computers, or multi-tenant servers can't isolate memories per user. The "team" mental model assumes each user has their own machines.

**Scale trigger:** any shared-host deployment.

---

### G-MULTITENANT-2: No per-project isolation at the storage layer

**Where:** `project` is a payload field, used as a filter (`src/core.py:283`) — not a namespace.

**Observation:** All projects share the same Qdrant collection. A search without a `project` filter returns memories across all projects the user has stored. There's no enforced isolation; "leak across projects" is purely a query-discipline question.

**Scale trigger:** users with strict per-client / per-project isolation requirements (consultants, contractors, agencies).

---

### G-VERSION-1: Single envelope version; no negotiation

**See G-CONSISTENCY-4.**

### G-VERSION-2: Wire format changes break old peers

**Where:** `src/constellation.py:_handle_memory_put` (266-356) — required fields enumerated as a fixed set.

**Observation:** Adding a required field to `/memory/put` breaks older peer versions. Currently all peers must run the same Constellation version. No version handshake.

**Scale trigger:** any deployment that lags behind head by more than one fix. Currently survivable because the deployment is 4 machines, all hand-managed.

**Bottlenecks that bite earliest (architect's read; engineer to confirm or rebut):**

1. **G-CONSTELLATION-1 + G-CONSTELLATION-5** — single-threaded HTTPServer + synchronous push fan-out. Becomes user-visible latency at the 5-peer × 100-memory scale.
2. **G-HOOK-1** — cold Python subprocess per prompt. Bites every Claude turn at any deployment scale.
3. **G-EMBED-2** — soft truncation at 8000 chars. Already flagged in 0.5.0-007 CHANGELOG note; chunked-embedding architecture pending.
4. **G-STORAGE-1** — 10⁴ scroll limit. Quietly miscalibrates `last_stored` and pull cursors at moderate scale.
5. **G-CONSISTENCY-2 + G-CONSISTENCY-3** — local-only deletes and split-brain edits. Erodes trust in the mesh once users realize.

**Bottlenecks that bite latest but bite hardest:**

1. **G-CONSTELLATION-2 + G-CONSTELLATION-9** — no peer authentication, sender-asserted origin_node. Breaks trust model the moment the mesh crosses an untrusted network. Currently mitigated by LAN-only deployment posture; the moment an attacker is on the same coffee-shop wifi, full memory exfiltration and content injection.
2. **G-OPS-7** — no disaster recovery. Single disk failure → permanent loss of any memories not propagated to peers.
3. **G-CONNECTOR-3** — Slack history retention. Silent data loss at the 90-day boundary on free-tier workspaces.

**Cross-cutting themes:**

- **Single-process / single-machine assumptions** in core.py and the hook scripts. Caches, cursors, and state are per-instance; coordination across instances is absent.
- **Trust model is "LAN with non-adversarial peers"** — multiple gaps fall away once that's the operating assumption, but the assumption fails for any deployment beyond a home network or trusted office.
- **Silent failure modes** — multiple paths return errors that callers may not surface (G-HOOK-5, G-STORAGE-1's stats miscalibration, G-CONNECTOR-3's retention drop). User trust erodes faster from silent failures than from loud ones.
- **No observability** — almost every operational gap above is harder to diagnose without metrics/traces/structured logs (G-MCP-4, G-OPS-3, G-OPS-4). Engineer may want to address observability *before* tackling individual gaps so we can measure remediation impact.

# v0.5 — First-Pull Semantics Spec

**Status:** PROPOSED · awaiting architect review
**Author:** Claude-Engineer (mc-macbookair) · 2026-05-17
**Targets:** mem-fusion v0.5+ (primarily SlackConnector; generalizable to all connectors)
**Audience:** mc-macbookpro (architect) for review

---

## 1. Why this spec exists

`/remember pull <connector>` has well-defined behavior on the steady-state path — there's a per-connector cursor (e.g., last Slack `ts` we've ingested), the connector queries for messages newer than the cursor, and the result is small and incremental.

But the **first** pull from a connector has no cursor. What should happen?

- Fetch **all** of the channel's history? On a Slack channel that's been collecting memories for six months, that's potentially thousands of messages. Rate-limited (Slack Tier 2 = 50 req/min for chat-pagination calls). Could take minutes. Might race with concurrent activity.
- Fetch only **recent** messages (last N, last 24h, …)? Cheap, but the user joining a team mid-stream wants the team's accumulated knowledge, not just yesterday's.
- Fetch **nothing**, force user to explicitly opt-in to a back-fill operation? Conservative, deterministic, but a bad new-user experience: the connector appears to "work" but the local store stays empty until the user runs an unfamiliar follow-up command.

The architect's lean per `0daf2f0c` was: *"fetch-all-history with progress UI"*. This spec proposes the concrete semantics, pagination, rate-limit strategy, progress signals, and failure modes.

---

## 2. Current state (v0.4 / pre-spec)

- v0.4 Constellation pull: each request asks `GET /memory/since?group_name=G[&cursor=X]`. With cursor unset, it returns up to `limit=10000` entries (per 0.5.0-013) — effectively the whole group, full-scan. No "first-pull is special" branch. The bound is the limit.
- v0.5 SlackConnector design (per `docs/v0.5_CONNECTOR_ARCHITECTURE.md` §6.2): the architecture doc sketches pull as "scan since cursor, filter for mem-fusion marker, parse envelope, dedup by content_hash, store." But for the no-cursor case, §6.2 is silent on the time window and pagination strategy.

This spec fills that gap.

## 3. Proposed semantics

### 3.1. Behavior decision matrix

| Cursor state | Connector type | Behavior |
|---|---|---|
| Cursor exists (steady-state pull) | Slack | `slack_read_channel(channel, oldest=cursor)` — fetch all messages newer than cursor. Apply pagination as needed. |
| Cursor exists | Constellation HTTP | Already covered by 0.5.0-013: full-scan group, dedup on receive. No spec change needed here. |
| **No cursor (first pull)** | Slack | **Fetch full available channel history, oldest-first.** Bounded by Slack's per-channel retention (typically 90d on Free, longer on Standard/Plus). No artificial age-cutoff applied by mem-fusion. |
| No cursor | Constellation HTTP | Same as steady-state (full-scan + dedup) — Constellation doesn't track cursors anyway post-0.5.0-013. |

### 3.2. Why "fetch full available history" for first-pull Slack

Three reasons:

1. **Onboarding completeness.** A user joining the team's mem-fusion Slack channel expects to ingest the team's accumulated memory. "Last 24h" returns a sliver; the user would have to figure out the back-fill incantation. Hostile to new users.
2. **Cost is bounded.** Slack's retention is the cap — mem-fusion can't request what Slack has discarded. On Free-tier workspaces this is 90 days × team-size memory-rate, on paid tiers it's longer but still bounded.
3. **Idempotent.** content_hash dedup ensures re-pulling a fully-back-filled channel is cheap (every message hashes to something we already have → skip). So the cost of "first pull" is one-time per fresh local store.

### 3.3. Pagination

Slack's `conversations.history` API returns up to 1000 messages per page, oldest-first when invoked with `oldest=0` and `inclusive=true`. The connector should:

```
cursor = None     # Slack pagination cursor, not our memory cursor
total  = 0
page_n = 0
while True:
    response = slack_read_channel(channel, oldest=memory_cursor or 0, cursor=cursor)
    for msg in response.messages:
        if has_mem_fusion_marker(msg):
            envelope = parse(msg)
            if envelope.content_hash not in local_store:
                store_memory(...)
                total += 1
    cursor = response.next_cursor
    page_n += 1
    progress_update(total, page_n)
    if cursor is None:
        break
    rate_limit_yield()
```

### 3.4. Rate-limit strategy

Slack Tier-2 limits (`conversations.history` is here): **50 calls per minute** per app per workspace (50 req/min sustained, short bursts allowed up to ~100 req/min).

With 1000 messages per page, 50 pages/min = 50,000 messages/min ≈ 833 messages/sec. The wall-clock bound for a back-fill is determined by `total_history_size / 50000 + parse-cost + qdrant-upsert-cost`.

Connector behavior:

- **Respect Slack's `Retry-After` header** if returned. Slack sends `429` with this header on rate-limit hits; sleep for the indicated duration and continue.
- **Inter-request floor of 1.2 seconds** to comfortably stay under 50/min. Most channels won't need 50 pages; the inter-request delay is invisible.
- **Per-page upsert batch.** Don't call `qdrant.upsert` per-message; batch each page's 1–1000 messages into one upsert call.

### 3.5. Progress signals

`/remember pull <connector>` returns telemetry that Claude renders as prose. For first-pull, the shape is augmented to surface progress:

```
{
  "connector":      "<id>",
  "first_pull":     true,
  "pages_fetched":  N,
  "messages_seen":  M,
  "stored":         S,
  "duplicates":     D,
  "elapsed_sec":    T,
  "status":         "complete" | "interrupted" | "rate_limited"
}
```

For long back-fills (>30s), the connector should also stream interim progress to a log file at `~/.local/share/mem-fusion/logs/connector_first_pull-<id>-<ts>.log` so the user can `tail -f` if they're impatient. Claude doesn't surface those interim updates in conversation (would clutter); it just narrates the final result.

### 3.6. Idempotency under interruption

If a first-pull is interrupted (network drop, Slack outage, Claude Code restart), the partial pull commits whatever it has stored so far. On the next `/remember pull <connector>`, the system:

1. Checks the local store: is there a successfully-set cursor for this connector? If yes → steady-state pull (use cursor).
2. No cursor → re-attempt first-pull. Re-fetches from the channel start, but content_hash dedup means already-stored memories skip cheaply.

This means **the cursor is set ONLY at first-pull completion**, not incrementally. If we set it incrementally, a mid-way interruption would leave the cursor at "halfway-back-filled" and the next pull would miss the older half. Setting it only on success guarantees re-attempt safety at the cost of redundant work on interrupted retries — acceptable because dedup is cheap.

## 4. Failure modes

| Failure | Detection | Connector response |
|---|---|---|
| Slack auth missing / expired | `not_authed` / `invalid_auth` from API | Return `{error: "slack_auth_required", detail: ...}`. Don't retry. |
| Channel not found / not joined | `channel_not_found` | Return `{error: "channel_not_accessible", detail: ...}`. Suggest user invite the connector's bot user. |
| Rate-limit hit | HTTP 429 + `Retry-After` | Sleep + retry, up to 3 backoff cycles. Then return `{error: "rate_limited_sustained", retry_after: ts}`. |
| Partial completion (network drop) | Exception during page fetch | Don't set cursor. Return `{first_pull: true, status: "interrupted", stored: N, ...}`. User re-runs `/remember pull <connector>` to resume from the start (cheap via dedup). |
| Parse failure on a message | Per-message `try/except` inside the loop | Skip + log. Don't fail the whole pull on one malformed envelope. Return a count of skipped messages. |

The general principle: **fail loudly on auth/access errors (user needs to fix); fail soft on per-message errors (the channel will keep working); never partially-commit cursor state**.

## 5. Migration / back-compat

- **First pull of a connector that was just declared** — covered above.
- **A user wipes their local mem-fusion store and re-pulls** — same as first-pull. The channel still has its history; dedup is moot because the local store is empty. Full back-fill again.
- **A connector's `channel` value is changed in `connector.json`** — treat as a new connector (different channel, no cursor for this combination). First-pull semantics apply. The old connector's cursor lingers in `connector_cursors.json` but is harmless; could be GC'd on next config-load.
- **Constellation pull behavior is unaffected.** This spec is connector-oriented; Constellation's full-scan-on-every-pull (post-0.5.0-013) doesn't have a first-pull distinction.

## 6. Open questions for architect

1. **First-pull cap / opt-out?** Should there be an environment variable or config knob to limit first-pull to N messages or M days? Adds complexity but lets users on huge channels do a measured back-fill. Default: no cap (full history). Knob name: `first_pull_max_age_days` on the connector entry?
2. **Bot-user invite for non-public channels?** If the user declares a connector pointing at a private channel, the Claude Slack MCP may not have access. Should the connector pre-flight-check membership and produce a helpful error message? Or just bubble Slack's API error? Recommend pre-flight check with a clear "invite required" message.
3. **Streaming interim progress to Slack itself?** Some installs might want a "first-pull progress" message posted to a different Slack channel (or DM the user) for visibility. v0.5 scope: log to local file only; no Slack-posted progress. Revisit if user feedback wants it.
4. **Parallel first-pull across connectors?** A user with three Slack connectors running their first-pull from `/remember pull` (bare, no arg) — sequential or parallel? Slack rate-limit is per-app, so parallel pulls share the budget; sequential keeps it simple. Recommend sequential for v0.5.
5. **What about non-Slack connectors when their day comes?** GDrive doesn't have a Slack-shaped `oldest` cursor; its semantics differ. The spec here is Slack-specific in detail. Should §3 generalize to "first-pull is connector-implementation-defined" and Slack becomes the reference implementation? Recommend yes; defer the generalized contract to v0.6 when a second connector type starts being designed.

---

## 7. Out of scope

- **Search-driven pulls** (e.g., `/remember pull <connector> --query=<text>`). v0.5 is bulk-pull only.
- **Cross-connector memory deduplication beyond content_hash.** Different connectors targeting the same Slack channel via different bot identities is an anti-pattern; we don't try to handle it.
- **Bidirectional reconciliation** during first-pull (we read everything from Slack and only then push our local memories). v0.5 is read-only for first-pull; subsequent steady-state pulls don't push. Push is always an explicit user action.
- **Encrypted-channel content.** If users encrypt mem-fusion message bodies, the connector still passes them through opaquely; content_hash is computed over the plaintext where available, ciphertext otherwise. Out of scope for v0.5.

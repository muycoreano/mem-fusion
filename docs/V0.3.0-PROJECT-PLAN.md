**Date:** 2026-05-12
**Status:** Active plan; v0.3.0 = MVP completion
**Versioning:** v0.3.0 is the MVP. Anything not in this plan is post-MVP — deferred with no commitment to specific release timing. Capabilities get scoped as real usage surfaces specific needs.

## What changed in this revision (2026-05-12)

Four corrections, plus the substantial **synchronization architecture** now in scope. In order of impact:

1. **Synchronization is in scope for v0.3.0.** Per `docs/CONSTELLATION_ARCHITECTURE.md` §5 (added 2026-05-12), v0.3.0 ships a pull-primary sync model: `GET /memory/since` (lightweight count check), `GET /memory/get?since=...` (incremental fetch with microsecond-precision `received_at` watermark), peer-side state file (`peer_state.json`), auto-promote behavior in `store_memory` (the v0.3.0 default), promotion queue with cap-100 + drain logic, peer-side scheduler (`constellation_pull.py` + launchd plist), four new MCP tools (`check_new`, `pull_new`, `sync_status`, `sync_now`), and SessionStart-hook integration for surfacing pending counts. **Push notifications (subscribe + webhook) are deferred (post-MVP)** — only the pull half is in v0.3.0 scope. This is two new work packages: **WP4d (sync pull infrastructure)** and **WP4e (auto-promote + promotion queue)**.

2. **WP4a + WP4b shipped 2026-05-12 in commit `f6274b0`.** Repo restructured to `src/` as source-of-truth; INSTALL files (`INSTALL_MEM_FUSION.md`, `INSTALL_CONSTELLATION.md`) generated by `build_install.sh` packager. Two daemons (`mem_fusion.py`, `constellation.py`) are peer components in `src/`; no more `extensions/`. The packaging pattern is documented in two new memories (file-based + vector DB) for general application to future Claude extensions.

3. **WP5 (Claude bridge) is restructured — much smaller.** The 2026-05-11 plan had WP5 as the "dual-call pattern" (`store_memory` → `export_record` → `constellation/memory/put` orchestrated by CLAUDE.md). Auto-promote in WP4e eliminates the dual-call entirely: `store_memory` returns `promoted_to[]` after fanning out internally. WP5 becomes the CLAUDE.md snippet that teaches Claude to interpret `promoted_to[]` and surface group-memory state — ~30 min of work, not 1 hr of orchestration plumbing.

4. **WP6 scope expanded to cover sync.** Beyond the prior four scenarios (basic propagation, cross-peer query, dedup, vector preservation), WP6 now also tests: cold-boot pending-count surfacing, polling cycle, orchestrator-offline behavior (queue accumulates, drains on recovery), queue-full at 100 entries, failure surfacing in `store_memory` response. The auth-related scenarios (5/6) remain deferred to post-MVP.

5. **Carries forward from prior revision:** auth/security deferred to post-MVP (commit `b10bed4`); semantic search (WP4c) still pending. (`tests/` directory now formalized; `dev/` deferral resolved.)

### WP4d — Sync pull infrastructure 🚧 NOT STARTED

**Goal:** Implement the pull half of the synchronization protocol per `docs/CONSTELLATION_ARCHITECTURE.md` §5. Peers detect new canonicals via a lightweight count + incremental fetch via watermark; the local peer maintains state and runs a background scheduler.

**Scope (orchestrator side):**
- `GET /memory/since?group_name=X&since=<iso>` — lightweight count check with microsecond-precision `received_at` watermark (per §5.2).
- `GET /memory/get?group_name=X&since=<iso>` — incremental fetch, sorted ascending by `received_at`.

**Scope (peer side):**
- `<state_dir>/peer_state.json` — schema per §5.5: `last_synced_at`, `last_check_at`, `pending_count`, `orchestrator_reachable`, `consecutive_failures`, `last_failure_at`, `last_failure_reason`. Atomic write.
- `src/scripts/constellation_pull.py` — runs the pull cycle: read state → call `/memory/since` → if count>0, call `/memory/get?since=...` → upsert into local `mem_fusion_memories` (canonical_id as point id; tag with `source=constellation-pull`, `group_name`, `origin_node`).
- `src/launchd/com.branchapp.memfusion.constellation-pull.plist` — `RunAtLoad=true`, `StartInterval=poll_interval_seconds` (default 30s).
- Peer-side MCP tools: `constellation/check_new`, `constellation/pull_new`, `constellation/sync_status`, `constellation/sync_now` (per §5.11).
- Mem-Fusion SessionStart hook extension: read `peer_state.json` + queue dir, surface "N new in group X" or "orchestrator unreachable for M minutes" in the `<memfusion_status>` block.

**Config additions** (per §5.1):

```json
{
  "sync": {
    "mode": "manual" | "poll",
    "poll_interval_seconds": 30,
    "auto_apply": true,
    "failure_verbosity": "verbose"
  }
}
```

**Deliverables:**
- Daemon: ~50 lines for `/memory/since` + `/memory/get?since=` extension
- Peer scheduler: ~150 lines (`constellation_pull.py`)
- Peer launchd plist: ~30 lines XML
- MCP tools: ~80 lines (4 tools)
- SessionStart hook extension: ~30 lines
- Test: `tests/constellation/test-sync-pull.py` — cold-boot (no watermark), incremental pull, orchestrator-unreachable behavior, peer state file updates correctly

**Success criteria:**
- Peer-c with no `last_synced_at` calls `pull_new` → fetches all canonicals in the group → advances watermark to `max(received_at)`.
- Peer-b adds memory X → peer-c's next poll detects `count=1` → pulls X → applies to local store → `search_memory` finds X tagged `source=constellation-pull`.
- Orchestrator down → peer's `check_new` records `orchestrator_reachable=false`; SessionStart surfaces "unreachable for N min".
- Watermark precision: microsecond-level — no missed memories on sub-second sync cadence.

**Stop point:** Peer sync works. New memories propagate via polling. State is durable across reboots.

### WP4e — Auto-promote + promotion queue 🚧 NOT STARTED

**Goal:** Implement the auto-promotion side of the sync protocol per §5.6–§5.9. `store_memory` on a peer that's a group member fans out to the orchestrator automatically; failures queue and retry.

**Scope:**
- Mem-Fusion `store_memory` extended: after local store succeeds, if `auto_promote: true` AND group memberships exist, attempt `POST /memory/put` to each group's orchestrator.
- Response includes `promoted_to: [{group_name, status, canonical_id? | reason?}]` per group — surfaces every outcome for v0.3.0 / post-MVP instrumentation phase.
- Queue at `<state_dir>/queue/<group>/<timestamp>-<content_hash>.json` per §5.7. File format includes `memory_record`, `provenance`, `attempt_count`, `last_attempt_at`, `last_failure_reason`.
- Drain logic in `constellation_pull.py` (same scheduler that runs pull). Every cycle, scan queue, attempt POST. 200 → delete file. 4xx → move to `queue/failed/<group>/`, log, surface in next SessionStart. 5xx / network → leave, retry next cycle.
- Queue-full behavior: cap at 100 per peer. New promotions when full → `status: "queue_full"` in `store_memory` response; local memory still stored.
- Failure surfacing: `peer_state.json` records `consecutive_failures`, `last_failure_reason`; `<state_dir>/logs/peer-client.log` continuous append.

**Config additions** (per §5.1):

```json
{
  "sync": {
    "auto_promote": true,
    "failure_verbosity": "verbose"
  }
}
```

`failure_verbosity` is fixed at `verbose` for v0.3.0–post-MVP (always communicate failures); configurable in a future version once stability is empirically demonstrated.

**Deliverables:**
- Mem-Fusion `mem_fusion.py` change: `store_memory` extended with fan-out logic (~80 lines)
- Queue helpers in `constellation_pull.py` (~100 lines added)
- Test: `tests/constellation/test-auto-promote.py` — happy path (promotes to orchestrator), orchestrator-offline (queues), recovery (queue drains on next cycle), 4xx (moves to failed/), queue-full (rejects new at 100).

**Success criteria:**
- User says `/remember X` on peer-b → mem-fusion stores locally AND `promoted_to[]` shows `status=stored` with `canonical_id`.
- Kill orchestrator → user says `/remember Y` → `promoted_to[]` shows `status=queued` with reason. Queue file exists.
- Restart orchestrator → next 30s cycle drains queue → memory Y now in canonical.
- 100 queued memories → 101st `store_memory` returns `status: "queue_full"`. Local memory still stored.
- Send malformed body (e.g., content_hash mismatch) → 400 → moved to `queue/failed/`. Not retried. SessionStart surfaces it.

**Stop point:** Group memory sharing has the least-friction UX described in `docs/CONSTELLATION_ARCHITECTURE.md` §5. Auto-promote works; failures are visible.

## Deferred to post-MVP

Explicitly NOT shipping in v0.3.0. No commitment to specific release timing; these will be scoped as real usage surfaces needs. Listed here for traceability of design discussions.

| Item | Why it's not in MVP |
|---|---|
| Push notifications (orchestrator → peer webhooks, subscriptions) | v0.3.0 pull-only sync sufficient for the MVP demo; push adds peer-side webhook-listener infrastructure that earns its keep only at scale |
